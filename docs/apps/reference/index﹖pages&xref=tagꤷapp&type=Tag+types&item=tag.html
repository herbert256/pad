{meta title='Application tests'}

<p>An application keeps its own tests in <code>_tests/</code>. A test is a page there -
<code>cart.pad</code>, with <code>cart.php</code> when it needs data - next to its answer,
<code>cart.txt</code>. <code>pad test shop</code> renders every test page and compares:</p>

{ignore}
<code>$ pad test shop
shop
  ok    cart
  FAIL  checkout
        want: <p>Total 42</p>
        got:  HTTP 500 - assert failed: $total eq 42
              apps/shop/_tests/checkout.pad:1:1  {assert $total eq 42}
  2 tests, 1 failed</code>
{/ignore}

<h2>The answer</h2>

<ul>
  <li>the exact output of the page, trimmed;</li>
  <li><code>/a pattern/</code> matched over it - for output that changes, a date or a count;</li>
  <li><code>HTTP 500</code>, with an optional <code>/pattern/</code> on the next line, for a test that is meant to fail.</li>
</ul>

<p>A test without an answer counts against the run; <code>pad test shop --record</code> writes
the missing answers from what the pages render now, and never overwrites one.
<code>pad test --all</code> runs every application that has tests, and <code>./ci.sh</code>
does that as its <code>apptests</code> line.</p>

<h2>Asserts</h2>

<p>{tag 'assert'} holds a page to a condition during a test run: false, and the test fails
with the condition and the message as its report. Anywhere else it is silent - the
condition is not even evaluated - so it can stay in the application's own pages. The switch
is <code>$padAssert</code>, which <code>pad test</code> turns on; this example turns it on in
its PHP:</p>

{example 'fragments/app_tests_1'}

<h2>A test page</h2>

<p>It is a page like any other, rendered bare - without the application's wrappers - and no
URL reaches it. It can bring in a real page with <code>{page 'cart'}</code>, or
include the page's own PHP and check the data it sets:</p>

{ignore}
<code>_tests/cart.php    <?php include APP . 'cart.php'; ?>
_tests/cart.pad    {assert $total eq 42, 'the cart total'}
                   <p>Total {$total}</p>
_tests/cart.txt    <p>Total 42</p></code>
{/ignore}

{meta title='Charts'}

<p>{tag 'chart'} draws a chart as inline SVG on the server. There is no JavaScript, so the
chart prints, works where scripts do not run, and caches like any other output. A
<code>bar</code> chart puts columns on a zero baseline; a <code>line</code> chart draws a line
over a light wash with the last point marked.</p>

{example 'fragments/charts_1'}

<h2>Where the numbers come from</h2>

<ul>
  <li><code>data='sales'</code> - a {tag 'data'} store, a sequence store, an array of the page's PHP, or a <code>_data</code> file of that name.</li>
  <li><code>value=</code> names the field with the number, <code>label=</code> the field for the axis. Without them the first numeric field is the value and the first other field the label.</li>
  <li><code>sequence='fibonacci', rows=12</code> - the first terms of a sequence, for demo data straight away.</li>
</ul>

<h2>Sparklines</h2>

<p>{tag 'sparkline'} is a line chart the size of a word, without axes, to stand in a sentence
or a table cell.</p>

{example 'fragments/charts_2'}

<h2>Accessible and themeable</h2>

<p>Every chart is an image to a screen reader (<code>role="img"</code>), named by its
<code>title=</code> and described by a list of its values. Each bar and point carries its own
tooltip. The colours are CSS custom properties - <code>--pad-chart-series</code>,
<code>--pad-chart-text</code>, <code>--pad-chart-grid</code>, <code>--pad-chart-surface</code> -
set on <code>.pad-chart</code>, and their defaults follow the page's
<code>color-scheme</code>, light or dark.</p>

{meta title='Comments'}

<p>PAD has two comment forms. Both are taken out of the template before it is scanned, so a tag written inside one never runs and nothing of it reaches the output.</p>

<ul>
  <li><code>{# ... #}</code> - the original form</li>
  <li><code>{-- ... --}</code> - the form the editor kits highlight and toggle</li>
</ul>

{example 'fragments/comments_1'}

<h2>Rules</h2>

<ul>
  <li>A comment closes at the first <code>#}</code> or <code>--}</code> after it, and may span lines.</li>
  <li><code>{--</code> must be followed by whitespace: a CSS custom property inside an {tag 'ignore'} block, <code>:root{--gap:4px}</code>, is CSS and stays as it is.</li>
  <li><code>{#name}</code> is not a comment but the option sigil - the value of the tag option <code>name</code>.</li>
</ul>

<h2>See Also</h2>

<ul>
  <li>{manual 'ignore'} - keep PAD from parsing braces</li>
</ul>

{meta title='Template coverage'}

<p>A test suite says what it checks; coverage says what it reaches. With coverage on, every
local request notes which templates it read, which of their tags ran, and which branch each
{tag 'if'} and {tag 'case'} took. The report then shows each template with the parts that
never ran marked.</p>

{example 'fragments/coverage_1'}

<ul>
  <li><code>$padCoverage = TRUE</code> in <code>_config/config.php</code> records into the run
      <code>default</code>; a name instead of TRUE records into a run of that name, and
      <code>?page&amp;padCoverage=name</code> records one request.</li>
  <li><code>develop/?coverage&amp;start=suites</code> records every local request of every
      application until <code>develop/?coverage&amp;stop</code> - start it, run the suites,
      stop it, and <code>develop/?coverage&amp;run=suites</code> lists every template with the
      share of its tags and branches that ran, and the files no request read at all.</li>
  <li>A run is a file of JSON lines, <code>DATA/coverage/<run>.jsonl</code>, one line per
      request. Only local requests are recorded.</li>
  <li>An {if} without an {else} has one branch more: the run in which
      its condition was false. It is marked on the {/if}.</li>
</ul>

App: manual - Page: pages/csrf_protection
PHP
 HTML
pages/csrf_protection.pad 		Result 
{meta title='CSRF protection'}

<p>Another site can make a visitor's browser post to your application - a hidden form that
submits itself - and the browser sends your session cookie along. A CSRF token tells those
posts apart from the ones your own forms send: a random value kept in the visitor's session
and written into your form, which another site can make the browser send but cannot read.</p>

<h2>One setting</h2>

<p>With <code>$padCsrf = TRUE</code> in <code>_config/config.php</code> every
<code><form method="post"></code> of a page gets a hidden <code>padCsrfToken</code> field
holding the token, and every POST - and PUT, PATCH and DELETE - that does not bring the token
back is answered <code>403</code> before any of the application runs. The forms an
application already has are protected without a change to them. A form that posts to another
site gets no token, and neither does a GET form, whose fields end up in the url.</p>

<h2>The {csrf} tag</h2>

<p>{tag 'csrf'} writes the field itself, for a form the page builds some other way, or for
an application that leaves <code>$padCsrf</code> off and checks a post by hand with
<code>padCsrfValid ()</code>. <code>{csrf token}</code> is the bare token, for a
script that sends it in an <code>X-CSRF-Token</code> header:</p>

{example 'fragments/csrf_protection_1'}

<ul>
  <li>The token is one per session, so two open tabs and the back button keep working. The
  session starts the first time a token is needed.</li>
  <li>A page carrying a token is never stored in the page cache - it would hand one visitor's
  token to the next.</li>
  <li>An application that accepts posts from elsewhere on some pages - a webhook - switches
  <code>$padCsrf</code> off for those pages in its <code>_config/config.php</code>, which
  knows <code>$padPage</code>.</li>
</ul>

{meta title='Directory guards'}

<p>A <code>_guard.php</code> in a directory decides, for every page below it, whether the
request may see the page - before any <code>_inits.php</code> or page PHP runs. Access
control follows the file tree: put one in <code>admin/</code> and every page there is
protected, with no list of routes to keep in step.</p>

<p>The guard of this manual's <code>guarded/</code> directory:</p>

{source 'guarded/_guard.php'}

<ul>
  <li>Returning <code>FALSE</code> - or anything that is not true: <code>NULL</code>,
  <code>0</code>, <code>''</code> - refuses the page with <code>403 Forbidden</code>. Returning
  <code>TRUE</code>, or no return at all, lets the request through to the next guard down.</li>
  <li>The guards run from the application root down, each directory's in turn, after the
  <code>_lib</code> files, so a guard can call the application's functions and read the session
  and request variables - and <code>$padPage</code>, to decide per page.</li>
  <li>A guard can send the visitor elsewhere itself: <code>padRedirect ( 'login' )</code>.</li>
  <li>A page a {tag 'page'} tag includes is guarded too: when its guard says no, it renders as
  nothing, and the page that includes it carries on.</li>
  <li>A guarded page is never served from the page cache, nor stored in it.</li>
</ul>

pages/file_uploads.pad 		Result 
{meta title='File uploads'}

<p><code>padUpload</code> takes the file of one form field and stores it safely:</p>

<ul>
  <li>its real type comes from its content - not from the type the browser claims, and not
  from its name - and is held against the types you allow, <code>image/*</code> for any image;</li>
  <li>a file over the size you allow, <code>'2M'</code>, <code>'500K'</code> or bytes, is refused;</li>
  <li>it is stored under a random name in <code>DATA/uploads/</code>, with the extension of
  what it really is, never under the name the visitor's file had.</li>
</ul>

{example 'fragments/file_uploads_1'}

<p>The answer is the record of the stored file - <code>name</code> (the visitor's own file
name, for showing only), <code>file</code> (the path under <code>DATA</code>, for
<code>padFileGet</code>), <code>path</code>, <code>size</code>, <code>type</code> and
<code>extension</code> - or <code>NULL</code> when the field brought no file, or
<code>FALSE</code> when the file was refused. <code>padUploadError ( 'avatar' )</code> says
why, and the {tag 'input'} file field of the form shows it beside itself, in the words of its
label.</p>

<p>A {tag 'form'} holding a file field posts as <code>multipart/form-data</code> by itself;
without that the browser sends only the file's name.</p>

{meta title='Flash messages'}

<p>A page that takes a post redirects the browser to a plain page, so a refresh cannot post
twice - and then the page the browser lands on has to say what happened. A flash message
carries that: <code>padFlash ( 'Thanks, your message was sent.' )</code> before the

{example 'fragments/flash_messages_1'}

<ul>
  <li>{tag 'flash'} renders its content once per message, with <code>{$message}</code>
  and <code>{$type}</code>; without a message the <code>@else@</code> half renders.
  <code>{flash 'error'}</code> shows the messages of that type only.</li>
  <li>The type is the second argument of <code>padFlash</code>, <code>info</code> when it is
  left out.</li>
  <li>A message lives exactly one request after the one that flashed it - the redirect's
  destination - and is gone after that, shown or not. A page that flashes and renders itself
  shows it at once, as here.</li>
  <li>The message is kept in the session, which starts on demand. A small

pages/forms.pad 		Result 
{meta title='Forms'}

<p>{tag 'form'}, {tag 'input'} and {tag 'textarea'} write the fields of a form. When the
form comes back with mistakes in it, each field shows again what was typed - escaped - and
the message for its mistake beside it. <code>padValidate</code> in the page's PHP finds the
mistakes.</p>

{example 'fragments/forms_1'}

<ul>
  <li>{tag 'form'} posts back to the page and carries the session's CSRF token (see
  {manual 'csrf_protection'}) and its name: <code>padPosted ( 'contact' )</code> is true when
  this form came back, so a page with two forms knows which one did.</li>
  <li>{tag 'input'} and {tag 'textarea'} take the field name first; <code>label=</code> writes a
  label tied to the field, <code>value=</code> the value before anything was posted, and every
  other item is an attribute of the field, as {tag 'attrs'} writes it - <code>required</code>,
  <code>rows=6</code>, <code>placeholder='...'</code>.</li>
  <li>A checkbox or radio is checked when the posted value is its own value; a password or
  file field is never refilled.</li>
</ul>

<h2>Validation</h2>

<p><code>padValidate ( $rules )</code> checks the posted values and answers one message per
field that breaks a rule, keyed by the field - empty when all is well. A second argument
checks other data; a third replaces messages, per field (<code>'email'</code>) or per field
and rule (<code>'email.required'</code>):</p>

{example 'fragments/forms_2'}

<p>The rules: <code>required</code>, <code>email</code>, <code>url</code>, <code>numeric</code>,
<code>integer</code>, <code>min:n</code> and <code>max:n</code> (a length, or a value with
<code>numeric</code> or <code>integer</code>), <code>in:a,b,c</code>, <code>regex:/.../</code>,
<code>same:other_field</code>, <code>accepted</code> and <code>date</code>. An empty field is
checked for <code>required</code> only. A rule name nothing knows is an error.</p>

<h2>After a failed post</h2>

<p>The fields of the form that came back show the message beside them, in the words of their
own label, tied to the field with <code>aria-invalid</code> and
<code>aria-describedby</code> so a screen reader reads them together. Here the post is
pretended in the PHP, the way a visitor's would arrive:</p>

{example 'fragments/forms_3'}

<p>After a post that passes, store it and send the visitor on with <code>padRedirect ()</code>:
a refresh of the page they land on does not post a second time.</p>

<h2>Rules in the template</h2>

<p>The rules can stand on the fields themselves: <code>rules='required|email'</code> on an
{tag 'input'} or a {tag 'textarea'}. They are read from the page's template before its PHP
runs, and a post of the form is checked against them there - <code>padPosted ( 'contact' )</code>
is true only for a post that kept them, so the PHP acts on a good post alone. A post that broke
one renders the form again, refilled, with the messages beside the fields and the form's
<code>error=</code> above them (<code>error</code> alone says "Please correct the errors
below."):</p>

{example 'fragments/forms_4', skipResult}

<ul>
  <li>Only what is written out counts: quoted rules, on a field with a quoted name, in a
  {tag 'form'} with a name that posts back to its own page. Rules on a field in a snippet, a
  custom tag, a {tag 'page'} or a layout, rules made from a variable, rules in a form with
  <code>action=</code> or <code>method='get'</code> and rules on a file field are errors -
  nothing would check them.</li>
  <li>Every field of the posted form that has rules is checked, also one in an {tag 'if'}
  branch that did not render. A field that is there only sometimes keeps its check in the
  PHP: <code>padValidate</code> adds its messages to those of the template.</li>
  <li><code>padFormFailed ( 'contact' )</code> is true when the form came back and broke its
  rules.</li>
</ul>

{meta title='Ignore - Preventing PAD from Parsing Curly Braces'}

<p>The {tag 'ignore'} feature tells PAD not to parse curly braces <code>{}</code> as PAD tags within specific content. This is essential when working with JavaScript, JSON data, CSS, or any content that uses curly braces for its own syntax.</p>

<h2>Why Use Ignore?</h2>

<p>PAD normally parses all <code>{}</code> pairs as potential PAD tags. When your content contains curly braces that should be treated as literal text (like JavaScript code or JSON data), you need to tell PAD to ignore them.</p>

<h2>Three Ways to Use Ignore</h2>

<h3>1. As a Tag Pair: <code>{ignore}...{/ignore}</code></h3>

<p>Wrap content in ignore tags to prevent PAD from parsing any curly braces within that block. This is commonly used for inline JavaScript or CSS.</p>

<h4>Example 1: JavaScript with Object Literals</h4>

<p>Without {tag 'ignore'}, PAD would try to parse the JavaScript object literal as PAD tags:</p>

{example 'fragments/ignore_1'}

<h4>Example 2: Inline CSS with Selector Blocks</h4>

<p>CSS uses curly braces for selector blocks. Wrap in {tag 'ignore'} to prevent PAD from parsing them:</p>

{example 'fragments/ignore_2'}

<h3>2. As a Pipe Function: <code>| ignore</code></h3>

<p>Apply ignore to the output of an expression to prevent PAD from parsing curly braces in that output. This is useful when passing JSON data to JavaScript.</p>

<h4>Example 3: JSON Data in Attributes</h4>

<p>When a variable contains JSON data, use the {tag 'ignore'} pipe function to prevent PAD from parsing the curly braces:</p>

{example 'fragments/ignore_4'}

<p>The JSON data was passed from PAD/PHP through a data attribute using <code>{echo $usersJson | ignore}</code>.</p>

<h3>3. As an Option: <code>ignore</code></h3>

<p>Add the ignore option to a tag to prevent PAD from parsing curly braces in its content.</p>

<h4>Example 4: A Tag with JSON in it</h4>

<p>Use the {tag 'ignore'} option on a tag to prevent PAD from parsing curly braces in its content:</p>

{example 'fragments/ignore_5'}

<p>Without the ignore option, PAD would try to parse <code>{"theme": "dark"}</code> as PAD tags, causing errors.</p>

<h2>Best Practices</h2>

<ul>
  <li><strong>Always use {tag 'ignore'} for JavaScript blocks</strong> - Any <code><script></code> tag with JavaScript should be wrapped</li>
  <li><strong>Use <code>| ignore</code> for dynamic JSON</strong> - When expressions output JSON, pipe through ignore</li>
  <li><strong>Keep CSS in external files</strong> - But if inline CSS is needed, wrap in {tag 'ignore'}</li>
  <li><strong>Minimal scope</strong> - Only wrap what needs to be ignored, not entire templates</li>
  <li><strong>Not needed for HTML</strong> - Regular HTML doesn't use curly braces, no ignore needed</li>
</ul>

<h2>What Gets Ignored?</h2>

<p>When ignore is active, PAD will NOT parse:</p>

<ul>
  <li><code>{variableName}</code> - Not treated as a variable reference</li>
  <li><code>{tagName}</code> - Not treated as a PAD tag</li>
  <li><code>{if condition}...{/if}</code> - Not treated as conditional</li>
  <li><code>{echo $expr}</code> - Not treated as expression</li>
</ul>

<p>Everything within ignored content is treated as <strong>literal text</strong>.</p>

<h2>Important Notes</h2>

<ul>
  <li><strong>Cannot nest</strong> - Once inside an ignore block, all content is literal until <code>{/ignore}</code></li>
  <li><strong>Use sparingly</strong> - Only use where necessary to avoid confusion</li>
  <li><strong>External files preferred</strong> - For large JavaScript or CSS, use external files instead of inline code</li>
</ul>
