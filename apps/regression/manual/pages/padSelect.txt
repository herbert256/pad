<p>The Select subsystem makes the tables of the application database tags. A table is
declared once in PHP - in <code>$padSelect</code>, with its key and the order of its rows - and
from then on its name is a tag that walks its rows, every column a field. The relations
between the tables are declared in <code>$padRelations</code>, and a table nested in another
reads only the rows related to the row around it: the template walks the database without a
join written anywhere. The examples read the Classic Models tables of the demo database; the
<a href="http://localhost/pad/padSelect/">padSelect application</a> shows every option over a music
catalogue, each with the SQL PAD sent for it.</p>

<p>An application declares its tables in <code>_lib/select.php</code>, so every page has them;
the examples here declare them in their own PHP half.</p>

<h2>Options on the tag</h2>

<p><code>where=</code>, <code>order=</code>, <code>having=</code> and <code>group=</code> are SQL
the template writes, so each is a quoted string. A value goes into them as <code>$name</code>:
in <code>where=</code> and <code>having=</code> it is bound as an escaped literal of that
variable, never as SQL; in <code>order=</code> and <code>group=</code> it must hold column
names. <code>rows=</code> and <code>page=</code> are the SQL limit, and
<code>$field=value</code> picks rows by a field of the declared key.</p>

<h2>Relations</h2>

<p>A relation is declared from the table that holds the reference -
<code>$padRelations ['employees'] ['offices']</code> - and is followed both ways: nested in an
office, <code>{employees}</code> is the people of that office, and nested in an
employee, <code>{offices}</code> would be the office they work in. Every enclosing
table counts, not only the nearest. A nested table with <code>fields="count(*) as n"</code>
counts the related rows in the SQL.</p>

<h2>Views - a table that stands on another</h2>

<p><code>base=</code> makes a virtual table: it takes what it does not declare - the table, the
key, the order - from its base, a <code>where</code> of its own adds to the base's, and it
follows the relations of its base. Two names for one table relate it to itself: an employee
and the manager they report to.</p>

<h2>The options</h2>

<p>Each can stand in the declaration or on the tag; the tag's wins.</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>option</th><th>what it is</th></tr>
  <tr><td><code>key</code></td><td>the field, or the fields, that name one row</td></tr>
  <tr><td><code>db</code></td><td>the table read, when it is not the tag's name</td></tr>
  <tr><td><code>base</code></td><td>the table a view stands on - in the declaration only</td></tr>
  <tr><td><code>fields</code></td><td>the column list; declared as an array, column => alias</td></tr>
  <tr><td><code>where</code>, <code>order</code></td><td>the SQL condition and sort</td></tr>
  <tr><td><code>group</code>, <code>having</code>, <code>rollup</code></td><td>a row per group, a condition on the groups, the total row</td></tr>
  <tr><td><code>distinct</code>, <code>distinctrow</code>, <code>all</code></td><td>the word after select</td></tr>
  <tr><td><code>join</code>, <code>union</code></td><td>more tables in the row, more rows in the list</td></tr>
  <tr><td><code>rows</code>, <code>page</code></td><td>the SQL limit</td></tr>
  <tr><td><code>type</code></td><td><code>array</code> (every row), <code>record</code> (one row) or <code>field</code> (one value)</td></tr>
  <tr><td><code>htmlAttrJson</code></td><td>the rows as JSON, escaped for an HTML attribute</td></tr>
</table>

<p>The rows a select answers go through the handling options of every tag after the SQL -
<code>sort=</code>, <code>first=</code> - and the properties of a loop work on them. The full
reference is <code>docs/DATABASE.md</code> in the repository; the
<a href="http://localhost/pad/classicModels/">classicModels application</a> walks these tables a level
further.</p>
