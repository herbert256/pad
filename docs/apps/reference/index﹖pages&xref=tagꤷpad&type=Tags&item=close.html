App: alpine - Page: guide
PHP
 HTML
guide.pad 		Result 
{meta title='Guide - PAD + Alpine'}
<header class="example-head">
  <h1>Alpine on a PAD page</h1>
  <p class="lede">
    Alpine reads attributes, PAD writes them. Both love braces - so give each its own, hand
    Alpine its state as JSON, and let it talk back to the page that wrote it.
  </p>
</header>

<h2>1. The braces</h2>
<p>PAD reads every <code>{</code> of a template as the start of a tag; Alpine writes objects
   with them. Three ways that never collide:</p>
<div class="grid">
  <div class="card">
    <h3>State from PHP</h3>
    <p>The ^ sigil writes a field as JSON, escaped for the attribute - <code>x-data="{^profile}"</code>.
       No brace of Alpine's in the template, and a quote in a value stays text.</p>
  </div>
  <div class="card">
    <h3>Components in a file</h3>
    <p><code>Alpine.data('tabs', ...)</code> in a script of <code>www/</code>, called by name:
       <code>x-data="tabs({^tabs})"</code> - the file never meets the PAD parser.</p>
  </div>
  <div class="card">
    <h3>A space after the brace</h3>
    <p><code>x-data="{ open: false }"</code> written as <code>{ open: false }</code> -
       a brace with a space after it is no PAD tag. It works for a short object; prefer the other two.</p>
  </div>
</div>

<h2>2. Load order</h2>
<p>The application's scripts first, Alpine last and deferred - a page's components register
   themselves on <code>alpine:init</code> before Alpine walks the page:</p>
{highlight 'html'}
<script src="alpine-app.js"></script>                         <!-- pad.get, pad.post -->
<script defer src="https://unpkg.com/alpinejs@3/dist/cdn.min.js"></script>
...
<script src="examples/search.js"></script>                    <!-- Alpine.data('search', ...) -->
{/highlight}

<h2>3. Talking back</h2>
<p>A page answers JSON when asked - <code>?page&amp;padFormat=json</code> - with only what its PHP
   names in <code>$padExpose</code>; the templates do not run for it. A post carries the session's
   token in a header, read from <code><meta name="csrf-token" content="{csrf token}"></code>:</p>
{highlight 'js'}
const answer = await pad.get('examples/search', { q: this.q });   // the JSON of $padExpose
const saved  = await pad.post('examples/todos', { op: 'add', text }); // X-CSRF-Token sent
{/highlight}

<h2>4. One set of rules</h2>
<p>Keep a form's rules in PHP: <code>padValidate ( $rules )</code> checks the post,
   <code>padValidateClient ( $rules )</code> hands them to the component, {validator} brings the
   checker, and <code>padValidate.field ( rules.email, value, form )</code> answers in the server's
   words.</p>

<h2>5. Events from the server</h2>
<p><code>padSse()</code> streams JSON events; an <code>EventSource</code> opened in
   <code>x-init</code> - in a component that closes it again in <code>destroy()</code> - turns them
   into state.</p>

<div class="callout"><p>Values are text: whatever a visitor typed, the ^ sigil writes it as JSON escaped for the attribute,
   and <code>x-text</code> puts it in as text. Avoid <code>x-html</code> with data that is not yours.</p></div>

App: htmx - Page: guide
PHP
 HTML
guide.pad 		Result 
{meta title='Guide - PAD + htmx'}
<header class="example-head">
  <h1>How PAD answers htmx</h1>
  <p class="lede">
    htmx asks for HTML and swaps it in. A PAD page is HTML with names on its parts - so the
    same template answers the browser's first visit and every question htmx asks after it.
  </p>
</header>

<h2>1. Name the part</h2>
<p>A {fragment} around the part that changes; the element around it gets the same name
   as its id:</p>
{highlight 'pad'}
<input name="q" hx-get="?products" hx-trigger="input changed delay:300ms" hx-target="#results">

<ul id="results">
  {fragment 'results'}
    {products}<li>{$name}</li>{/products}
  {/fragment}
</ul>
{/highlight}

<h2>2. PAD answers the part alone</h2>
<p>htmx sends <code>HX-Request: true</code> and the id of the element it swaps in
   <code>HX-Target</code>. When the page has a fragment of that name, the answer is that fragment
   and nothing else - no wrapper, no rest of the page; when it has none the page renders whole,
   as it always did. A request can also name the fragment itself, for an element without an id
   or another part than the target:</p>
{highlight 'pad'}
<tr hx-get="?orders&p=2&padFragment=rows" hx-trigger="revealed" hx-swap="afterend">
{/highlight}
<p>The page's PHP runs as for any request - <code>$q</code> is the request's value - and may narrow
   what the fragment shows: <code>$padFragmentOnly = 'row'</code> sets the answer from PHP. A
   fragment inside a loop answers with the first row it renders, so narrow the rows to the one
   asked for.</p>

<h2>3. Posts carry the token</h2>
<p>With <code>$padCsrf</code> on, a post without the session's token is refused before the page
   runs. A {form} carries it as a field; for an <code>hx-post</code> on anything else, put
   the header on the body once - the ^ sigil writes the array as JSON for the attribute:</p>
{highlight 'pad'}
<body hx-headers="{^headers}">          <!-- $headers = [ 'X-CSRF-Token' => padCsrfToken () ] -->
{/highlight}

<h2>4. Forms check the same rules twice</h2>
<p>Fields with <code>rules=</code> are checked on the server before the PHP runs, and with
   <code>client</code> in the browser first. Posted through htmx, a form that broke a rule comes
   back as its own fragment, refilled, with PAD's messages beside the fields:</p>
{highlight 'pad'}
<div id="signup">{fragment 'signup'}
  {form 'signup', client, error, hx-post='?signup', hx-target='#signup'}
    {input 'email', label='E-mail', rules='required|email'}
  {/form}
{/fragment}</div>
{/highlight}

<h2>5. More than one place</h2>
<p>An answer can update other parts of the page as well: elements in it marked
   <code>hx-swap-oob="true"</code> go where their id is - the cart count in the header, a summary
   beside the list.</p>

<h2>6. Pushed by the server</h2>
<p><code>padSse()</code> keeps a page's connection open and sends events; with htmx's sse
   extension each event's HTML is swapped in as it arrives:</p>
{highlight 'pad'}
<div hx-ext="sse" sse-connect="?ticker" sse-close="done">
  <ol sse-swap="tick" hx-swap="afterbegin"></ol>
</div>
{/highlight}

<div class="callout"><p>The page cache knows htmx: a request for a part is answered fresh and never stored, and a
   fragment chosen by a header is never stored under the page's address.</p></div>

{meta title='Alpine'}

<p>Alpine adds behaviour to HTML with attributes - and PAD writes that HTML. Both use braces,
and PAD reads every <code>{</code> of a template as the start of a tag, so the state of a
component comes from the page's PHP as JSON instead:</p>

{ignore}
<code><div x-data="{^profile}">                <!-- $profile = [ 'name' => 'Ada', 'likes' => 12 ] -->
  <h2 x-text="name"></h2>
  <button @click="likes++">♥ <span x-text="likes"></span></button>
</div></code>
{/ignore}

<p>The ^ sigil writes a field as JSON escaped for the attribute: a quote or a brace in a value
stays text. Three ways keep the braces apart:</p>

<ul>
  <li><b>State from PHP</b> - <code>x-data="{^field}"</code>, as above.</li>
  <li><b>Components in a file</b> - <code>Alpine.data('tabs', list => (...))</code> in a script of
      <code>www/</code>, called by name with PAD's data: <code>x-data="tabs({^tabs})"</code>.
      Load the page's scripts before Alpine, and Alpine with <code>defer</code>.</li>
  <li><b>A space after the brace</b> - <code>{ open: false }</code> is no PAD tag; fine for a short
      object.</li>
</ul>

<h2>Talking back</h2>

<p>A component asks the page that wrote it: <code>?page&amp;padFormat=json</code> answers what
the page's PHP names in <code>$padExpose</code> ({manual 'data_answers'}). A post carries the
session's token in an <code>X-CSRF-Token</code> header, read from
<code><meta name="csrf-token" content="{csrf token}"></code>. A form's rules can live in
PHP for both sides - <code>padValidateClient ( $rules )</code> for the browser,
<code>padValidate ( $rules )</code> for the post ({manual 'client_validation'}) - and
<code>padSse()</code> streams events an <code>EventSource</code> in <code>x-init</code> turns into
state ({manual 'server_sent_events'}).</p>

<p>The Alpine application shows each of these, with its template, PHP and script:
<a href="{$padHost}alpine/">alpine</a>.</p>

{meta title='Application tests'}

<p>An application keeps its own tests in <code>_tests/</code>. A test is a page there -
<code>cart.pad</code>, with <code>cart.php</code> when it needs data - next to its answer,
<code>cart.txt</code>. <code>pad test shop</code> renders every test page and compares:</p>

{ignore}
<code>$ pad test shop
shop
  ok    cart
  FAIL  checkout
        want: <p>Total 42</p>
        got:  HTTP 500 - assert failed: $total eq 42
              apps/shop/_tests/checkout.pad:1:1  {assert $total eq 42}
  2 tests, 1 failed</code>
{/ignore}

<h2>The answer</h2>

<ul>
  <li>the exact output of the page, trimmed;</li>
  <li><code>/a pattern/</code> matched over it - for output that changes, a date or a count;</li>
  <li><code>HTTP 500</code>, with an optional <code>/pattern/</code> on the next line, for a test that is meant to fail.</li>
</ul>

<p>A test without an answer counts against the run; <code>pad test shop --record</code> writes
the missing answers from what the pages render now, and never overwrites one.
<code>pad test --all</code> runs every application that has tests, and <code>./ci.sh</code>
does that as its <code>apptests</code> line.</p>

<h2>Asserts</h2>

<p>{tag 'assert'} holds a page to a condition during a test run: false, and the test fails
with the condition and the message as its report. Anywhere else it is silent - the
condition is not even evaluated - so it can stay in the application's own pages. The switch
is <code>$padAssert</code>, which <code>pad test</code> turns on; this example turns it on in
its PHP:</p>

{example 'fragments/app_tests_1'}

<h2>A test page</h2>

<p>It is a page like any other, rendered bare - without the application's wrappers - and no
URL reaches it. It can bring in a real page with <code>{page 'cart'}</code>, or
include the page's own PHP and check the data it sets:</p>

{ignore}
<code>_tests/cart.php    <?php include APP . 'cart.php'; ?>
_tests/cart.pad    {assert $total eq 42, 'the cart total'}
                   <p>Total {$total}</p>
_tests/cart.txt    <p>Total 42</p></code>
{/ignore}

{meta title='Options of your own'}

<p>A file in the application's <code>_options/</code> directory makes its name an option
of every tag - written bare, <code>{staff words}</code>, or with a value,
<code>{staff wrap='em'}</code>. Where the file stands decides when it runs:</p>

{meta title='Comments'}

<p>PAD has two comment forms. Both are taken out of the template before it is scanned, so a tag written inside one never runs and nothing of it reaches the output.</p>

<ul>
  <li><code>{# ... #}</code> - the original form</li>
  <li><code>{-- ... --}</code> - the form the editor kits highlight and toggle</li>
</ul>

{example 'fragments/comments_1'}

<h2>Rules</h2>

<ul>
  <li>A comment closes at the first <code>#}</code> or <code>--}</code> after it, and may span lines.</li>
  <li><code>{--</code> must be followed by whitespace: a CSS custom property inside an {tag 'ignore'} block, <code>:root{--gap:4px}</code>, is CSS and stays as it is.</li>
  <li><code>{#name}</code> is not a comment but the option sigil - the value of the tag option <code>name</code>.</li>
</ul>

<p>A tag of your own with a <code>.pad</code> template is a component: the caller's content goes where the template writes {construct 'content'}. Named slots give it more than one place for content, and <code>{parms}</code> says which parameters it takes. The card below is <code>_tags/card.pad</code>:</p>

{source '_tags/card.pad'}

{example 'fragments/components_1'}

<h2>Slots</h2>

<ul>
  <li>A <code>{slot 'footer'}...{/slot}</code> pair standing directly in the content of the tag is a fill: it is taken out of the content and goes where the template has its <code>{slot 'footer'}</code>. The rest of the content goes to {construct 'content'}.</li>
  <li>In the template, the content of a <code>{slot}</code> is its default, rendered when the caller gave no fill. <code>{slot 'header'/}</code> in the caller's content is an empty fill.</li>
  <li>A default holding {construct 'content'} is a frame: <code>{slot 'footer'}<small>&#64;content&#64;</small>{/slot}</code> renders the frame round the fill, and nothing - or its {construct 'else'} part - when there is no fill.</li>
  <li>A fill is the caller's text: it renders with the caller's variables, and a <code>{#name}</code> or a <code>{slot}</code> inside it belongs to the caller's tag - which is how a template passes a slot of its own on to a tag it uses.</li>
</ul>

<h2>Every use has its own</h2>

<p>The fills belong to one use of the tag, so a card inside a card keeps its own footer:</p>

{example 'fragments/components_2'}

<h2>Declared parameters</h2>

<ul>
  <li><code>{parms title, tone='plain'}</code> at the top of the template declares the parameters: a name alone is required, <code>name=default</code> fills in what the caller left out. Both read as <code>{#title}</code>.</li>
  <li>A required parameter left out is an error, and so - under the strict check - is a parameter the tag does not declare: <code>{card title='x', titel='y'}</code> is reported by name.</li>
</ul>

<h2>Components written in the template</h2>

<p>A component used on one page only needs no file of its own. <code>{define 'name'}...{/define}</code> writes it in the template: from there on <code>{name}</code> renders the body as <code>_tags/name.pad</code> would - <code>{parms}</code>, <code>{#name}</code>, {construct 'content'} and slots work alike.</p>

{example 'fragments/components_3'}

<p>A <code>{macro}</code> is called the way a function is: its parameters are declared on it - a name alone required, <code>name=default</code> filling in - given in their order or by name, and read as fields, <code>{$label}</code>.</p>

{example 'fragments/components_4'}

<ul>
  <li>Both render at every use, in its place and with its fields; both can use themselves, for the rows below the current one.</li>
  <li>A define or macro exists from the point it is walked, as a <code>{content}</code> store does: a use before it is an unknown tag.</li>
  <li>A macro given too many values, missing a required one, or given a name it does not declare is an error.</li>
</ul>
