<?php

  $title = 'Calendar';

  // The agenda of the month on show - the one the calendar's links ask for, else this
  // one: a stand-up every Monday, payday on the 25th, drinks on the last Friday and a
  // release on the second Tuesday.

  $shown = padCalendarMonth ( $_GET ['month'] ?? '' ) ?? padNow ( 'Y-m' );
  $first = new DateTimeImmutable ( "$shown-01" );

  $agenda = [];

  for ( $day = $first; $day->format ( 'Y-m' ) == $shown; $day = $day->modify ( '+1 day' ) )
    if ( $day->format ( 'N' ) == 1 )
      $agenda [] = [ 'when' => $day->format ( 'Y-m-d' ), 'what' => 'Stand-up' ];

  $agenda [] = [ 'when' => $first->modify ( 'second tuesday of this month' )->format ( 'Y-m-d' ), 'what' => 'Release' ];
  $agenda [] = [ 'when' => "$shown-25",                                                         'what' => 'Payday' ];
  $agenda [] = [ 'when' => $first->modify ( 'last friday of this month' )->format ( 'Y-m-d' ),   'what' => 'Drinks' ];

?>
 
<p>The <code>{ignore}{calendar}{/ignore}</code> tag draws a month with its events - from a <code>{ignore}{data}{/ignore}</code>
block, a page array or a <code>_data</code> file. The arrows move a month; today is marked.</p>

{calendar data='agenda', title='what'}

<p><code>{ignore}{calendar data='agenda', title='what'}{/ignore}</code></p>

<h2>Your own markup</h2>

<p>As a pair the tag hands over the weeks and their days as rows - <code>$day</code>, <code>$date</code>,
<code>$today</code>, <code>$count</code>, <code>$class</code>, the day's <code>events</code> - so a
mini calendar with a dot per busy day is a few lines:</p>

<table class="mini">
  <tr><th>Mo</th><th>Tu</th><th>We</th><th>Th</th><th>Fr</th><th>Sa</th><th>Su</th></tr>

    {days}<td class="{$class}" title="{$date}">{$day}{if $count gt 0}<i></i>{/if}</td>{/days}

  {/calendar}

App: manual - Page: pages/alpine
PHP
 HTML
pages/alpine.pad 		Result 
{meta title='Alpine'}

<p>Alpine adds behaviour to HTML with attributes - and PAD writes that HTML. Both use braces,
and PAD reads every <code>{</code> of a template as the start of a tag, so the state of a
component comes from the page's PHP as JSON instead:</p>

{ignore}
<code><div x-data="{^profile}">                <!-- $profile = [ 'name' => 'Ada', 'likes' => 12 ] -->
  <h2 x-text="name"></h2>
  <button @click="likes++">♥ <span x-text="likes"></span></button>
</div></code>
{/ignore}

<p>The ^ sigil writes a field as JSON escaped for the attribute: a quote or a brace in a value
stays text. Three ways keep the braces apart:</p>

<ul>
  <li><b>State from PHP</b> - <code>x-data="{^field}"</code>, as above.</li>
  <li><b>Components in a file</b> - <code>Alpine.data('tabs', list => (...))</code> in a script of
      <code>www/</code>, called by name with PAD's data: <code>x-data="tabs({^tabs})"</code>.
      Load the page's scripts before Alpine, and Alpine with <code>defer</code>.</li>
  <li><b>A space after the brace</b> - <code>{ open: false }</code> is no PAD tag; fine for a short
      object.</li>
</ul>

<h2>Talking back</h2>

<p>A component asks the page that wrote it: <code>?page&amp;padFormat=json</code> answers what
the page's PHP names in <code>$padExpose</code> ({manual 'data_answers'}). A post carries the
session's token in an <code>X-CSRF-Token</code> header, read from
<code><meta name="csrf-token" content="{csrf token}"></code>. A form's rules can live in
PHP for both sides - <code>padValidateClient ( $rules )</code> for the browser,
<code>padValidate ( $rules )</code> for the post ({manual 'client_validation'}) - and
<code>padSse()</code> streams events an <code>EventSource</code> in <code>x-init</code> turns into
state ({manual 'server_sent_events'}).</p>

<p>The Alpine application shows each of these, with its template, PHP and script:
<a href="{$padHost}alpine/">alpine</a>.</p>

{meta title='Application tests'}

<p>An application keeps its own tests in <code>_tests/</code>. A test is a page there -
<code>cart.pad</code>, with <code>cart.php</code> when it needs data - next to its answer,
<code>cart.txt</code>. <code>pad test shop</code> renders every test page and compares:</p>

{ignore}
<code>$ pad test shop
shop
  ok    cart
  FAIL  checkout
        want: <p>Total 42</p>
        got:  HTTP 500 - assert failed: $total eq 42
              apps/shop/_tests/checkout.pad:1:1  {assert $total eq 42}
  2 tests, 1 failed</code>
{/ignore}

<h2>The answer</h2>

<ul>
  <li>the exact output of the page, trimmed;</li>
  <li><code>/a pattern/</code> matched over it - for output that changes, a date or a count;</li>
  <li><code>HTTP 500</code>, with an optional <code>/pattern/</code> on the next line, for a test that is meant to fail.</li>
</ul>

<p>A test without an answer counts against the run; <code>pad test shop --record</code> writes
the missing answers from what the pages render now, and never overwrites one.
<code>pad test --all</code> runs every application that has tests, and <code>./ci.sh</code>
does that as its <code>apptests</code> line.</p>

<h2>Asserts</h2>

<p>{tag 'assert'} holds a page to a condition during a test run: false, and the test fails
with the condition and the message as its report. Anywhere else it is silent - the
condition is not even evaluated - so it can stay in the application's own pages. The switch
is <code>$padAssert</code>, which <code>pad test</code> turns on; this example turns it on in
its PHP:</p>

{example 'fragments/app_tests_1'}

<h2>A test page</h2>

<p>It is a page like any other, rendered bare - without the application's wrappers - and no
URL reaches it. It can bring in a real page with <code>{page 'cart'}</code>, or
include the page's own PHP and check the data it sets:</p>

{ignore}
<code>_tests/cart.php    <?php include APP . 'cart.php'; ?>
_tests/cart.pad    {assert $total eq 42, 'the cart total'}
                   <p>Total {$total}</p>
_tests/cart.txt    <p>Total 42</p></code>
{/ignore}

{meta title='Options of your own'}

<p>A file in the application's <code>_options/</code> directory makes its name an option
of every tag - written bare, <code>{staff words}</code>, or with a value,
<code>{staff wrap='em'}</code>. Where the file stands decides when it runs:</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>file</th><th>runs</th><th><code>$padContent</code> is</th></tr>
  <tr><td><code>_options/name.php</code></td><td>before the tag renders</td><td>the template between the tags</td></tr>
  <tr><td><code>_options/end/name.php</code></td><td>after the tag rendered</td><td>the result - every occurrence, joined</td></tr>
</table>

<p>&nbsp;</p>

<p>The handler changes <code>$padContent</code>, and the option's value is in
<code>$padGetName</code> - TRUE when the option is written bare. An end option sees the
fields filled in, so it can count, mark or tidy what the tag produced. Here
<code>fragments/options/_options/end/words.php</code> appends a word count:</p>

{ignore}
<code><?php                                   // _options/end/words.php

  $padContent .= '(' . str_word_count ( strip_tags ( $padContent ) ) . ' words)';

?></code>
{/ignore}

{example 'fragments/options/options_1'}

<p>With a value - <code>_options/end/wrap.php</code> puts the result in the element it is
given:</p>

{ignore}
<code><?php                                   // _options/end/wrap.php

  $padContent = "<$padGetName>" . trim ( $padContent ) . "</$padGetName>";

?></code>
{/ignore}

{example 'fragments/options/options_2'}

<p>An option may have both files: the first works on the template, the second on what it
became. The end options run before the built-in <code>toContent</code>, <code>toData</code>
and <code>tidy</code> - those store or tidy what the end option made - and before the closing
tag's pipe. Like tags and callbacks they are looked up from the page's directory up to the
application root.</p>

{meta title='Application Structure'}

<p>An application is a directory under <code>apps/</code>, and a page is a pair of files in
it: <code>name.php</code> gathers the data, <code>name.pad</code> renders it - the
<a href="?pages/php_and_html">php and html</a> page is about that pairing. No routing and no
controllers: creating the files creates the page, and subdirectories become url paths -
<code>?admin/users</code> is <code>admin/users.pad</code>.</p>

<h2>The wrappers</h2>

<p>A file <code>_inits.pad</code> wraps every page of its directory: the page's own output
lands where the wrapper writes <code>@page@</code>, and an <code>_exits.pad</code> closes
below it. This very page is inside one - the menu at the side and the bar with the title
above what you are reading come from the wrapper of the manual, which opens the frame every
PAD application shares and closes it again below the page:</p>

{source '_inits.pad'}

<p>Wrappers nest: the application's own <code>_inits.pad</code> wraps the subdirectory's,
which wraps the page. The page never mentions any of them.</p>

<h2>The PHP runs first, in order</h2>

<p>All PHP has run before any template renders. Down the directory chain and back up:</p>

{ignore}
<code>/_inits.php
    /admin/_inits.php
        /admin/users.php
    /admin/_exits.php
/_exits.php</code>
{/ignore}

<h2>Subdirectories inherit, and may override</h2>

<p>The <a href="?pages/extending">extension directories</a> work at every level.
<code>_lib/</code> files accumulate down the chain, so a deeper page has every level's
functions; the lookup for a tag, function or snippet starts in the page's own directory and
walks up, so a subdirectory may bring its own words - or redefine an inherited name, and its
version wins for its pages.</p>

<p><b><a href="{$padHost}structure/">The structure application</a></b> is this page live: a
tree three levels deep: the root carries the full set of special directories, every level
its own wrappers, and each level below overrides one or two names and inherits the rest, with
pages that show which level answered.</p>

pages/client_validation.pad 		Result 
{meta title='Validation in the browser'}

<p>The rules a form's fields carry are checked on the server, after the post. With
<code>client</code> on the {tag 'form'} the browser checks them too, as the visitor types and
before the form leaves - with the same rules and the same messages, so the two never
disagree. The server still checks every post: the browser's check only saves a round trip.</p>

{example 'fragments/client_validation_1', skipResult}

<ul>
  <li>The form gets its rules in a <code>data-pad-rules</code> attribute, and the first such form
      of the page brings a small script along. A field is checked when it is left, again
      while it is typed in once it showed a message, and every field when the form is sent - a
      form that fails is not sent, and the first field with a message gets the focus.</li>
  <li>The messages stand where {tag 'input'} puts the server's - a
      <code><span class="error"></code> after the field, tied to it with
      <code>aria-invalid</code> and <code>aria-describedby</code> - in the words of the field's
      label; the form's <code>error=</code> shows above the fields.</li>
  <li>A form with <code>client</code> needs a name and fields with <code>rules=</code>. A
      <code>regex:</code> rule JavaScript cannot read as PCRE does is left to the server.</li>
</ul>

<h2>Forms a component draws</h2>

<p>A React, Vue or Alpine form is no {tag 'form'} of the template. Keep the rules in the page's
PHP instead - one list for both sides: <code>padValidate ( $rules )</code> checks the post, and
<code>padValidateClient ( $rules )</code> exports the same list for the browser, every rule
with the message padValidate would give:</p>

{example 'fragments/client_validation_2'}

<p>{tag 'validator'} in the template brings the checker without a form, and the component asks
it:</p>

{ignore}
<code><div x-data="{ rules: {^rules}, form: {}, errors: {} }">
  <input x-model="form.email" @blur="errors = padValidate.check(rules, form)">
  <span class="error" x-text="errors.email"></span>
</div>
{validator}</code>
{/ignore}

<p><code>padValidate.check ( rules, values )</code> answers the message of every field that broke
a rule; <code>padValidate.field ( rules.email, value, values )</code> one field's, empty when it
holds. A field named <code>tags[]</code> takes a list.</p>
