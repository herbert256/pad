Independent framework code audit

The PAD engine, read line by line

A deep audit of the PHP that is PAD — the template engine, expression evaluator, tag library, data and database layers, request lifecycle and the sequence subsystem. Every file was read; every finding is traced to source, and the ones that matter most were reproduced on a running server. Fifteen years of careful, honest, well-commented code, carrying a security model that one design decision quietly turns inside out.

Audited 1 October 2026 · commit f641bde20 · PHP 8.5.10 (Apache) / 8.5.11 (CLI) · Apache 2.4.68 · pad/ only — 1,014 files, 26,752 lines

Verdict
Needs work

The craftsmanship is real: zero syntax errors across the tree, a fail-safe error ladder, contained file I/O, correct maths in nearly every sequence generator, and a header comment on nearly every file that tells the truth about what it does. But PAD promotes request parameters into the template namespace and then re-parses rendered values as template code, and a bare word resolves to a PHP function call with no allow-list. Those facts combine into remote code execution — demonstrated live on this machine. The default configuration also writes database passwords and raw request bodies into a web-reachable directory, request values silently override and persist session state, and the declarative select builder uses the wrong escaper on its way into SQL. Not safe to expose to untrusted input or untrusted networks until the template/data trust boundary, the session and SQL ownership rules, and the error-dump defaults are fixed.

What the audit found

The audit converges on five structural problems: field values re-parsed into template code, request parameters taking precedence over session state, PAD's own delimiter escaping used in place of SQL escaping, a page cache that is blind to identity and answers before the application initialises, and a "local" classifier that trusts the Host header. The code-execution path was demonstrated on a live server.

Around those sit a long tail of ordinary defects — the expression evaluator's wrong arithmetic and boolean logic, the sequence runner's filtering and position bugs, comment and comparison parsing, name validation that never rejects, HTTP caching and negotiation errors, data conversion that corrupts text — and a set of maintainability hazards that follow from the include-driven, globally-stateful architecture.

Scope & method

How the engine was read

Scope was the framework itself: everything under pad/, plus the two entry points www/pad.php and home/home.php. Applications under apps/ and the regression runner were read only where they show how the engine behaves. The tree was split into six subsystem reviews — request lifecycle; template engine core; expression evaluator; data & I/O; tags, info & events; sequences — each reading every file in its slice and following calls into the shared library as needed.

Behaviour was confirmed four ways: reading the code; running isolated copies of pure functions under PHP 8.5; building temporary applications with a separate DATA directory for HTTP fixtures (identity variants, failed transport, protocol headers, conditional requests) and fetching crafted pages from the live server; and replaying the framework's own test corpus — 987 enumerated cases over HTTP, of which 986 pass — plus 1,395 independent sequence reference checks. Temporary files were removed afterward; the working tree is clean at f641bde20.

Checked and found sound

Things that were tested on suspicion and held up — stated so the findings below are read at their true size.

  • Page selection: the page allow-list rejects traversal syntax and underscore-prefixed segments; no page-name bypass was established. (The tag/type-name validator is a different function and is broken — H6.)
  • Fast-link unserialize: sits behind an unconditional return in inits/fast.php; dormant, not a live deserialization path.
  • x-prefixed raw SQL substitution in db(): a deliberate, trust-sensitive escape hatch; its existence alone is not evidence that request input reaches it.
  • Script arguments go through escapeshellarg; only the executable path is unquoted (a hardening gap, not a demonstrated request-to-shell path).
  • Default field sanitization does escape HTML markup — <b>x</b> comes out encoded. It simply does not escape PAD's own delimiters.
  • Sequence generators: 76 of 77 spot-checked produce correct terms, and 1,395 term and predicate checks pass. The sequence findings are about the runner, not the maths.
  • Nested-pass state: sandbox, reporting level, engine level and a temporary data store all restore correctly on normal return.

The central issue: a trust boundary that isn't there

PAD's documentation states the rule plainly: a form field arrives in a template as {$fieldname} "with no plumbing in between" (inits/parms.php). POST, GET and cookie values are copied into PHP globals for any name that isn't pad-prefixed. That is the framework working as designed.

The engine renders a value by splicing it back into the buffer it is still scanning (lib/level.php:129-137, padLevel()), and the scanner then re-reads from the start of that buffer. So a { that arrived inside a field's value is parsed as the opening of a tag. And the type resolver, at the end of its lookup chain, treats a bare word as a PHP function if one exists:

// pad/lib/type.php:39-42  (and the prefixed form at :89-95)
elseif ( defined         ( $item ) ) return 'constant';
elseif ( padDataFileName ( $item ) ) return 'local';
elseif ( padScriptCheck  ( $item ) ) return 'script';
elseif ( function_exists ( $item ) ) return 'php';   // ← any PHP function

// pad/types/php.php:16 · pad/eval/parms/php.php:12
return call_user_func_array ( $padTag [$pad], $padUserFunc );   // no allow-list

Chaining those facts gives remote code execution. Reproduced on the running server through a field value supplied in the query string, against a page whose PHP does nothing but $value = $_GET['input'] ?? '' and whose template is {$value}:

?index&input={echo 7 * 7}            → 49
?index&input={echo php:chr(65)}      → A
?index&input={php:getcwd}            → /Users/herbert/pad/apps/test
?index&input={php:strrev $r}&r=…      → runs strrev on another field's value
?index&input={object:padSqlPassword} → reads the engine's own DB password global

The default sanitize step does not stop this: it encodes <, >, & and quotes — <b>x</b> comes out escaped — but not braces. The strict syntax check does not stop it either: the value is valid PAD. The raw {!x} form instead fails the request with a 500 ("No close } found") because it escapes } but not {. And even if the padLevel re-scan were fixed tomorrow, three other paths splice untrusted text into template source and run it: {page app=x ajax=false} returns a fetched body unescaped (start/pad/pageApp.php:22), padTagAsFunction compiles a piped value as source (lib/execute.php:74-84), and curl data sniffed as a list is run through the evaluator (data/list.php). The fix is architectural — see Remediation.

What is genuinely strong

It holds together

All 1,014 files are syntactically clean on PHP 8.5. The error handling is a layered, fail-safe ladder: the boot net is armed before config and lib load, every reporting step is wrapped and guarded against re-entry, and every path ends at padExit(500) — a failure while reporting a failure doesn't loop or half-print. Remote visitors see only Error: <request id>, with display_errors forced off at boot.

Page routing and file I/O are contained

The page allow-list is restrictive: it rejects traversal syntax and underscore-prefixed segments, and no bypass was established. Engine and app disk access funnels through padFileGet/padFilePut with a single shared guard that rejects .., // and control characters, and writes are confined to DATA. padDeleteDataDir resolves with realpath, checks the DATA prefix and refuses to follow symlinks. (The gap is the tag-name lookups that bypass this — H6 — not the file layer itself.)

The data parsers are safe

XML is parsed without LIBXML_NOENT/DTDLOAD, so external entities don't expand (no XXE); YAML won't decode PHP objects; curl never disables TLS verification and bounds its timeouts; script arguments go through escapeshellarg. db() uses the connection-aware mysqli_real_escape_string, sets TRADITIONAL sql_mode and logs every statement centrally. Default field sanitization does escape HTML markup — the control probe confirms it.

The strict check earns its keep

With $padCheckSyntax on, long-silent failures — unclosed pairs, empty conditions, duplicate {when}, unread options, missing store names, undefined fields — become precise, located messages in the template's own terms, with a deliberate lenient fallback. Runaway loops are bounded (while-round limit, nesting depth limit, always-advancing pair search), and shadowed globals are saved and restored by the scope model: a nested-state probe confirms sandbox, reporting level, engine level and a temporary store all restore correctly on normal return.

The maths is right

76 of 77 sequence generators spot-checked are correct against independent references (Catalan through C(35), the lucky sieve, Golomb and Newman-Conway recurrences), and 1,395 term and predicate checks all pass. All 51 lookup tables match their generators; integer overflow is handled in one place so sequences stop cleanly rather than printing imprecise floats; and the 375,354-row OEIS store is opened read-only with prepared statements and a per-sequence cache.

It documents itself honestly

Nearly every file opens with a precise header explaining its contract — and, remarkably, many record the bugs they once had and the reasoning behind the fix, and flag their own dormant code. That candour is what made a review of an include-driven, globally-stateful engine of this size tractable at all.

Remediation, in order

In priority order:

  1. Separate literal data from executable template input (C1). Establish a literal insertion path first: escape braces on every value spliced back into the scan buffer (the padEscape helper already exists) and apply it to the other source-splicing sinks — pageApp, padTagAsFunction, sniffed curl data. Review every user-data output form together so a fix in one form does not simply move the vulnerability to another. In the type resolver, drop the function_exists/defined/script fallbacks so those prefixes must be written explicitly, and gate php: behind a configurable allow-list. Preserve deliberate trusted-code features such as padCode().
  2. Define ownership of request, session and database values (C2, H1, H2, H5, H7). Remove implicit writes into trusted session state; promote only declared request names. Move the select subsystem and db() to prepared statements, or quote and connection-escape every interpolated value including numerics and the track session queries; cast pagination to int.
  3. Make cache eligibility and diagnostic exposure explicit (H3, H4, H10). Public-only cache policy with access checks before delivery and keys partitioned by app/host; base "local" on REMOTE_ADDR behind an off-by-default switch; default the disk dumps off; keep DATA out of the docroot; redact credentials, session values and request bodies from any dump; define retention.
  4. Validate names and hosts (H6, M1, M2, M3, M19). Repair padValid, reject / and . wherever a name becomes a path, escapeshellarg the script exec, allow-list {output} and sequence build=/action=, contain {files}/{dir}, and build cross-app URLs from a configured base rather than the Host header.
  5. Repair the evaluator and sequence runner (H8, H9, M13, M14, M20, M28). Rebuild expression evaluation around precedence groups with a prefix-unary pass and real comparison tokens; in sequences, record history before filtering, keep a hard candidate ceiling, isolate the expression entry, fix pqArray's cardinality and the zero-ending range. Add tests that compare against independent reference values, and regenerate the baselines that currently encode wrong output.
  6. Repair representation and error lifecycle handling (M7, M9, M22, M23, M26, M27). URL-specific validators, cached response metadata, finally-based cleanup, honoured q=0, correct Vary, case-insensitive header parsing, a validated curl-multi window, and a restart guard that actually stops.
  7. Then the remaining Medium set — comment parsing, == as assignment, Tidy defaults, multibyte strings, CSV, the XML report leak, empty-file writes, the select row/htmlAttrJson mix-up, handler crashes, state clobbering — most of which are small, local, independently verifiable patches.

The Critical and High items are what make PAD unsafe to expose to untrusted input or an untrusted network today. Everything below them is quality and correctness work that a codebase this carefully commented is well positioned to absorb. Keep changes small; add negative and boundary tests with an independent expected result; document any compatibility change to recursive output or session promotion.
