PAD has a substantial working core and a broad regression corpus, but several important contracts fail where modules meet: authenticated account changes, signed imports, nested render cleanup, HTTP redirects, replay paths and browser persistence. This audit identifies 23 reproduced executable defect groups, one confirmed backup-contract gap and one source-supported release-identity risk. Five findings deserve P1 attention under their stated conditions; the other twenty are P2, including conditional and narrow numerical cases. These are engineering priorities, not CVSS scores or claims of anonymous remote compromise. The current AST evaluator, escaping defaults, session ownership, guarded developer tools and several transaction-aware example applications provide useful foundations. The full isolated gate nevertheless ended exit 1: 8,046 of 8,076 HTTP cases passed and 30 failed. Repairs should preserve the public template language and proceed through small contract-focused changes, backed by independent oracles and stateful failure tests.

Assessment: fix state ownership before broad rewrites

The most consequential defects share a cause: a component assumes that another component has preserved an invariant. Atomic file replacement is mistaken for an atomic user-store mutation; a cached request is identified before its source is resolved; a SQLite bookkeeping insert changes connection state before the real SQL; a completed browser write can be replaced by another tab's stale filesystem. These are concrete ownership failures. More abstraction alone will not correct them: each boundary needs an explicit owner, input/output contract and failure behavior.

First priority: lock and revalidate Editor user mutations APP-01, preserve signed Ledger imports APP-02, strip cross-origin credentials in the HTTP fallback CORE-01, make replay path classification canonical ST-01, and serialize independent disk-mode writers ST-02. Exposure is conditional: the HTTP issue requires credential-bearing fallback requests and a cross-origin redirect; the Editor race requires concurrent authenticated management actions; packaging exposure requires an out-of-root symlink and subsequent distribution. No current default remote-code-execution exploit or production compromise was demonstrated.

Next priority: restore nested state on exceptions, preserve native SQLite semantics, make imports atomic, reject malformed money/dates, detect stale forms, provide complete consistent backups, and retain the last successful browser view on network failures. These changes are small enough to review separately. Add each focused reproducer as a regression before changing shared internals; run existing compatibility fixtures after every migration step.

Do not replace the evaluator to solve historical defects already removed. It already has a parser/AST/runtime separation, lazy branches and bounded parse caches. The new arithmetic oracle passed 1,200 expressions, and 16,000 addition operands completed within 128 MiB in the measured environment. The current evidence supports investing in lifecycle, transport, persistence and release contracts before a framework rewrite. See current positive controls and measured validation.

Architecture: separate trusted programs from request data

PAD initializes path constants and handlers, loads route/config/host/client/cache/session/application state, builds the selected page, evaluates nested template levels and writes the response. Templates and PHP-call expressions are trusted program input. Ordinary interpolated values are escaped and protected from template reparse by default. A PAD “sandbox” isolates variable/store scope; it is not an untrusted-PHP capability sandbox. The lifecycle and its early cache lookup are visible in bootstrap and initialization order.

P1CORE-01Reproduced defectRuntime

HTTP fallback forwards credentials across origins

Trigger / scope: HTTP fallback; cross-origin redirect

Preconditions: ext-curl is unavailable, or code calls padNoCurl directly; a fetch uses Basic credentials and/or explicit cookies; redirects are enabled (the default); the origin returns a redirect to a different scheme/host/port. The origin or its redirect input must be controlled or compromised for an attack. This is not a claim that every deployment currently uses the fallback.

Source: pad/lib/curl.php:66 retains one $options array throughout the redirect loop; lines 98–104 replace the URL without stripping authentication. pad/lib/curl.php:146, especially lines 158–162, reconstruct Cookie and Basic Authorization for every hop. Explicit headers in HTTPHEADER likewise persist. The fallback is selected at pad/lib/curl.php:538.

Repro: two Python ThreadingHTTPServer instances bound to 127.0.0.1 on random ports. The first's /redirect-auth returns 302 to http://localhost:<second-port>/echo. The destination reports only the request method/path/authorization/cookie headers. Pass:

$input = ['url' => $origin . '/redirect-auth',
        'user' => 'audit-user', 'password' => 'audit-secret',
        'cookies' => ['auditcookie' => 'audit-value']];
$built = padCurlBuild($input);
$curl = padCurlWire($built);
$fallback = padNoCurl($built);

Expected / negative control: ordinary cURL destination returns authorization:null,cookie:null. Actual fallback: destination receives Authorization: Basic YXVkaXQtdXNlcjphdWRpdC1zZWNyZXQ= and Cookie: auditcookie=audit-value; padSesID=audit-session; padReqID=audit-request. The destination never requested these credentials.

External basis: libcurl's default protects generated and explicit Authorization/Cookie headers when any of scheme, hostname or port changes. Official CURLOPT_UNRESTRICTED_AUTH documentation. No unrestricted-auth option was enabled in the probe.

Recommendation: compare normalized origin tuples before every redirect and strip user/password, Cookie and explicit Authorization/Cookie on a change. Decide separately whether an explicit trusted-redirect setting should restore them. Include HTTPS→HTTP, same hostname/different port, explicit header and scheme-relative redirect cases. Security policy should be shared by both transport adapters.

Evidence: /tmp/pad-codex-20261102/framework/http-server.py, http-probe.php, http-probe.log, mode redirect-auth.

P2CORE-02Reproduced defectRuntime

A caught nested-render exception leaves the caller's state cleared

Trigger / scope: Nested exception recovery

Preconditions: an application uses padSandbox/nested padCode, a callback throws, the application catches it and continues. The reproduced route uses the documented $padErrorTry=FALSE setting so the exception reaches the caller. This is a failure-recovery defect, not evidence that arbitrary remote users can execute templates. The default fatal error path need not continue to exhibit it.

Source: pad/start/function.php:13 restores $pad and output only after its include returns. pad/start/pad/function.php:19 increments function depth, imports globals and decrements only on normal return (line 46). pad/start/pad/pad.php:25 starts/saves/clears a nested pass, but its matching start/pad/end.php is a later straight-line include (line 43). pad/start/pad/start.php:13 and pad/start/pad/end.php:11 are the ownership pair.

Repro in an isolated application's index.php:

function auditExplode() { throw new RuntimeException('audit-boom'); }
$auditsaved = 'ORIGINAL';
$padDataStore['auditsaved'] = [['name' => 'outer']];
try { padSandbox('{php:auditExplode/}'); }
catch (Throwable $e) { $message = $e->getMessage(); }
echo 'continued=[' . ($auditsaved ?? 'MISSING') . ']';

Expected: the catch sees audit-boom, caller variables/stores and all depth counters are restored, and continuing PHP prints continued=[ORIGINAL].

Observed snapshot: before {level:0,stringDepth:-1,functionDepth:0,saved:"ORIGINAL",store:[{name:"outer"}]}; after {level:2,stringDepth:0,functionDepth:1,saved:null,store:null}. Continuing PHP prints continued=[MISSING]. A subsequent padCode field lookup happened to print continued=[ORIGINAL] through remaining engine scope state. That distinction matters: do not claim every later template lookup is blank; PHP globals/store ownership and renderer counters are demonstrably inconsistent.

Recommendation: give each nested-render entry a frame object with one idempotent finally unwind, including flags, floor level, function counter, globals, stores and output buffers. Preserve the original exception if cleanup also fails. Do not simply add a finally to one include while leaving the other two ownership layers unbalanced. The public evaluator already uses try/finally for its busy counter at pad/lib/eval/eval.php:102, and its equivalent exception probe passed.

External basis: PHP unwinds through finally blocks when a Throwable propagates; finally does not rescue abrupt process termination. PHP exceptions, PHP finally.

Evidence: framework/boot.php, framework/app/index.php, mode AUDIT_CASE=nested; framework/nested.log. The fixture keeps its before snapshot on disk because sandbox clearing also removes ordinary probe globals.

P2CORE-03Reproduced defectRuntime

SQLite insert-id bookkeeping changes the application's SQL meaning

Trigger / scope: SQLite connection state

Source: pad/lib/db.php:401, especially line 416 before $connect->query($sql) and lines 432–433; pad/lib/db.php:465, padDbSqliteMark, inserts a sentinel -9223372036854775808 into temp.pad_insert_id before every INSERT.

Rationale acknowledged: the sentinel avoids incorrectly returning a previous id for ignored/no-row inserts, UPSERT updates or WITHOUT ROWID tables, including cases where two genuine inserts produce the same numeric id. The existing fix addresses real ambiguity but modifies connection state visible inside the statement it is about to run.

Standalone reproduction (no PAD bootstrap needed):

require '/Users/herbert/pad/pad/lib/db.php';
$c = new PDO('sqlite::memory:');
$c->setAttribute(PDO::ATTR_ERRMODE, PDO::ERRMODE_SILENT);
$c->exec('PRAGMA foreign_keys=ON');
$c->exec('CREATE TABLE parent(id INTEGER PRIMARY KEY,name TEXT);
        CREATE TABLE child(id INTEGER PRIMARY KEY,parent_id INTEGER REFERENCES parent(id));');
padDbRun($c, "INSERT INTO parent(name) VALUES ('p')", 'insert');
// SELECT last_insert_rowid() here is 1.
$r = padDbRun($c, 'INSERT INTO child(parent_id) VALUES(last_insert_rowid())', 'insert');
var_export([$r, $c->errorInfo(), $c->query('SELECT last_insert_rowid()')->fetchColumn()]);

Actual: false, SQLSTATE 23000, SQLite error 19, FOREIGN KEY constraint failed; last rowid is now -9223372036854775808. Expected/native PDO control: executing exactly the same parent and child SQL directly succeeds with one child row whose parent is 1. With foreign keys disabled, the corruption can be persisted as the bogus parent id instead of rejected.

Negative controls that a fix must preserve: INSERT OR IGNORE duplicate → rows 0/id 0; ON CONFLICT DO UPDATE → rows 1/id 0; insert into WITHOUT ROWID → rows 1/id 0; empty INSERT…SELECT → rows 0/id 0. All currently passed. Logs include the exact statements and outputs.

Recommendation: do not perform a bookkeeping INSERT on the application connection. Separate the statement outcome (affected rows, new id, returned rows, kind) in an explicit result type, with a compatibility adapter for db()'s existing return values. Consider opt-in explicit RETURNING queries for callers needing unambiguous ids. Do not blindly append RETURNING rowid to every query: SQLite supports it from 3.35.0, it also returns UPSERT-updated rows, has virtual-table/trigger constraints and changes the query result contract. Preserve native last_insert_rowid() semantics. SQLite last-insert-rowid contract, SQLite RETURNING.

Evidence: framework/db-probe.php, framework/db-probe.log.

P2CORE-05Reproduced defectRuntime

Curl-cache keys collide for relative inputs in different page directories

Trigger / scope: Resolved-source cache identity

Source: pad/lib/curlCache.php:31 looks up cache before input resolution. pad/lib/curlCache.php:125 hashes only $padApp plus serialized input. pad/lib/curl.php:261 resolves an unqualified data name later; pad/lib/paths.php:136 searches _data/ according to padDirs()/$padDir. The same raw input can therefore resolve to different sources while having the same cache key.

Fixture files: app/a/_data/audit-rates.json contains [{"value":"a"}]; app/b/_data/audit-rates.json contains [{"value":"b"}]. Set a disposable DATA directory and $padCurlCache='file'.

$padDir='a'; $one=padCurlCached('audit-rates',600);
$padDir='b'; $direct=padCurl('audit-rates');
$two=padCurlCached('audit-rates',600);

Expected: a→a, b direct→b, b cached→b. Actual: a→a, b direct→b, b cached→a, cache=hit. This was reproduced using the real local-file resolver and real file cache, not a fake HTTP provider.

Impact/preconditions: two page directories in one application use the same relative/local source input with ttl caching. The second receives wrong data; whether that becomes a data-separation issue depends on the application's data/authorization model. Do not label it a demonstrated cross-user secret leak.

Recommendation: build/canonicalize the request before computing its cache identity, including resolved source URL/path and relevant request representation options. Keep credentials out of readable cache-key material; a keyed/hash identity can vary on them without logging them. Add scalar URL vs ['url'=>...] equivalence, relative-local directory separation and mount/base variation tests. Invalidate the old cache-key version during migration.

Evidence: framework/app/index.php, mode AUDIT_CASE=curlcache, framework/curlcache.log; both local fixture JSON files.

Framework Vary generation overwrites the application's selector

Trigger / scope: Cacheable custom-header response

Source: pad/lib/output.php:168 constructs a new list from built-in dimensions and line 189 writes it. pad/lib/tidy.php:235 calls PHP header($header) with replacement enabled, discarding an existing Vary. The framework preserves its own known CORS/locale/expose dimensions, but not arbitrary application dimensions or Vary:*.

Fixture: _config/config.php sets $padCookies=FALSE so anonymous responses do not set cookies. index.php:

header('Vary: X-Audit');
$auditVariant=$_SERVER['HTTP_X_AUDIT'] ?? 'none';
$padGzip=TRUE;
$padCacheClientAge=0;
$padCacheProxyAge=600;

index.pad contains variant={$auditVariant}. Request the same URL with X-Audit:A and X-Audit:B.

Actual: bodies are respectively variant=A\n and variant=B\n; both responses say Vary: Accept-Encoding and Cache-Control: public, max-age=0, s-maxage=600, no-transform, must-revalidate, proxy-revalidate. X-Audit is missing. Expected: Vary contains both X-Audit and Accept-Encoding. A shared cache may now reuse the A representation for B without reaching the server.

Preconditions/limits: application actually varies representation by a custom header and permits caching; enabling gzip or another built-in Vary dimension triggers overwrite. This is not evidence that current default no-store pages are leaking. No CDN/proxy was deployed in the probe; the wrong public cache metadata and differing response bodies were observed directly.

Recommendation: centralize header collection, parse existing Vary field lines case-insensitively, merge/de-duplicate all selectors, and preserve *. Ensure expose/CORS/normal output/download paths share the same merger. RFC 9110 section 12.5.5 describes Vary as the request fields that influence representation selection, which caches use to decide reuse.

Evidence: framework/web-probe.py, framework/web-probe.log; isolated PHP built-in server shut down in a finally block.

P1APP-01Reproduced defectRuntime

Editor password changes can resurrect a deleted account

Trigger / scope: Concurrent authenticated operations

Class/evidence: Helper verified, high confidence; security-relevant lost update, requiring concurrent authenticated management actions in separate sessions. No anonymous exploit or role escalation is claimed. All editor users already have installation-level editing privileges; this implementation has no role/demotion abstraction. Editor users API, lines 5–39

Contract and cause: Editor explicitly promises that deletion or changed password invalidates sessions. editUserPasswordSet() reads the entire user map at line 105, computes a real password hash at 110, and writes the old map back at 113. editUserDelete() independently reads/unsets/writes at 121–131. Neither locks the read/modify/write unit. Atomic rename prevents a torn JSON file but does not prevent stale-map replacement. Store, lines 40–43, 102–131, atomic write, lines 178–216

Minimal reproduction: Seed two synthetic users, owner and victim. Fork a process calling actual editUserPasswordSet(base,'victim',newPassword). After its start marker, wait 50 ms; parent calls actual editUserDelete(base,'victim') and confirms victim absent. Wait for password operation (~0.177 s). User is present again and padHashCheck(newPassword,storedHash) succeeds. 5/5 attempts reproduced deletion followed by resurrection. The probe includes current paths.php, files.php, store.php, and pad/lib/crypt.php; it does not stub hashing or change source. Reproducer [evidence/apps/edit-user-race.php], five results [evidence/apps/edit-user-race.jsonl]

Expected/actual/impact: Once owner deletes victim, an in-flight password operation should fail or leave the user deleted. Fix direction/regression: Reuse the admin store's locked mutation pattern: hash expensive input outside the lock, then lock, re-read authoritative users, revalidate presence/current stamp, mutate, and atomically write. P2APP-03Reproduced defectRuntime

Budget text is silently coerced into a different amount or deletion

Trigger / scope: Malformed decimal text

Class/evidence: HTTP verified, high confidence. Budgets are editable text inputs (inputmode=decimal), with no rule declaration. Budget form lines 4–11
