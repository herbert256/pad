App: manual - Page: pages/alpine

pages/alpine.pad 		Result 
{pad:meta title='Alpine'/}

<p>Alpine adds behaviour to HTML with attributes - and PAD writes that HTML. Both use braces,
and PAD reads every <code>{</code> of a template as the start of a tag, so the state of a
component comes from the page's PHP as JSON instead:</p>

{pad:ignore}
<code><div x-data="{^profile}">                <!-- $profile = [ 'name' => 'Ada', 'likes' => 12 ] -->
  <h2 x-text="name"></h2>
  <button @click="likes++">♥ <span x-text="likes"></span></button>
</div></code>
{/pad:ignore}

<p>The ^ sigil writes a field as JSON escaped for the attribute: a quote or a brace in a value
stays text. Three ways keep the braces apart:</p>

<ul>
  <li><b>State from PHP</b> - <code>x-data="{^field}"</code>, as above.</li>
  <li><b>Components in a file</b> - <code>Alpine.data('tabs', list => (...))</code> in a script of
      <code>www/</code>, called by name with PAD's data: <code>x-data="tabs({^tabs})"</code>.
      Load the page's scripts before Alpine, and Alpine with <code>defer</code>.</li>
  <li><b>A space after the brace</b> - <code>{ open: false }</code> is no PAD tag; fine for a short
      object.</li>
</ul>

<h2>Talking back</h2>

<p>A component asks the page that wrote it: <code>?page&amp;padFormat=json</code> answers what
the page's PHP names in <code>$padExpose</code> ({app:manual 'data_answers'/}). A post carries the
session's token in an <code>X-CSRF-Token</code> header, read from
<code><meta name="csrf-token" content="{pad:csrf token/}"></code>. A form's rules can live in
PHP for both sides - <code>padValidateClient ( $rules )</code> for the browser,
<code>padValidate ( $rules )</code> for the post ({app:manual 'client_validation'/}) - and
<code>padSse()</code> streams events an <code>EventSource</code> in <code>x-init</code> turns into
state ({app:manual 'server_sent_events'/}).</p>

<p>The Alpine application shows each of these, with its template, PHP and script:
<a href="{$padHost}alpine/">alpine</a>.</p>

pages/comments.pad 		Result 
{pad:meta title='Comments'/}

<p>PAD has two comment forms. Both are taken out of the template before it is scanned, so a tag written inside one never runs and nothing of it reaches the output.</p>

<ul>
  <li><code>{# ... #}</code> - the original form</li>
  <li><code>{-- ... --}</code> - the form the editor kits highlight and toggle</li>
</ul>

{common:example 'fragments/comments_1'/}

<h2>Rules</h2>

<ul>
  <li>A comment closes at the first <code>#}</code> or <code>--}</code> after it, and may span lines.</li>
  <li><code>{--</code> must be followed by whitespace: a CSS custom property inside an {app:tag 'ignore'/} block, <code>:root{--gap:4px}</code>, is CSS and stays as it is.</li>
  <li><code>{#name}</code> is not a comment but the option sigil - the value of the tag option <code>name</code>.</li>
</ul>

<h2>See Also</h2>

<ul>
  <li>{app:manual 'ignore'/} - keep PAD from parsing braces</li>

{pad:meta title='Data formats'/}

<p>Besides JSON, XML, YAML and CSV, {app:tag 'format:auto'/} reads the formats of
<code>pad/subs/formats/</code>: TOML, INI, TSV, NDJSON, Markdown pipe tables, iCalendar,
vCard, GeoJSON, GPX, KML, WebVTT and SRT subtitles and Excel spreadsheets. Name the format with <code>format=</code> - or
<code>type=</code>, the same option:</p>

{common:example 'fragments/data_formats_1'/}

<p>An array of tables is a list of rows inside the row, so <code>{array:stops}</code>
iterates it; a date is the text it is, <code>2026-11-06</code>.</p>

<h2>Known on sight</h2>

<p>Some formats need no name: a text that opens with <code>BEGIN:VCALENDAR</code> is a
calendar, <code>BEGIN:VCARD</code> a vCard, lines of JSON objects NDJSON, a Markdown pipe
table a table and a header of tabs TSV. Each event is a row - <code>summary</code>,
<code>start</code>, <code>end</code>, <code>allday</code>, <code>location</code> and the rest:</p>

{common:example 'fragments/data_formats_2'/}

<h2>Captions and subtitles</h2>

<p>A text that opens with <code>WEBVTT</code> is the captions of a video, an SRT file its
subtitles: a cue is a row - <code>start</code> and <code>end</code> as
<code>00:01:02.500</code> (<code>startms</code> and <code>endms</code> in milliseconds),
<code>text</code> with its markup, <code>plain</code> without it and <code>voice</code>, who
speaks:</p>

{common:example 'fragments/data_formats_4'/}

<h2>Places</h2>

<p>A KML file of Google Earth is a placemark a row, with the folder it stands in, the fields of
its <code>ExtendedData</code> and its geometry as GeoJSON has it - <code>lat</code> and
<code>lon</code> of a point, <code>coordinates</code> of a line or a polygon - so the rows of
one are written as the other:</p>

{common:example 'fragments/data_formats_5'/}

<h2>Files and PHP</h2>

<p>A file in <code>_data/</code> is read by its extension - <code>_data/trip.toml</code> is
<code>{data:trip}</code> and <code>{local:trip.toml}</code>,
<code>_data/sales.xlsx</code> the first sheet of the workbook
(<code>{local:sales.xlsx sheet='Notes'}</code> another). In a page's PHP,
<code>padFormatRead</code> reads a text and <code>padFormatWrite</code> writes rows:</p>

{common:example 'fragments/data_formats_3'/}

<ul>
  <li>The formats are the files of <code>pad/subs/formats/types/</code> - toml, ini, tsv,
      ndjson, jsonseq (JSON text sequences), markdown, ics, vcf, geojson, gpx, kml, vtt, srt,
      xlsx and json, csv, yaml, xml; rss, atom and jsonfeed write only. An extension names its
      format too: md, jsonl, yml.</li>
  <li>A text a format cannot read is an error naming the format and the line -
      <code>TOML error on line 3: the key 'name' is defined twice</code>; with the strict check
      off it gives no rows.</li>
  <li>TOML, INI, GeoJSON, GPX and KML are never guessed - they read as CSV, JSON or XML before -
      so name them, or keep them in a file with their extension.</li>
  <li>Writing data out - a calendar, a feed, a spreadsheet - is {app:manual 'feeds_and_exports'/}.</li>
</ul>

{pad:meta title='Feeds and exports'/}

<p>A page that exposes its data with <code>$padExpose</code> answers it as JSON and CSV
({app:manual 'data_answers'/}) - and in every other format of <code>pad/subs/formats/</code> that
writes: a calendar, a feed, a spreadsheet, a map. <code>$padFormatOptions</code> gives the
writer what the rows do not say, here the name of the calendar:</p>

{common:example 'fragments/feeds_and_exports_1'/}

<p>Asked with <code>&amp;padFormat=ics</code> - or by a calendar application sending
<code>Accept: text/calendar</code> - the page answers an iCalendar file, with
<code>&amp;padFormat=md</code> a Markdown table. The template does not run for either:</p>

{common:example 'fragments/feeds_and_exports_2'/}

<ul>
  <li>The formats that write: ics, vcf, xlsx, rss, atom, jsonfeed, geojson, gpx, kml, vtt, srt,
      markdown, tsv, ndjson, jsonseq, toml, yaml, ini, besides json and csv. A table format
      answers the first list the page exposes, toml, yaml and ini every exposed variable by name.</li>
  <li>A page of chapters - a <code>start</code> and a <code>title</code> each, the end the next
      one's start - asked with <code>&amp;padFormat=vtt</code> is the <code>src</code> of a
      video's <code><track kind="chapters"></code>.</li>
  <li>Each answers with its own content type, and a file with the page's name and the format's
      extension - <code>talks.ics</code> inline, <code>talks.xlsx</code> as an attachment.</li>
  <li>The answer is the same bytes for the same rows: an event's UID is made of the row, its
      DTSTAMP is its start, a spreadsheet's parts carry a fixed date - never the clock.</li>
  <li>A row a format has no place for - an order without a date in a calendar - is left out
      of the answer.</li>
</ul>

<p><code>padFormatWrite</code> writes rows in a format in a page's PHP. The rows of a

slug behind the feed's link is an entry's address:</p>

{common:example 'fragments/feeds_and_exports_3'/}

<ul>
  <li>rss, atom and jsonfeed take <code>title</code>, <code>link</code>, <code>self</code>,
      <code>description</code> and <code>author</code>; the feed's updated is its newest
      entry's date.</li>
  <li>ics takes <code>name</code> and <code>stamp</code>, xlsx <code>sheet</code>, gpx
      <code>name</code> and <code>as='track'</code>, kml <code>name</code>.</li>
</ul>

{pad:meta title='Field sigils'/}

<p>The character in front of a name says which value is meant and how it is written into the page. None of these opens a level - the value is spliced in where the tag stood.</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr style="background: #f0f0f0;"><th>Form</th><th>Writes</th></tr>
  <tr><td><code>{$name}</code></td><td>The field, through the sanitize chain</td></tr>
  <tr><td><code>{!name}</code></td><td>The same field raw - the sanitize chain is skipped</td></tr>
  <tr><td><code>{?name}</code></td><td>The field as a query fragment: <code>&amp;name=url+encoded</code></td></tr>
  <tr><td><code>{^name}</code></td><td>The field as JSON, escaped for a double-quoted HTML attribute; an array is encoded whole</td></tr>
  <tr><td><code>{&#35;name}</code></td><td>An option or parameter of the tag</td></tr>
  <tr><td><code>{&amp;name}</code></td><td>A property of the tag</td></tr>
</table>

{common:example 'fragments/sigils_1'/}

<p>The JSON form is made for mount points of client-side components: <code>JSON.parse(elem.getAttribute('data-props'))</code> reads it back, with no custom tag and no {app:tag 'ignore'/} pipe.</p>

pages/forms.pad 		Result 
{pad:meta title='Forms'/}

<p>{app:tag 'input:form'/}, {app:tag 'input:field'/} and {app:tag 'input:textarea'/} write the fields of a form. When the
form comes back with mistakes in it, each field shows again what was typed - escaped - and
the message for its mistake beside it. <code>padValidate</code> in the page's PHP finds the
mistakes.</p>

{common:example 'fragments/forms_1'/}

<ul>
  <li>{app:tag 'input:form'/} posts back to the page and carries the session's CSRF token (see
  {app:manual 'csrf_protection'/}) and its name: <code>padPosted ( 'contact' )</code> is true when
  this form came back, so a page with two forms knows which one did.</li>
  <li>{app:tag 'input:field'/} and {app:tag 'input:textarea'/} take the field name first; <code>label=</code> writes a
  label tied to the field, <code>value=</code> the value before anything was posted, and every
  other item is an attribute of the field, as {app:tag 'attrs'/} writes it - <code>required</code>,
  <code>rows=6</code>, <code>placeholder='...'</code>.</li>
  <li>A checkbox or radio is checked when the posted value is its own value; a password or
  file field is never refilled.</li>
</ul>

<h2>Validation</h2>

<p><code>padValidate ( $rules )</code> checks the posted values and answers one message per
field that breaks a rule, keyed by the field - empty when all is well. A second argument
checks other data; a third replaces messages, per field (<code>'email'</code>) or per field
and rule (<code>'email.required'</code>):</p>

{common:example 'fragments/forms_2'/}

<p>A rule takes its argument after a colon: <code>min:n</code>, <code>max:n</code> and
<code>between:a,b</code> are a length, or a value with <code>numeric</code> or
<code>integer</code>; <code>in:a,b,c</code> a list, <code>regex:/.../</code> a pattern,
<code>same:other_field</code> another field, <code>digits:4</code> a number of digits. An empty
field is checked for <code>required</code> and <code>accepted</code> only. Every rule is a file of
<code>pad/subs/rules/types/</code> - its check in the browser beside it in <code>www/assets/rules/</code> -
and these are the {pad:echo php:count(padRuleTypes())/} there are:
{pad:echo php:implode(', ', padRuleTypes())/}. A rule name nothing knows is an error.</p>

<h2>After a failed post</h2>

<p>The fields of the form that came back show the message beside them, in the words of their
own label, tied to the field with <code>aria-invalid</code> and
<code>aria-describedby</code> so a screen reader reads them together. Here the post is
pretended in the PHP, the way a visitor's would arrive:</p>

{common:example 'fragments/forms_3'/}

<p>After a post that passes, store it and send the visitor on with <code>padRedirect ()</code>:
a refresh of the page they land on does not post a second time.</p>

<h2>Rules in the template</h2>

<p>The rules can stand on the fields themselves: <code>rules='required|email'</code> on an
{app:tag 'input:field'/} or a {app:tag 'input:textarea'/}. They are read from the page's template before its PHP
runs, and a post of the form is checked against them there - <code>padPosted ( 'contact' )</code>
is true only for a post that kept them, so the PHP acts on a good post alone. A post that broke
one renders the form again, refilled, with the messages beside the fields and the form's
<code>error=</code> above them (<code>error</code> alone says "Please correct the errors
below."):</p>

{common:example 'fragments/forms_4', skipResult/}

<ul>
  <li>Only what is written out counts: quoted rules, on a field with a quoted name, in a
  {app:tag 'input:form'/} with a name that posts back to its own page. Rules on a field in a snippet, a
  custom tag, a {app:tag 'page'/} or a layout, rules made from a variable, rules in a form with
  <code>action=</code> or <code>method='get'</code> and rules on a file field are errors -
  nothing would check them.</li>
  <li>Every field of the posted form that has rules is checked, also one in an {app:tag 'if'/}
  branch that did not render. A field that is there only sometimes keeps its check in the
  PHP: <code>padValidate</code> adds its messages to those of the template.</li>
  <li><code>padFormFailed ( 'contact' )</code> is true when the form came back and broke its
  rules.</li>
</ul>

App: manual - Page: pages/htmx
PHP
 HTML
pages/htmx.pad 		Result 
{pad:meta title='htmx'/}

<p>htmx asks the server for a part of the page and swaps the answer in - HTML over the wire,
no JavaScript of your own. A PAD template already has names on its parts: every
{app:tag 'fragment'/} can be asked for alone, so the template that renders the first visit also
answers every question htmx asks after it.</p>

{pad:ignore}
<code><input name="q" hx-get="?products" hx-trigger="input changed delay:300ms" hx-target="#results">

<ul id="results">
  {pad:fragment 'results'}
    {array:products}<li>{$name}</li>{/array:products}
  {/pad:fragment}
</ul></code>
{/pad:ignore}

<h2>Which part answers</h2>

<ul>
  <li><b>By the target.</b> htmx sends the id of the element it swaps in <code>HX-Target</code>; a
      request of htmx that names no fragment itself gets the fragment called like that element,
      when the page has one - and the whole page when it has none.</li>
  <li><b>By the address.</b> <code>&amp;padFragment=rows</code> names the fragment outright - for a
      target without an id (<code>hx-target="closest tr"</code>, <code>this</code>) or a part other
      than the target.</li>
  <li><b>By the PHP.</b> <code>$padFragmentOnly = 'row'</code> decides in the page's PHP. A fragment
      inside a loop answers with the first row it renders: narrow the rows to the one asked
      for.</li>
</ul>

<h2>Posts and forms</h2>

<ul>
  <li>With <code>$padCsrf</code> on, a post needs the session's token. A {app:tag 'input:form'/} carries it;
      for an <code>hx-post</code> on anything else put it on the body once:
      <code><body hx-headers="{^headers}"></code> with
      <code>$headers = [ 'X-CSRF-Token' => padCsrfToken () ]</code>.</li>
  <li>A {app:tag 'input:form'/} with <code>rules=</code> posted through htmx comes back as its own fragment -
      refilled, with PAD's messages - and with <code>client</code> the browser checks the same
      rules first ({app:manual 'client_validation'/}).</li>
  <li>Elements of an answer marked <code>hx-swap-oob="true"</code> go where their id is: the
      count in the header, a summary beside a list.</li>
</ul>

<h2>Pushed by the server</h2>

<p><code>padSse()</code> ({app:manual 'server_sent_events'/}) streams events; with htmx's sse
extension (<code>hx-ext="sse" sse-connect="?ticker"</code>) every event's HTML is swapped in as
it arrives.</p>

<p>The htmx application shows all of it, each example with its template and PHP:
<a href="{$padHost}htmx/">htmx</a> - active search, lazy loading, infinite scroll, inline
editing, forms, out-of-band updates and server-sent events.</p>

App: manual - Page: pages/islands
PHP
 HTML
pages/islands.pad 		Result 
{pad:meta title='Islands of any framework'/}

<p>An island is a place in a PAD page where a component takes over: an element naming the
component, its props as JSON in <code>data-props</code>, and HTML of PAD's own inside that
shows until the component runs. Which framework the component is written in does not matter to
the page:</p>

{pad:ignore}
<code><div data-island="VueCounter" data-props="{^counter}">{$counter.start}</div>
<div data-island="Shelf" data-load="visible" data-props="{^shelf}"></div>

{pad:vite 'src/main.js'/}</code>
{/pad:ignore}

<p>A small runtime in the build pairs each name with a component and its framework, and mounts
it - fetching the component, and its framework with it, only when an island of that name is on
the page and due:</p>

{pad:ignore}
<code>islands({
  VueCounter: vue(() => import('./islands/Counter.vue')),
  Shelf:      react(() => import('./islands/Shelf.react.jsx'))
});</code>
{/pad:ignore}

<ul>
  <li><code>data-load</code> says when: <code>eager</code> (at once), <code>idle</code> (when the
      browser has nothing else to do) or <code>visible</code> (when the island scrolls into
      view).</li>
  <li>An adapter per framework mounts a component with props and answers how to unmount it -
      React, Vue, Svelte, Preact and Solid each take a dozen lines.</li>
  <li>Islands of different frameworks share state through a store, and talk to PAD through the
      page's JSON (<code>$padExpose</code>) and posts with the CSRF token.</li>
  <li>{app:manual 'vite'/} builds the components; {app:tag 'vite'/} links the build, or the dev server while
      it runs.</li>
</ul>

<p>The islands application has all of it, with the runtime, the adapters and the components
beside each example: <a href="{$padHost}islands/">islands</a>. The react application does the
same without a build step, with Babel in the browser.</p>

App: manual - Page: pages/live_reload
PHP
 HTML
pages/live_reload.pad 		Result 
{pad:meta title='Live reload'/}

<p>With <code>$padReload = 'local'</code> in an application's <code>_config/config.php</code>,
every page of a local request carries a small script that asks the server once a second
whether a file behind the page has changed - and reloads the page when one has. Save a
template, a page's PHP or a stylesheet, and the browser shows it.</p>

{pad:ignore}
<code><?php

  // _config/config.php
  $padReload = 'local';

?></code>
{/pad:ignore}

<h2>What it watches</h2>

<ul>
  <li><code>'local'</code> (or <code>TRUE</code>) - the application's directory, its entry point directory in <code>www/</code> (stylesheets, scripts, images), and <code>_common</code> when the application uses it.</li>
  <li><code>'engine'</code> - <code>pad/</code> as well, for work on the engine itself.</li>
</ul>

<p>The script asks <code>?page&amp;padReload</code>, which the engine answers with the
newest file time before it runs any page. Together with <code>pad serve</code> (see
{app:manual 'pad_command'/}) no other tool is needed.</p>

<h2>Where it never goes</h2>

<p>Only a local request gets it - the command line, or this machine asking itself with
nothing forwarded - whatever the setting. It is left out of a bare fragment
(<code>&amp;padInclude</code>), of anything that is not an HTML page answering 200, of the
page cache, which stores the page before the script is added, and of a <code>pad export</code>.
Set it in the configuration rather than in a page's PHP: the poll is answered before any
page runs.</p>

App: manual - Page: pages/offline_applications

pages/offline_applications.pad 		Result 
{pad:meta title='Offline applications'/}

<p><code>pad pack</code> puts a whole application - its pages, its PHP, its <code>www/</code> files -
with the PAD engine and PHP compiled to WebAssembly into one directory. Opened from the disk it
runs in the browser tab; put on any https host it installs as an application and works offline.
There is no PHP server at all, and what the application writes - its SQLite database first - is
kept in the browser between visits.</p>

{pad:ignore}
<code>pad pack --install            # once: what it packs with, in ~/.cache/pad-wasm
pad pack notes                # DATA/wasm/notes/
pad pack notes --serve        # served on http://127.0.0.1:8090/ - installable
pad pack notes,ledger,kanban  # several, with a launcher</code>
{/pad:ignore}

{common:example 'fragments/offline_applications_1'/}

<h2>Two ways to run it</h2>

<table border="1" cellpadding="4">
  <tr><th></th><th>Opened from the disk</th><th>Served over https, or on localhost</th></tr>
  <tr><td>Start</td><td>double-click <code>index.html</code></td><td>open the address; the browser offers to install it</td></tr>
  <tr><td>PHP runs</td><td>in the tab</td><td>in the service worker, for every window</td></tr>
  <tr><td>The pages</td><td>in a frame filling the window, the address after the <code>#</code></td><td>at their own addresses</td></tr>
  <tr><td>Offline</td><td>always</td><td>after the first visit</td></tr>
</table>

<p>Both answer every request as a server would: cookies are kept - sessions, CSRF tokens, flash
messages, a login - any method and header of the page's own JavaScript is passed on, an upload
arrives in <code>$_FILES</code>, an answer may be binary or a download.</p>

<h2>What is kept</h2>

<p>Everything under <code>DATA/</code> - SQLite databases, uploads, JSON files, sessions - is written
to the browser's IndexedDB after every request that changed it, and put back when the
application starts again. A new pack of the same applications finds that data: an application
that keeps its schema in <code>_migrations/</code> and runs <code>padMigrate()</code> when one is pending
brings the database a visitor kept up to date - the ledger application does.</p>

<h2>The database</h2>

<p>PHP in the browser has SQLite and no MySQL. An application that is SQLite already
(<code>padSqlDriver=sqlite</code>, see {app:manual 'sqlite'/}) runs as it is. One written for MySQL on its
server can switch for the browser in <code>_offline.json</code>, whose <code>env</code> the runtime passes
where <code>padEnv</code> looks first:</p>

{pad:ignore}
<code>{
  "name": "Shop", "short": "Shop", "theme": "#0f766e",
  "icon": "icon.svg",
  "icons": { "192": "icon-192.png", "512": "icon-512.png" },
  "env": {
    "padSqlDriver": "sqlite",
    "padSqlDatabase": "shop/shop.sqlite",
    "padSqlSetup": "_install/schema.sql"
  }
}</code>
{/pad:ignore}

<p><code>.env</code> files are never packed: they hold a server's passwords, and whoever has the pack
can read it.</p>

<h2>Import and export</h2>

<p>The badge in a corner of every page - or <kbd>Ctrl</kbd>+<kbd>Shift</kbd>+<kbd>K</kbd> - opens the
runtime's panel. Its Database tab browses the tables, runs SQL, exports a database as the
<code>.sqlite</code> file or as SQL that builds it again, and imports either - SQLite checks what comes
in before it replaces anything. Its Storage tab backs up all of <code>DATA/</code> as one zip and puts
such a zip back. An application can offer the same from its own pages, on a server as in the
browser: the database file with <code>padUploadSend</code>, its rows as JSON or CSV with
<code>$padExpose</code> - the notes application's backup page does both.</p>

<h2>The page's own requests</h2>

<p><code>fetch</code>, <code>XMLHttpRequest</code>, a {app:tag 'live'/} region, an {app:tag 'ajax'/}, htmx asking for a
{app:tag 'fragment'/}, an <code>EventSource</code> - they all reach PHP in the browser. One PHP answers
every request of the application, so a stream that held it would hold the application:
<code>padSse</code> answers one round per connection there, and <code>EventSource</code> comes back after
the interval by itself, with the last event's id - see {app:manual 'server_sent_events'/}. A page
that should behave differently in the browser asks <code>padWasm()</code>:</p>

{common:example 'fragments/offline_applications_2'/}

<h2>Limits</h2>

<ul>
  <li>No MySQL, and no network from PHP: {app:tag 'curl'/}, <code>padCurl</code>, <code>padPrefetch</code> and a
      fetch of the server's own pages answer nothing offline.</li>
  <li>No sodium and no intl in the build - <code>padEncrypt</code> and the intl formatting fall back or
      are not there; the sequence subsystem's large tables are left out.</li>
  <li>One request at a time: a page that sleeps holds the others.</li>
  <li>Opened from the disk, an application's module scripts cannot import their neighbours and
      <code>document.cookie</code> does not show PHP's cookies. Served over https none of this
      applies.</li>
</ul>

<h2>The applications</h2>

<p>Three applications are made to show it, each running on this server as well:</p>

<ul>
  <li><a href="{$padHost}notes/">notes</a> - Markdown notes in SQLite: search as you type, live pins,
      attachments, a JSON export and import, the database as a download.</li>
  <li><a href="{$padHost}ledger/">ledger</a> - a household budget built by its migrations: charts,
      budgets, CSV in and out, a quick entry posted as JSON.</li>
  <li><a href="{$padHost}kanban/">kanban</a> - a task board: drag and drop posted as JSON, fragments,
      every open window kept in step by server-sent events.</li>
</ul>

<p><code>pad pack notes,ledger,kanban</code> packs them together, with a launcher. How it is built -
the runtime, the service worker, the panel - is in <code>wasm/README.md</code>.</p>

{pad:meta title='Requests and sessions'/}

<p>A page's PHP reads what the request brought, keeps what has to outlive it in the
session, and builds the address the visitor goes to next. The engine already turns request

<h2>The input</h2>

<p><code>padRequest</code> reads a value by the name the form gave it, a dot path into an
array - <code>customer.name</code> for a field named <code>customer[name]</code> - and
answers the default when the request did not bring it. A posted value wins over a query value
of the same name, the body of a request sent as <code>application/json</code> is input too,
and every text is trimmed. The query key that names the page is no input.</p>

{common:example 'fragments/requests_and_sessions_1'/}

<ul>
  <li>The names of <code>padRequestHas</code>, <code>padRequestOnly</code> and
  <code>padRequestExcept</code> are an array or one text with commas:
  <code>'customer.email, note'</code>.</li>
  <li>Blank is nothing, an empty or whitespace-only text, an empty array; a <code>'0'</code>
  is filled.</li>
  <li>A <code>*</code> in a dot path reads every item of a list:
  <code>padRequest ( 'items.*.id' )</code>.</li>
</ul>

<h2>The session</h2>

<p><code>padSessionPut</code> starts the session when there is none yet; reading never does
- a visitor without a session cookie gets the default, and no session is made to find that
out. Dot paths work here too:</p>

{common:example 'fragments/requests_and_sessions_2'/}

<p>A name listed in <code>$padSessionVars</code> is a variable as well as a session value: the
helpers keep the two in step, so a value put in is the one the end of the request writes
back. After a login, <code>padSessionRegenerate ()</code> moves the session to a new id, so an
id someone learned before it is worth nothing.</p>

<h2>The form after a failed post</h2>

<p>The page a form posts to checks it; when something is wrong it keeps the input with
<code>padFlashInput ()</code> and sends the browser back to the form with
<code>padBack ()</code>. The form's page reads the input with <code>padOld</code> - on that
one next request only, like a {app:manual 'flash_messages'/} message. Passwords and the CSRF token
are left out unless another list is given.</p>

<p>Without a list, every field whose name looks like a password, a key, a token, a card's
code or number or a one-time code stays out as well - <code>new_password</code>,
<code>user[password]</code>, <code>api_key</code>, <code>card_number</code>,
<code>otp_code</code>. That is judged by the words of the name, and no word rule knows every
name: a field it does not recognise, a <code>stripe_key</code>, is kept. For a form with such
a field, give the list yourself - it replaces the default, so it names every field that
stays out - or flash only the fields the form needs back:
<code>padFlashInput ( array_diff ( array_keys ( padRequestExcept ( [] ) ), [ 'name', 'email' ] ) )</code>.</p>

{common:example 'fragments/requests_and_sessions_3'/}

{pad:ignore}
<code>// signup.php - the page the form posts to
$errors = padValidate ( [ 'email' => 'required|email' ] );

if ( $errors ) {
  padFlash ( 'Please check the form.', 'error' );
  padFlashInput ();
  padBack ( 'signup/form' );
}

// signup/form.php - the form, filled again
$email = padOld ( 'email' );        // {input:field 'email', value=$email/}</code>
{/pad:ignore}

<h2>Going back, and stopping</h2>

<p>Both end the request, so they are shown here, not run. <code>padBack</code> follows the
browser's Referer only when it is a page of this application on this host, and goes to the
fallback page otherwise - the index when none is given. <code>padAbort</code> answers an error

<p>A search result, a page of a list, a counter: a part of a page that the browser wants to refresh on its own. <code>{pad:fragment 'name'}...{/pad:fragment}</code> names such a part. A normal request renders the whole page, the fragment in its place:</p>

{common:example 'fragments/response_fragments_1'/}

<p>A request that adds <code>&amp;padFragment=order-list</code> to the URL gets that fragment and nothing else - the same template serves the full page and the update:</p>

{common:example 'fragments/response_fragments_2'/}

<h2>How it works</h2>

<ul>
  <li>The page renders up to the end of the fragment, and the fragment's rendering - closing pipe included - is the whole response. What comes after it is not rendered at all.</li>
  <li>The response is bare, like a <code>padInclude</code> request: no wrapper, no tidy.</li>
  <li>The first fragment of that name to finish rendering is the one sent. Keep a fragment unconditional and put conditions inside it: a request for a fragment that never rendered is an error under the strict check, and an empty 404 otherwise.</li>
  <li>The page's PHP may decide too: <code>$padFragmentOnly = 'order-list';</code> - for instance when the request carries an <code>HX-Request</code> header.</li>
</ul>

<h2>With ajax and HTMX</h2>

<ul>
  <li><code>{pad:ajax 'orders', fragment='order-list'/}</code> fetches only that fragment of the page into its div.</li>
  <li>HTMX: <code><div hx-get="?orders&amp;padFragment=order-list" hx-trigger="every 5s"></code> swaps in the fresh list.</li>
  <li>An HTMX request needs no <code>padFragment</code> when it swaps an element named like the fragment: <code>hx-target="#order-list"</code> sends <code>HX-Target: order-list</code>, and a page with a fragment of that name answers it alone. A page without one renders whole, as it would otherwise. See {app:manual 'htmx'/}.</li>
</ul>
