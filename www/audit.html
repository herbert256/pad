Regression application, deeply audited.

The test inventory is substantial and the current run is green, but the release signal is not trustworthy yet. Several control-flow defects can turn an unexecuted, incomplete, new, or erroneous run into an apparent pass.

Release gate: not reliable

Strong test content; weak test-control integrity.

The app’s four-layer design is sound. The primary risk is the machinery around it: stale result reuse, auto-created baselines, incomplete status aggregation, an inverted export condition, and state-changing GET endpoints. Fixing those control-plane issues would materially raise confidence without rewriting the suites.

Executive summary

The current data says “all ok”: 835 sandbox assertions, 194 assertions across 70 Pages pages, 36 Common pages, and 764 scanned pages. That statement is internally consistent for this run, but it is not yet safe to treat it as proof that a run occurred or completed.

What is working well

Clear separation between in-process cases, real-request tests, shared-application tests, and a broad crawl. Exact body comparisons, explicit HTTP expectations, readable suite descriptions, path-guarded DATA writes, and fast local execution are all solid foundations.

What blocks trust

CI can pass after a 404 without running tests; errors and new pages do not make the top-level scan fail; first-seen pages write their own baselines; and repeated build scans can wash those states back to green. These are evidence-integrity failures, not cosmetic defects.

Security posture

The server listens on all interfaces, while expensive runs and baseline mutations are unauthenticated GET links. The request Host header is also reused to construct internal fetches and redirects. This is acceptable only if the entire installation is deliberately isolated; the current network posture is not isolated.

Best next move

Introduce a run manifest with an ID, start/completion timestamps, inventory hash, and per-status counts. Make CI consume only that fresh manifest, fail closed, and separate “observe” from “accept baseline.” That single redesign resolves most of the highest-risk findings.

Where the trust chain breaks

The suites themselves may be correct, yet the hand-off between trigger, stored state, aggregation, and verdict can still manufacture a green result.

1 · Triggercurl ?index&test starts the browser-facing run.
2 · HTTP unchecked404 and 500 responses are accepted because curl is not told to fail.
3 · State reusedExisting JSON files are read without a run ID or freshness proof.
4 · VerdictOnly suite failed counts are gated; scan errors/new/empty are ignored.

Prioritized findings

Severity reflects impact on the correctness of the regression signal first, then security, reliability, and usability. All findings below are based on the current worktree and live local instance.

CriticalF-01
CIFalse greenConfirmed

CI passes when the run endpoint returns 404

ci.sh checks only curl’s transport exit code. Without --fail, HTTP errors are success; the script then reads whatever suite JSON happened to be on disk. A broken route, server-side fatal, or request that dies before updating results can therefore pass using stale green data.

Evidence

ci.sh:15–33. A controlled nonexistent base returned HTTP 404 while the script printed all-green stale results and exited 0.

Recommended fix

Use curl --fail-with-body; generate a unique run ID; require every suite result and final manifest to carry that ID and a completion timestamp; fail if any are absent, stale, or unreadable.

HighF-02
AggregationFalse greenConfirmed

Scan errors, new pages, and empty regressions do not fail the dashboard or CI

The dashboard status becomes “WARNINGS” only when the warning count is nonzero; every other scan state is labelled “ok.” CI merely counts warnings and explicitly excludes them from its verdict. Thus an undeclared HTTP error, a newly discovered page, or a page that went empty can coexist with an overall pass.

Evidence

apps/regression/index.php:55–83 and ci.sh:37–40. Neither path gates error, new, or empty.

Recommended fix

Define a verdict matrix explicitly: fail on error, empty, unknown statuses, missing status, and usually new; let warnings be policy-configurable but never relabel other states as ok.

HighF-03
BaselinesEvidence integrityConfirmed

First-seen pages create their own baseline and disappear on the next crawl

When a page has no stored file, the crawler writes the current response as its baseline immediately and marks it new. A second crawl compares the page to the just-created copy and marks it ok without human approval. getRegressionBuild() performs multiple crawls and bulk-accepts warnings, amplifying the possibility of baseline laundering.

Evidence

_lib/regression.php:249–262 writes on new; lines 4–9 run three crawl cycles around bulk acceptance.

Recommended fix

Store candidates separately from approved baselines. Keep new sticky until an explicit reviewed POST promotes the candidate. Never perform acceptance inside a build or test run.

HighF-04
ExportSide effectsConfirmed

The examples export condition is inverted

if ( ! $extra != '&padExamples' … ) evaluates in the opposite direction from the surrounding intent: an ordinary scan falls through and writes examples, while the dedicated &padExamples run returns before exporting. The combined build flag also does not equal the single expected string.

Evidence

_lib/regression.php:264–277. The normal CI run refreshed 1,553 files under DATA/examples at the run timestamp.

Recommended fix

Replace the boolean expression with an explicit parsed flag such as str_contains($extra, '&padExamples'), and add focused tests for empty, examples-only, reference-only, and combined flags.

HighF-05
Show/diffCorrectnessConfirmed

The inspection view fabricates index diffs and cannot inspect expected errors

The scanner stores root indexes with their full wrapper, but show/index.php always fetches with padInclude. An unchanged index therefore appears changed. For any non-2xx page, the inspection view redirects to the failing page instead of showing the expected response and stored evidence.

Evidence

show/index.php:3–6. regression3/index: baseline/full response 2,329 bytes and equal; show-fetch 240 bytes and unequal. An expected error link returns 302 then HTTP 500.

Recommended fix

Share one URL builder with the crawler; omit padInclude for root indexes. Render status, headers, and escaped body for non-2xx responses instead of redirecting away.

HighF-06
SecurityNetworkConfirmed

Expensive and destructive operations are unauthenticated GETs on a network-wide listener

Test runs, full crawls, bulk baseline acceptance, and one-page acceptance are ordinary links. Apache is listening on *:80, so another host on the reachable network can trigger CPU-heavy runs and filesystem changes. Browser prefetchers, crawlers, or CSRF can also activate GET side effects.

Evidence

_inits.php, scan/index.php:15–33, and ok.php expose test, go, acceptWarnings, and ok as GET parameters. The local listener is TCP *:80.

Recommended fix

Bind development installs to loopback by default. Require POST plus CSRF protection and a local admin capability for runs and acceptance. Apply rate limits and a single-run lock.

HighF-07
SecuritySSRFConfirmed

The Host header controls internal crawl targets and redirects

PAD constructs $padHost directly from the request Host header. Regression then uses that value for server-side curl requests and Location headers. A crafted Host can steer the runner toward a different local or remote service, and can poison navigation responses.

Evidence

pad/inits/host.php:12–31 plus regression curl calls. A request with Host: 127.0.0.1:9 produced a Location header to http://127.0.0.1:9/pad/… after the internal fetch failed.

Recommended fix

Use a configured canonical internal base URL, not request metadata. Reject unapproved Host values at the web server and application boundary; never use user-controlled hosts for server-side fetches.

HighF-08
IsolationDisk growthConfirmed

The “crawl” is not observational: it executes page side effects

Action filtering applies only to PHP-only pages and recognizes four source tokens. Paired pages are always fetched. Current examples increment counters and create timestamped output files on GET; each scan therefore alters application data and accumulates artifacts. Normal scans also export examples because of F-04.

Evidence

padAppsList():299–319. apps/demo/counter.php:20–23 increments on GET. Audit-time DATA held 345 generated temp files (1.3 MB), and the counter had reached 546.

Recommended fix

Crawl an explicit read-only manifest, or run in an ephemeral DATA/database sandbox restored per page. Declare side-effect fixtures explicitly and clean them in finally; do not infer safety from source substrings.

MediumF-09
ExpectationsFalse greenConfirmed

Regex expectations can pass on HTTP failures, and “new” page tests do not fail

Exact-body expectations require a 2xx status, but whole-body regular expressions do not. A matching fragment in a 500 response can pass a test intended to assert a successful dynamic page. Separately, a page with no expectation is marked new but never increments failed, so CI accepts it.

Evidence

_lib/regression.php:666–712. The regex branch checks only preg_match; the failed counter increments only for literal FAILED.

Recommended fix

Require 2xx for body and regex modes unless the expectation starts with explicit HTTP nnn. Treat new as non-passing in CI and expose separate missing-expectation counts.

MediumF-10
NondeterminismCoverageDesign risk

Random-page detection and masking are broad enough to hide real regressions

A page is classified as drawing if its combined source contains the lowercase substring random, shuffle, or chance anywhere—including prose and comments. Once classified, every digit and every demo-result block is masked. Two extra samples decide whether a changed shape is actionable. Numeric regressions and intermittent changes can therefore be suppressed by design.

Evidence

_lib/regression.php:113–199. The current dashboard classifies 36 of 764 pages as random.

Recommended fix

Use explicit page metadata with named normalizers scoped to known fields. Preserve structural and semantic numeric assertions, seed random sources where possible, and report masked regions and sample confidence.

MediumF-11
State modelReliabilityDesign risk

A crawl has no atomic run record, completion marker, or inventory reconciliation

Each page status is overwritten independently. If a crawl dies midway, the dashboard mixes old and new statuses. Its “ran” timestamp is merely the mtime of one mid-crawl page, not proof of completion. Deleted pages are never explicitly pruned or reported; they can remain as stale stored results until separate cleanup occurs.

Evidence

getRegressionAll() has no transaction/manifest; index.php:71–75 derives time from regression/scan/index.txt. Current inventory happens to reconcile at 764 live / 764 stored.

Recommended fix

Write into a run-specific staging directory, include the discovered inventory, then atomically publish a completed manifest. Report added/deleted pages explicitly and preserve the last complete run if a new one aborts.

MediumF-12
Read semanticsSurprise workConfirmed

Opening a report can execute tests when stored results are absent or invalid

The user-facing copy repeatedly promises that a page load never runs anything. Yet getCases() and getPages() fall back to running and persisting a suite whenever its result file is missing or malformed. A fresh install or corrupt result can therefore launch hundreds of assertions merely by opening the index.

Evidence

_lib/regression.php:786–800 and 1024–1042 call the test runners on cache miss.

Recommended fix

Return an explicit “never run / result unreadable” state. Restrict execution to a deliberate POST action or CLI command, and keep read routes side-effect free.

MediumF-13
OperationsDoSDesign risk

Long runs lack bounded per-page work and mutual exclusion

The shared curl helper has no default connect or request timeout. The runner resets its PHP time limit per item, and parallel triggers can write the same result and baseline files concurrently. The diff viewer uses an O(n×m) dynamic-programming table; stored pages currently reach 3,220 lines. Expected fatal tests also flood the main Apache error log, reducing operational signal.

Evidence

pad/lib/curl.php:109–160 sets no timeout; result writes have no run lock; show/_lib/diff.php:66–92 builds the full matrix.

Recommended fix

Add connect/total deadlines, response-size and diff-size caps, a single-flight lock, cancellation, and per-page timing. Route expected negative-test logs to a dedicated channel or suppress known expected records.

MediumF-14
AccessibilityResponsiveConfirmed

The large result pages are not mobile-usable or semantically accessible

The live UI emits HTML 4 Transitional, no language or viewport metadata, two top-level H1s, layout tables, and data tables without captions, thead, or scoped headers. Actions are links rather than buttons/forms. At a 390 px viewport, the 150-case Tags page had a 797 px document width and required horizontal scrolling.

Evidence

Live DOM audit of the dashboard, scan, and Tags suite; all four sampled tables lacked captions/header scope. Index fit at 390 px; suite overflowed to 797 px.

Recommended fix

Emit HTML5 with lang and viewport metadata, use one page H1, semantic navigation/forms, captions and scoped headers, responsive cards or scroll containers, visible status text, and keyboard-focus styling.

LowF-15
IsolationMaintainabilityCode review

Per-case globals are deleted rather than restored

Array-based case setup overwrites a global and unsets it after execution. If the name existed before the case, its original value is lost. Cleanup also is not protected by finally, so a thrown exception can leave the request contaminated. The same file contains all harness logic but has no focused self-tests.

Evidence

_lib/regression.php:911–925 writes and then unsets setup globals unconditionally.

Recommended fix

Snapshot existence and value, restore in finally, reserve engine-global names, and add direct harness tests for URL building, status aggregation, normalization, cache misses, flags, and CI freshness.

Remediation roadmap

This order restores trust quickly. The first three items should land before the app is used as a merge or release gate.

Make the gate fail closed

Add --fail-with-body, a run ID, freshness validation, a completion manifest, and explicit gating for every non-passing scan status. Return a non-2xx API response when the run fails.

Separate candidates from approved baselines

Never write approved baselines during discovery. Keep new/current/approved artifacts distinct; make acceptance an authenticated, reviewed POST with a visible diff and audit record.

Fix the confirmed deterministic defects

Correct the examples flag logic; share one fetch URL builder between Scan, Show, and OK; preserve non-2xx evidence; require 2xx for regex body expectations.

Isolate execution

Bind to loopback or authenticate; use canonical configured hosts; apply CSRF/rate protection; run each crawl against disposable DATA/database state with per-page cleanup.

Publish runs atomically

Stage page results under a run directory, record inventory and timings, then atomically promote only a complete run. Detect additions, deletions, duplicates, missing results, and unknown statuses.

Test the harness itself

Add narrow unit/integration tests for CI freshness, all status combinations, new-page lifecycle, normalization, URL modes, flags, expected errors, cache misses, interrupted/concurrent runs, and baseline rejection.

Modernize the report UI

Use semantic HTML5, accessible data tables, buttons/forms for commands, visible status labels, responsive result cards, pagination/filtering for large suites, and safe escaped error inspection.

Scope and limitations

Reviewed: apps/regression/, the regression2 and regression3 fixtures, their web entry points, ci.sh, relevant shared PAD request/file/curl code, current DATA results, and the live local app at http://localhost/pad/regression/. The worktree contained substantial pre-existing staged, unstaged, and untracked changes; the audit assessed that current state and did not rewrite or discard any of them. The full gate was run once, which by design updated runtime files under DATA—and, due to F-04, refreshed examples. This was not a penetration test of external infrastructure, database permissions, or the host operating system.
