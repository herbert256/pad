App: manual - Page: pages/codes
PHP
 HTML
pages/codes.pad 		Result 
{pad:meta title='Barcodes and QR codes'/}

<p>{app:tag 'barcode:auto'/} and {app:tag 'barcode:qr'/} write a code a scanner reads. It is encoded on the server and
drawn as inline SVG - no image library, no font, no remote service - so a page with a code prints,
caches and goes in an e-mail like any other. There are {pad:echo php:count(padKinds('codes'))/}
symbologies, every one a file of <code>pad/subs/codes/types/</code>. Twelve or thirteen digits are an
EAN-13, with the check digit added when it is left off; any other text is Code 128.</p>

{common:example 'fragments/codes_1'/}

<h2>Two ways to write one</h2>

<p>The name after <code>barcode:</code> selects the symbology: <code>{barcode:upce '0425261'/}</code>.
The barcode type does the same, <code>{barcode:upce '0425261'/}</code>.
Both forms require their type prefix and draw the same UPC-E.</p>

{common:example 'fragments/codes_2'/}

<h2>Products, parcels and labels</h2>

<p>The product codes - <code>ean13</code>, <code>ean8</code>, <code>upca</code> and
<code>upce</code> - check the digit a number ends in, or add it; <code>databar</code>, GS1 DataBar, writes a
GTIN in the small symbol of loose fruit and vegetables. Code 128 and Code 93 take printable
ASCII, Code 39 capital letters, digits and a few signs, with <code>check</code> for its check
symbol. <code>itf</code> and <code>itf14</code> are the digits of cartons, <code>codabar</code> the
code of libraries and blood banks, <code>msi</code> that of shelf labels.
<code>gs1128</code> writes the GS1 element strings of a logistics label -
<code>(01)09501101530003(17)261231(10)AB-123</code> - with every value checked as GS1 defines it;
<code>datamatrix</code> with <code>gs1</code> writes them as GS1 DataMatrix, the code of medicine packs.
<code>bookland</code> is the barcode of a book, its ISBN as an EAN-13 with the ISBN above the bars,
and <code>addon=</code> puts two or five more digits beside an EAN or UPC - a magazine's issue, a
book's price.</p>

{common:example 'fragments/codes_3'/}

<h2>Two-dimensional codes</h2>

<p><code>qr</code> is the code of {app:tag 'barcode:qr'/}, which a phone camera reads; <code>datamatrix</code>
the square code of parts and medicine packs. Both take any text and choose the smallest symbol that
holds it, and both take <code>size=</code> in pixels in place of the height and scale of the bars.
<code>aztec</code>, the code of train tickets and boarding passes with a bullseye in its middle, does
the same, with <code>ecc=</code> for the share of its codewords that corrects errors.
<code>pdf417</code>, the code of boarding passes and driving licences, stacks rows of codewords
instead, each row telling the scanner where it stands; <code>columns=</code> sets how wide it is
and <code>level=</code> its error correction.</p>

{common:example 'fragments/codes_4'/}

<ul>
  <li>The colours are black on white unless <code>color=</code> and <code>background=</code> say
  otherwise - fixed, whatever the page's colour scheme, as a scanner needs the contrast.</li>
  <li>The SVG is <code>role="img"</code> with the text, or <code>title=</code>, as its name.</li>
  <li>A wrong check digit, a character the symbology has no bars for or a text too long for it is
  an error under the strict check, and nothing is drawn.</li>
</ul>

pages/diagrams.pad 		Result 
{pad:meta title='Diagrams'/}

<p>{app:tag 'diagram:auto'/} draws a diagram from a few lines of text between its tags, written the way
Mermaid writes them, and lays it out on the server as inline SVG. There is no JavaScript, so a
diagram prints, works in an e-mail and caches like any other output, and the same lines always
draw the same picture. There are {pad:echo php:count(padKinds('diagrams'))/} kinds - every kind is a
file of <code>pad/subs/diagrams/types/</code>, and a flowchart is the one drawn when the tag names
none.</p>

{common:example 'fragments/diagrams_1'/}

<p>A line of a flowchart is a chain of nodes and edges. The brackets give a node its shape -
<code>[box]</code>, <code>(rounded)</code>, <code>{decision}</code>,
<code>((circle))</code>, <code>[(database)]</code> - and the arrow its line: <code>--></code>,
<code>-.-></code> dashed, <code>==></code> thick, <code>---</code> without a head, a label
between bars. The lines are taken as they stand, so their braces need no
{app:tag 'ignore'/}.</p>

<h2>Two ways to write one</h2>

<p>The name after <code>diagram:</code> selects the kind: <code>{diagram:state}</code>. The diagram
type does the same, <code>{diagram:state}</code>. Both forms require their type prefix.
<code>sequence</code> and <code>tree</code> are tags of their own, so those two kinds are written
<code>{diagram:sequence}</code> and <code>{diagram:tree}</code>. A first
line written the Mermaid way - <code>sequenceDiagram</code>, <code>stateDiagram-v2</code>,
<code>classDiagram</code>, <code>erDiagram</code>, <code>gitGraph</code> - names the kind as well,
so a diagram copied from Mermaid draws as it is.</p>

<h2>Messages and states</h2>

<p>A sequence diagram puts the participants side by side and the messages between them from top
to bottom, with notes and frames for loops and alternatives. A state diagram draws a machine:
<code>[*]</code> is its start on the left of an arrow and its end on the right, a label follows
the colon, and a state can be a choice or a fork.</p>

{common:example 'fragments/diagrams_2'/}

{common:example 'fragments/diagrams_3'/}

<h2>Classes and tables</h2>

<p>A class diagram draws a box of three parts for every class - its name, its fields, its methods
- and the relations between them: <code><|--</code> inherits, <code>*--</code> is made of,
<code>o--</code> holds, <code>..></code> depends on, with the multiplicities in quotes. The
parent and the whole are laid out above. An entity-relationship diagram draws every entity as a
table of its attributes and the relations with the feet of a crow: <code>||</code> exactly one,
<code>o{</code> zero or more, <code>|{</code> one or more.</p>

{common:example 'fragments/diagrams_4'/}

{common:example 'fragments/diagrams_5'/}

<h2>Hierarchies</h2>

<p>A mind map and a tree read their hierarchy from the indentation: a line is a node, and a line
indented under another is its child. The mind map shares the branches of its root over two
sides, each in a colour its twigs keep; the tree stands top down, every box centred over its
children - <code>direction='LR'</code> lays it on its side.</p>

{common:example 'fragments/diagrams_6'/}

{common:example 'fragments/diagrams_7'/}

<h2>Journeys and commits</h2>

<p>A user journey puts the steps of a day in a row, a face under each at the height of its score
from 1 to 5, and a dot for everybody who takes the step. A commit graph draws the commits of a
repository on the lanes of their branches, with the branches leaving and the merges joining.</p>

{common:example 'fragments/diagrams_8'/}

{common:example 'fragments/diagrams_9'/}

<h2>Causes</h2>

<p>A fishbone - the cause-and-effect diagram of Kaoru Ishikawa - reads its hierarchy from the
indentation as well: the first line is the effect, drawn in the head on the right, a line under
it a category, a bone above or below the spine by turns, and a line under a category a cause, a
rib along the bone, with the causes of a cause hanging off it. Mermaid's first line
<code>ishikawa-beta</code> names the kind too. The causes it shows are possible ones: the drawing
proves none of them.</p>

{common:example 'fragments/diagrams_10'/}

<h2>Grammars</h2>

<p>A railroad diagram draws the rules of a grammar written in the EBNF of the W3C - the notation
of the XML specification: <code>name ::= expression</code>, a terminal in quotes, a rule by its
name, <code>[a-z]</code> a character class, <code>|</code> a choice, <code>?</code> optional,
<code>*</code> none or more and <code>+</code> one or more. Every rule is a track; a name the
grammar defines is a link to its own track.</p>

{common:example 'fragments/diagrams_11'/}

<h2>Packets</h2>

<p>A packet diagram lays the fields of a header out by their bits, as the RFCs draw them:
<code>0-15: "Source Port"</code> a field from bit 0 to bit 15, <code>+16: "Destination Port"</code>
the next 16, in rows of 32 bits - <code>bits=</code> takes another width. The fields follow each
other from bit 0, and the first and the last bit of each stand over it.</p>

{common:example 'fragments/diagrams_12'/}

<ul>
  <li>The SVG has <code>role="img"</code>, a <code><title></code> - <code>title=</code>, else
  the name of the kind - and a <code><desc></code> that says every edge, message, relation or
  step in words, so a screen reader hears the whole diagram.</li>
  <li>The colours are custom properties on <code>.pad-chart-diagram</code> -
  <code>--pad-diagram-node</code>, <code>--pad-diagram-border</code>, <code>--pad-diagram-edge</code>
  and their like - with light and dark defaults; the mind map, the journey and the commit graph
  take the colours of the charts.</li>
  <li>A kind reads only the options it draws with: <code>direction</code> on a sequence diagram is an
  option nothing reads, and a line a kind cannot read is an error that names the line.</li>
  <li>A diagram without nodes answers nothing, so its <code>&#64;else&#64;</code> shows.</li>
</ul>
