App: manual - Page: pages/application_structure
PHP
 HTML
pages/application_structure.pad 		Result 
{pad:meta title='Application Structure'/}

<p>An application is a directory under <code>apps/</code>, and a page is a pair of files in
it: <code>name.php</code> gathers the data, <code>name.pad</code> renders it - the
<a href="?pages/php_and_html">php and html</a> page is about that pairing. No routing and no
controllers: creating the files creates the page, and subdirectories become url paths -
<code>?admin/users</code> is <code>admin/users.pad</code>.</p>

<h2>The wrappers</h2>

<p>A file <code>_inits.pad</code> wraps every page of its directory: the page's own output
lands where the wrapper writes <code>@page@</code>, and an <code>_exits.pad</code> closes
below it. This very page is inside one - the menu at the side and the bar with the title
above what you are reading come from the wrapper of the manual, which opens the frame every
PAD application shares and closes it again below the page:</p>

{app:source '_inits.pad'/}

<p>Wrappers nest: the application's own <code>_inits.pad</code> wraps the subdirectory's,
which wraps the page. The page never mentions any of them.</p>

<h2>The PHP runs first, in order</h2>

<p>All PHP has run before any template renders. Down the directory chain and back up:</p>

{pad:ignore}
<code>/_inits.php
    /admin/_inits.php
        /admin/users.php
    /admin/_exits.php
/_exits.php</code>
{/pad:ignore}

<h2>Subdirectories inherit, and may override</h2>

<p>The <a href="?pages/extending">extension directories</a> work at every level.
<code>_lib/</code> files accumulate down the chain, so a deeper page has every level's
functions; the lookup for a tag, function or snippet starts in the page's own directory and
walks up, so a subdirectory may bring its own words - or redefine an inherited name, and its
version wins for its pages.</p>

<p><b><a href="{$padHost}structure/">The structure application</a></b> is this page live: a
tree three levels deep: the root carries the full set of special directories, every level
its own wrappers, and each level below overrides one or two names and inherits the rest, with
pages that show which level answered.</p>

Named slots give it more than one place for content, and <code>{pad:parms}</code> says which parameters it takes. The card below is <code>_tags/card.pad</code>:</p>

{app:source '_tags/card.pad'/}

{common:example 'fragments/components_1'/}

<h2>Slots</h2>

<ul>
  <li>A <code>{pad:slot 'footer'}...{/pad:slot}</code> pair standing directly in the content of the tag is a fill: it is taken out of the content and goes where the template has its <code>{pad:slot 'footer'}</code>. The rest of the content goes to {app:construct 'content'/}.</li>
  <li>In the template, the content of a <code>{pad:slot}</code> is its default, rendered when the caller gave no fill. <code>{pad:slot 'header'/}</code> in the caller's content is an empty fill.</li>
  <li>A default holding {app:construct 'content'/} is a frame: <code>{pad:slot 'footer'}<small>&#64;content&#64;</small>{/pad:slot}</code> renders the frame round the fill, and nothing - or its {app:construct 'else'/} part - when there is no fill.</li>
  <li>A fill is the caller's text: it renders with the caller's variables, and a <code>{#name}</code> or a <code>{pad:slot}</code> inside it belongs to the caller's tag - which is how a template passes a slot of its own on to a tag it uses.</li>
</ul>

<h2>Every use has its own</h2>

<p>The fills belong to one use of the tag, so a card inside a card keeps its own footer:</p>

{common:example 'fragments/components_2'/}

<h2>Declared parameters</h2>

<ul>
  <li><code>{pad:parms title, tone='plain'/}</code> at the top of the template declares the parameters: a name alone is required, <code>name=default</code> fills in what the caller left out. Both read as <code>{#title}</code>.</li>
  <li>A required parameter left out is an error, and so - under the strict check - is a parameter the tag does not declare: <code>{app:card title='x', titel='y'}</code> is reported by name.</li>
</ul>

<h2>Components written in the template</h2>

<p>A component used on one page only needs no file of its own. <code>{pad:define 'name'}...{/pad:define}</code> writes it in the template: from there on <code>{define:name}</code> renders the body as <code>_tags/name.pad</code> would - <code>{pad:parms}</code>, <code>{#name}</code>, {app:construct 'content'/} and slots work alike.</p>

{common:example 'fragments/components_3'/}

<p>A <code>{pad:macro}</code> is called the way a function is: its parameters are declared on it - a name alone required, <code>name=default</code> filling in - given in their order or by name, and read as fields, <code>{$label}</code>.</p>

{common:example 'fragments/components_4'/}

<ul>
  <li>Both render at every use, in its place and with its fields; both can use themselves, for the rows below the current one.</li>
  <li>A define or macro exists from the point it is walked, as a <code>{pad:content}</code> store does: a use before it is an unknown tag.</li>
  <li>A macro given too many values, missing a required one, or given a name it does not declare is an error.</li>
</ul>

pages/directory_guards.pad 		Result 
{pad:meta title='Directory guards'/}

<p>A <code>_guard.php</code> in a directory decides, for every page below it, whether the
request may see the page - before any <code>_inits.php</code> or page PHP runs. Access
control follows the file tree: put one in <code>admin/</code> and every page there is
protected, with no list of routes to keep in step.</p>

<p>The guard of this manual's <code>guarded/</code> directory:</p>

{app:source 'guarded/_guard.php'/}

<ul>
  <li>Returning <code>FALSE</code> - or anything that is not true: <code>NULL</code>,
  <code>0</code>, <code>''</code> - refuses the page with <code>403 Forbidden</code>. Returning
  <code>TRUE</code>, or no return at all, lets the request through to the next guard down.</li>
  <li>The guards run from the application root down, each directory's in turn, after the
  <code>_lib</code> files, so a guard can call the application's functions and read the session
  and request variables - and <code>$padPage</code>, to decide per page.</li>
  <li>A guard can send the visitor elsewhere itself: <code>padRedirect ( 'login' )</code>.</li>
  <li>A page a {app:tag 'page'/} tag includes is guarded too: when its guard says no, it renders as
  nothing, and the page that includes it carries on.</li>
  <li>A guarded page is never served from the page cache, nor stored in it.</li>
</ul>

<p>This request did not say <code>?pass=yes</code>, so the included page stays empty:</p>

{common:example 'fragments/directory_guards_1'/}

{pad:meta title='Layouts: extends, block and parent'/}

<p>The directories give a page its frame - every <code>_inits.pad</code> and <code>_exits.pad</code> on the way to it. A layout is a frame the page picks itself, wherever it lives, and whose regions it can override one by one. This is <code>_layouts/report.pad</code>:</p>

{app:source '_layouts/report.pad'/}

<p>A page that extends it fills in the title, adds to the sidebar and leaves the footer as it is:</p>

{common:example 'fragments/layouts_1'/}

<h2>The three tags</h2>

<ul>
  <li><code>{pad:extends '_layouts/report'/}</code> - the page is framed by that layout instead of by its directories' wrappers. The layout is named from the application root, like a <code>{pad:page}</code>; an underscore directory keeps it from being a page of its own. A layout may extend another layout.</li>
  <li><code>{pad:block 'name'}...{/pad:block}</code> in the layout is a region: its content renders unless the page overrides it. The same pair standing directly in the page is an override. The name is always quoted.</li>
  <li><code>{pad:parent}</code> inside an override is the content it overrides - to add to a region instead of replacing it.</li>
</ul>

<p>What the page holds outside its blocks goes where the layout writes {app:construct 'page'/}, or in front of the layout when it has none.</p>

<h2>Blocks in the directory wrappers</h2>

<p>The blocks of an ordinary <code>_inits.pad</code> are regions too, so a page that extends nothing still overrides them: with <code><title>{pad:block 'title'}My site{/pad:block}</title></code> in the wrapper, a page sets its own title with <code>{pad:block 'title'}Sales{/pad:block}</code> - no PHP needed. A block of such a page that overrides nothing renders where it stands.</p>

<h2>Resolved before rendering</h2>

<p>Blocks are put together in the text while the page is assembled, before anything renders, so they cost nothing at run time. Under the strict check a block of an extending page that overrides nothing is reported - usually a misspelt name - and so is an <code>{pad:extends}</code> inside another tag, where the assembly does not look.</p>
