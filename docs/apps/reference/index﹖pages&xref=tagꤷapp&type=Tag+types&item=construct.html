{meta title='Markdown collections'}

<p>A folder of Markdown files is a data source - a small flat-file CMS. The files live in
<code>_content/<name>/</code>, and {tag 'collection'} iterates them: each file is a
row, the keys of its front matter (YAML between two <code>---</code> lines) are its fields,
and three are added - <code>slug</code>, the file name without <code>.md</code>;
<code>body</code>, the Markdown written as HTML; and <code>source</code>, the Markdown as it
was.</p>

<p>This manual has a folder <code>_content/news/</code> with two files. The newest first:</p>

{example 'fragments/collections_1'}

<h2>One post</h2>

<p>A list links to the page of a post with its slug - <code>?news/post&amp;slug={$slug}</code> -
and that page names it with the <code>slug</code> option. A slug that names no file gives no
rows, so the {construct 'else'} part answers.</p>

{example 'fragments/collections_2'}

<ul>
  <li><code>body</code> is HTML; print it raw with <code>{!body}</code>. Raw HTML in a file is escaped unless the tag has the <code>html</code> option.</li>
  <li><code>sort</code>, <code>first</code>, <code>where</code> and the other handling options work on the rows as on any data.</li>
  <li>The folder is looked up like a <code>_data</code> file: the page's directory, its parents, then <code>_common</code>.</li>
  <li>In PHP, <code>padCollection('news')</code> gives the same rows.</li>
</ul>

{meta title='Components: slots and declared parameters'}

<p>A tag of your own with a <code>.pad</code> template is a component: the caller's content goes where the template writes {construct 'content'}. Named slots give it more than one place for content, and <code>{parms}</code> says which parameters it takes. The card below is <code>_tags/card.pad</code>:</p>

{source '_tags/card.pad'}

{example 'fragments/components_1'}

<h2>Slots</h2>

<ul>
  <li>A <code>{slot 'footer'}...{/slot}</code> pair standing directly in the content of the tag is a fill: it is taken out of the content and goes where the template has its <code>{slot 'footer'}</code>. The rest of the content goes to {construct 'content'}.</li>
  <li>In the template, the content of a <code>{slot}</code> is its default, rendered when the caller gave no fill. <code>{slot 'header'/}</code> in the caller's content is an empty fill.</li>
  <li>A default holding {construct 'content'} is a frame: <code>{slot 'footer'}<small>&#64;content&#64;</small>{/slot}</code> renders the frame round the fill, and nothing - or its {construct 'else'} part - when there is no fill.</li>
  <li>A fill is the caller's text: it renders with the caller's variables, and a <code>{#name}</code> or a <code>{slot}</code> inside it belongs to the caller's tag - which is how a template passes a slot of its own on to a tag it uses.</li>
</ul>

<h2>Every use has its own</h2>

<p>The fills belong to one use of the tag, so a card inside a card keeps its own footer:</p>

{example 'fragments/components_2'}

<h2>Declared parameters</h2>

<ul>
  <li><code>{parms title, tone='plain'}</code> at the top of the template declares the parameters: a name alone is required, <code>name=default</code> fills in what the caller left out. Both read as <code>{#title}</code>.</li>
  <li>A required parameter left out is an error, and so - under the strict check - is a parameter the tag does not declare: <code>{card title='x', titel='y'}</code> is reported by name.</li>
</ul>

<h2>Components written in the template</h2>

<p>A component used on one page only needs no file of its own. <code>{define 'name'}...{/define}</code> writes it in the template: from there on <code>{name}</code> renders the body as <code>_tags/name.pad</code> would - <code>{parms}</code>, <code>{#name}</code>, {construct 'content'} and slots work alike.</p>

{example 'fragments/components_3'}

<p>A <code>{macro}</code> is called the way a function is: its parameters are declared on it - a name alone required, <code>name=default</code> filling in - given in their order or by name, and read as fields, <code>{$label}</code>.</p>

{example 'fragments/components_4'}

<ul>
  <li>Both render at every use, in its place and with its fields; both can use themselves, for the rows below the current one.</li>
  <li>A define or macro exists from the point it is walked, as a <code>{content}</code> store does: a use before it is an unknown tag.</li>
  <li>A macro given too many values, missing a required one, or given a name it does not declare is an error.</li>
</ul>

pages/flash_messages.pad 		Result 
{meta title='Flash messages'}

<p>A page that takes a post redirects the browser to a plain page, so a refresh cannot post
twice - and then the page the browser lands on has to say what happened. A flash message
carries that: <code>padFlash ( 'Thanks, your message was sent.' )</code> before the
<code>padRedirect ()</code>, and {tag 'flash'} on the page it leads to.</p>

{example 'fragments/flash_messages_1'}

<ul>
  <li>{tag 'flash'} renders its content once per message, with <code>{$message}</code>
  and <code>{$type}</code>; without a message the {construct 'else'} half renders.
  <code>{flash 'error'}</code> shows the messages of that type only.</li>
  <li>The type is the second argument of <code>padFlash</code>, <code>info</code> when it is
  left out.</li>
  <li>A message lives exactly one request after the one that flashed it - the redirect's
  destination - and is gone after that, shown or not. A page that flashes and renders itself
  shows it at once, as here.</li>
  <li>The message is kept in the session, which starts on demand. A small
  <code>padFlash</code> cookie tells the next request that there is something to take, so the
  pages that never flash do not open the session at all.</li>
</ul>

{meta title='Layouts: extends, block and parent'}

<p>The directories give a page its frame - every <code>_inits.pad</code> and <code>_exits.pad</code> on the way to it. A layout is a frame the page picks itself, wherever it lives, and whose regions it can override one by one. This is <code>_layouts/report.pad</code>:</p>

{source '_layouts/report.pad'}

<p>A page that extends it fills in the title, adds to the sidebar and leaves the footer as it is:</p>

{example 'fragments/layouts_1'}

<h2>The three tags</h2>

<ul>
  <li><code>{extends '_layouts/report'}</code> - the page is framed by that layout instead of by its directories' wrappers. The layout is named from the application root, like a <code>{page}</code>; an underscore directory keeps it from being a page of its own. A layout may extend another layout.</li>
  <li><code>{block 'name'}...{/block}</code> in the layout is a region: its content renders unless the page overrides it. The same pair standing directly in the page is an override. The name is always quoted.</li>
  <li><code>{parent}</code> inside an override is the content it overrides - to add to a region instead of replacing it.</li>
</ul>

<p>What the page holds outside its blocks goes where the layout writes {construct 'page'}, or in front of the layout when it has none.</p>

<h2>Blocks in the directory wrappers</h2>

<p>The blocks of an ordinary <code>_inits.pad</code> are regions too, so a page that extends nothing still overrides them: with <code><title>{block 'title'}My site{/block}</title></code> in the wrapper, a page sets its own title with <code>{block 'title'}Sales{/block}</code> - no PHP needed. A block of such a page that overrides nothing renders where it stands.</p>

<h2>Resolved before rendering</h2>

<p>Blocks are put together in the text while the page is assembled, before anything renders, so they cost nothing at run time. Under the strict check a block of an extending page that overrides nothing is reported - usually a misspelt name - and so is an <code>{extends}</code> inside another tag, where the assembly does not look.</p>

pages/pager.pad 		Result 
{meta title='Page links'}

<p>The <code>page</code> and <code>rows</code> options cut one page out of a tag's rows. The
<code>{pager}</code> tag writes the links to the other pages: the first and the last
page, a window of pages on each side of the current one, a gap where pages are left out, and
previous and next. The current page is marked <code>aria-current="page"</code>.</p>

{example 'fragments/pager_1'}

<p>The pager reads what the paged tag left, so it comes after it, and names it - without a
name it follows the last paged tag of the page. It counts the rows that the options written
before <code>page</code> left, so a <code>where</code> in front of the page pages the rows that
pass. <code>window</code> is the number of pages on each side of the current one, 2 when not
given.</p>

<h2>The links</h2>

<p>Each link is built from the application's own address, so a mount prefix keeps working, and
keeps the other values of the request - a search field stays on every page. The value it
sets is the variable <code>page=</code> was written with: <code>page=$pg</code> links with
<code>pg=</code>, and <code>query='p'</code> on the pager names another. On a first visit the
value is not there yet, hence <code>$pg ?? 1</code>.</p>

<h2>Markup of your own</h2>

<p>Written as a pair, the pager hands the links over as rows instead: <code>$kind</code> is
<code>prev</code>, <code>next</code>, <code>page</code>, <code>current</code> or
<code>gap</code>, with <code>$page</code>, <code>$label</code> and <code>$href</code> - empty for
a gap, and for a previous or next that does not exist. With a single page there are no rows,
and the pair shows its {construct 'else'}.</p>

{example 'fragments/pager_2'}

<p>A Select table is paged by its SQL limit, so the rows do not hold the total: the pager then
counts with one more query, and only when it is there.</p>

{meta title='Recursive trees'}

<p>Menus, category trees and threaded comments are trees: each row may hold a list of rows
like itself. <code>{tree}</code> renders its body for every row, and inside that
body <code>{recurse}</code> renders the same body again for the current row's
children. <code>{branch}</code> renders only when the row has children - the place
for the <code><ul></code> around the next level.</p>

{example 'fragments/trees_1'}

<p>The rows are named by the first parameter or by <code>data=</code> - a
<code>{data}</code> block, an array of the page, a <code>_data/</code> file.
<code>children</code> names the field that holds a row's children, <code>children</code> when
not given.</p>

<h2>Depth and the other properties</h2>

<p><code>depth@tree</code> is 1 for the tree's own rows and one more for every level down -
for indentation. The other properties, such as <code>current@tree</code> and
<code>count@tree</code>, speak of the list being rendered. The {construct 'else'} part of
<code>{branch}</code> renders for a leaf, and the handling options
<code>sort</code>, <code>where</code> and <code>reverse</code> on the tree apply to every list,
the children included.</p>

{example 'fragments/trees_2'}
