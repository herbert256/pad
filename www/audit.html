Deep technical, product, safety and accessibility audit

Regression application audit

The current run is internally consistent and green, but the application is not yet a trustworthy unattended release gate: several paths can turn missing, new, stale or unreviewable evidence into ok.

Audited 9 August 2026 Source: apps/regression/ Live: http://localhost/pad/regression/ Report: www/audit.html

Scope note. This was a read-only audit of the harness and reporting UI. State-changing links such as Test, ok, Accept all warnings and Build all were deliberately not activated. Persisted results, source inventory, live read-only routes, PHP syntax, browser behavior and data consistency were inspected.

Overall assessment

Cconditionally useful; not release-gate safe

The architecture has a valuable core: real HTTP requests, version-controlled suite expectations, explicit expected-error support and a broad crawl. The current persisted dataset exactly matches the current page discovery set. The principal risk is the lifecycle around that evidence—how a result becomes green, how missing state is shown, how new/deleted pages are handled, and how review actions are authorized.

Fixing findings F-01 through F-05 would materially change the verdict. The remaining findings improve coverage fidelity, operability and the usability of a report that has grown to more than 900 rows.

Ranked findings

Severity reflects the local developer-tool context. F-01 and F-05 become more severe if the app is reachable beyond a single trusted loopback user.

High · Safety

F-01 — “Show” is an unvalidated same-host GET dispatcher

The read-only comparison route interpolates request-controlled $app and $item directly into a second URL. An encoded ampersand in item is decoded before interpolation and becomes a new downstream query parameter.

  • apps/regression/show/index.php:7-9 builds "$padHost$app/?$item$include" without validation or encoding.
  • apps/regression/ok.php:11-16 repeats the same construction and then writes a baseline.
  • A crafted value shaped like item=build%26goBuild%3D1 becomes ?build&goBuild=1 in the internal request.
  • The reachable target apps/develop/build.php:8-13 deletes multiple DATA trees before rebuilding. This destructive chain was not executed during the audit.

Impact

A comparison URL can invoke expensive or destructive actions in any same-host application; ordinary cross-site navigation can reach localhost GET endpoints.

Recommendation

Resolve app/item against an exact server-side page manifest, reject delimiters and traversal, build query strings with proper encoding, and call an internal read service rather than recursively requesting arbitrary URLs.

High · Correctness

F-02 — Missing, corrupt and never-run state renders as green

The status model collapses “no evidence” into zero failures, which multiple views translate to ok or all ok.

  • apps/regression/_lib/regression.php:912-925 returns failed=0 and new=0 for missing/unreadable suite JSON.
  • apps/regression/index.php:15-25 maps that fallback to status ok, even while the adjacent columns say never run.
  • All three suite controllers derive the verdict only from failed; a result with new tests says all ok.
  • getScanCounts() returns an empty set when the scan directory is missing; the overview then says 0 pages, all ok and never.
  • ci.sh:53-58 has no scan run manifest, freshness/completeness check or unknown-status check. A missing scan tree counts as zero attention.

Impact

A fresh environment, deleted DATA directory, partial JSON read or never-completed crawl can look successful to a person and can escape parts of the CI gate.

Recommendation

Add explicit not-run, running, incomplete and invalid states. Persist a run manifest with run ID, start/end, expected/observed counts and completion status. Treat every state except an explicitly complete pass as non-green.

High · Coverage

F-03 — New pages self-approve; deleted pages remain green forever

The crawl has no durable reviewed-inventory lifecycle.

  • apps/regression/_lib/regression.php:350-368 labels a missing baseline new but immediately writes the received body as the baseline.
  • On the next run, the stored body exists; an unchanged page becomes ok without any acceptance action. A second CI run can therefore approve a new page by repetition alone.
  • The scan dashboard and getScanCounts() enumerate stored DATA files. Neither compares stored keys with the current discovery set or marks removed pages deleted.
  • The current dataset happens to be exact—1,743 discovered and 1,743 stored—but this was established independently, not guaranteed by the app.

Impact

Additions need only one failed run before becoming trusted; deletions are invisible and inflate the “ok” count with pages that no longer exist.

Recommendation

Store first responses as unapproved candidates, keep them new across reruns, and promote only through explicit review. Diff the current discovery manifest against the reviewed manifest and surface deleted as attention.

High · Functional

F-04 — Demo-result diffs render as an empty rule box

The specialized comparison path for pages containing demo markers is broken by an include-name collision.

  • apps/regression/show/index.php:21-40 correctly extracts changed demo result/source blocks.
  • apps/regression/show/index.pad:21-25 invokes {lines}, intending show/_include/lines.pad.
  • Live checks of sequence/basic/chance had a stored result different from two successive live draws, but showed no SRC/OLD/NEW table, no difference and no acceptance link.
  • The rendered markup was the empty two-rule wrapper from apps/_common/_include/lines.pad, proving the wrong include resolved.

Impact

The primary human-review surface silently withholds the actual change for demo-backed pages—precisely the pages the special code was written to make easier to inspect.

Recommendation

Rename the local include/tag to an unambiguous name such as demoDiffLines, and add a browser regression fixture asserting visible SRC, OLD, NEW and diff content.

High · Integrity

F-05 — Acceptance and test mutations use unchecked GET requests with no run lock

ok.php fetches the requested page, ignores the returned status, writes whatever body arrived, and unconditionally writes status ok. A page that fails between scan and acceptance can therefore have an error/empty transfer recorded as an accepted baseline.

Test, scan, accept-all, per-page ok and build actions are links using GET. Link prefetching, cross-site navigation, double-clicks or two operators can trigger or overlap runs.

  • apps/regression/ok.php:13-16 never checks $curl['result'].
  • apps/regression/_lib/regression.php:34-65 invokes each accept action by GET and ignores each response.
  • apps/regression/_inits.php:26-31 exposes mutating Test actions as links.
  • apps/regression/scan/index.pad:23-25 exposes bulk acceptance as a link with no confirmation.
  • Writes are individually locked by the shared helper, but the app has no run-level mutex, immutable run ID or atomic completed snapshot.

Recommendation

Use POST + CSRF protection + a confirmation screen for every mutation; require a known current warning candidate and a successful expected response before acceptance; acquire one run lock; write results under a run ID; atomically publish only a completed run; expose progress and failure counts.

Medium · Coverage

F-06 — Volatile-page detection masks too much and defaults uncertainty to clean

A page becomes volatile when its source contains the substring random, shuffle or chance—including comments, prose or unrelated identifiers.

  • regression.php:175-210 removes request/session IDs, all digit runs, weekday/month names and entire demo-result bodies.
  • regression.php:218-223 uses three raw substring tests as the volatility declaration.
  • regression.php:236-258 returns random whenever two fresh shapes disagree, even if both differ from the baseline.
  • All 66 current random statuses are excluded from overview attention and the CI verdict.

Impact

Deterministic regressions in numbers, dates or demo results can be erased; unstable structural regressions are reported as an accepted random condition.

Recommendation

Replace source-word inference with explicit metadata and a per-page normalizer/oracle. Report inconclusive volatility separately and make it attention-worthy until an invariant is supplied.

Medium · Safety & discovery

F-07 — Crawl inclusion and side-effect safety depend on source substrings

The crawler guesses whether a PHP-only page mutates state by looking for four function-name strings. Paired/template pages bypass that check entirely.

  • regression.php:391-445 builds the page inventory heuristically.
  • Only padRedirect, padRestart, padFilePut and padDeleteDataDir are recognized, and only in PHP-only pages.
  • Raw strpos(..., 'develop') excludes every path containing that substring, not just the develop application.
  • The current inventory includes regression2/file/file and file/index, whose own suite descriptions say they write files/output.
  • Suite-directory collapsing similarly treats any {page substring as proof that an index covers every sibling.

Impact

Harmless pages can be silently skipped, action pages can be executed, and new sibling tests can be omitted without appearing new.

Recommendation

Use a declarative page/test manifest with explicit crawl: safe|skip, expected side effects and coverage relationships. Default unknown pages to skipped-with-attention in shared environments.

Medium · Diagnostics

F-08 — Twenty-five clean statuses have no historical response body

Status classification occurs before the only branch that saves a first body.

  • regression.php:350-368 saves HTML only for status new.
  • Expected errors and the hard-coded random-page list are classified before the new check.
  • The current DATA tree contains 17 expected and 8 random .txt statuses without adjacent .html.
  • The live clock comparison consequently showed only a fresh rendering, with no baseline, no diff and no explanation that history was absent.

Impact

Operators cannot inspect historical evidence for expected failures and several permanently volatile pages even though those records contribute to a clean total.

Recommendation

Persist the first response body and HTTP metadata for every status class, independently of verdict. Make “baseline unavailable” explicit in Show.

Medium · UX & accessibility

F-09 — The largest reports are difficult to navigate and overflow the viewport

The reporting model renders every row into one unfiltered table and relies on the shared legacy shell.

  • The Framework page produces about 354k characters, 5,574 DOM nodes, 918 result rows and 936 links.
  • At 1280px it was 28,000px tall and 1,558px wide; at a 390px viewport it still required 1,558px of horizontal scroll.
  • A generic Show diff reached 1,660px wide at the 390px viewport.
  • The live document has no language, viewport meta, landmarks or ARIA metadata; it uses two page-level H1s and layout tables/blockquote.
  • Dozens of links share the accessible name show; tables have no captions, sticky headers, filters, fail-only mode or group navigation.

Impact

Finding a failure is slow, mobile use is impractical, and assistive-technology users receive weak structure and many ambiguous controls.

Recommendation

Render summary/failures first, add search/group/fail-only filters and pagination or disclosure, wrap wide code, label per-row actions, use semantic landmarks and one H1, and fix the shared shell’s lang/viewport.

Low · Maintainability

F-10 — Small contract and markup defects increase ambiguity

  • getRegressionWarning() is documented as returning accepted items but returns nothing; one caller still passes an unused 'ok' argument.
  • show/_include/changed.pad:9 closes a cell with invalid </tb>.
  • Suite JSON validation checks only for a tests key before consumers assume every other field exists.
  • Suite comparisons trim response ends, while the README describes an exact body comparison.
  • Displayed run times use the server timezone without a label; the live server reports UTC while the audit workstation is Europe/Amsterdam.
  • The scan’s “last run” is the mtime of one page’s status file, not a completion record.

Recommendation

Define and validate persisted schemas, align comments and signatures, lint rendered HTML, label timestamps with timezone, and derive run time only from an atomic completion manifest.

What is working well

The audit found a strong testing idea under the lifecycle and interface defects.

Strong Test fidelity

  • Suites exercise real HTTP requests, including each page’s PHP half and application boundary.
  • Pages/Common expectations are version-controlled and are never rewritten by the suite runner.
  • Expected failures can assert both HTTP status and a body pattern.
  • Regex expectations also require a healthy 2xx response, preventing an error page from passing on a surviving fragment.
  • The Framework suite isolates each of 917 engine cases as a request.

Strong Current hygiene

  • The current framework case/expectation inventory is exactly paired.
  • The current crawl discovery set and stored status set are exactly paired.
  • All saved suite row names are unique and all current statuses are recognized.
  • Report pages do not rerun suites merely by being viewed.
  • Concurrent crawl windows isolate known self-testing applications that share state.

Bottom line: keep the real-request and handwritten-expectation architecture. Repair the evidence lifecycle around it rather than replacing the harness wholesale.

Remediation plan

Sequence the work so the tool first stops producing false confidence, then becomes easier to operate.

  1. Close the dispatcher and mutation boundary.Validate known pages, encode URLs, convert mutation GETs to protected POSTs, check fetch results and add a run lock.
  2. Make unknown evidence fail closed.Add explicit run states and an atomic completion manifest; update both UI and CI to require a complete, fresh run.
  3. Repair baseline lifecycle.Stage new candidates, require explicit promotion, detect deleted pages and preserve bodies/HTTP metadata for every status.
  4. Restore change review.Fix the demo include collision and invalid markup; test generic, demo, missing-baseline and error comparisons in the browser.
  5. Replace source heuristics with declarations.Declare crawl safety, volatility normalizers, expected side effects and directory coverage in manifests.
  6. Make reports usable at scale.Prioritize failures, add filters/group navigation, improve semantic structure and remove viewport-wide overflow.

Acceptance criteria

These tests should be added before calling the remediation complete.

Gate integrity

  • With DATA/suites or DATA/regression absent, every UI status is non-green and CI exits nonzero.
  • An interrupted/partial run never replaces the last completed run.
  • An unknown or malformed scan status fails CI.
  • A new page remains new after repeated runs until explicit acceptance.
  • A deleted page appears as deleted and blocks the gate until reviewed.

Safety and review

  • Encoded &, ?, traversal and unknown app/item values cannot add downstream parameters or leave the page manifest.
  • A non-2xx/expected response cannot be accepted as ok.
  • All mutations require protected POST, confirmation and a known candidate/run ID.
  • A changed demo page visibly shows SRC, OLD, NEW and the actual difference.
  • Every clean status has inspectable response metadata; missing history is explicit.

Coverage fidelity

  • Every omitted sibling page is explicitly declared covered by another case.
  • Every crawled page is explicitly marked safe or is run in an isolated disposable data scope.
  • Volatile pages have named normalizers/invariants; inconclusive results are not counted as clean.

Interface and accessibility

  • At 390px, reports do not cause page-level horizontal scrolling.
  • Failures/new/deleted/incomplete results are reachable before passing rows.
  • The document has a language, viewport, landmarks, one H1, table captions and uniquely named actions.
  • Keyboard and screen-reader navigation can move by suite, group and failing result.
