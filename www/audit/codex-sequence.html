Executive summary

The subsystem works broadly, but one data design and several missing guards create outsized risk.

1critical finding
4high findings
80sequence types
297demo routes exercised

54/54generated vectors matched runtime

Primary risk: the OEIS lookup is a 73.4 MB PHP constant.

Loading it once consumed approximately 1.81 GB peak PHP memory in a controlled CLI measurement. It fails under a 1 GB memory limit and makes the all-sequences catalogue consistently take about 1.1 seconds. Concurrent OEIS requests can multiply this cost across web workers. This should be redesigned before the app is treated as production-safe.

What is reliable

The principal tag pipeline is understandable once mapped, all reviewed PHP files parse, every shipped demo and reference route completed successfully on its intended inputs, and all 54 generated lookup tables agreed with the live engine for their first ten values.

What is not yet reliable

Malformed or adversarial parameters can cause non-terminating work, fatal action errors, local text-file traversal, and verbose error disclosures. Two published mathematical types have incorrect or ambiguous semantics, and the demo suite does not assert mathematical truth.

Severity context. App security findings assume the route can be reached by users outside a trusted local workstation. If it is permanently bound to localhost, exploitability is lower, but the unsafe code and secret-bearing diagnostics should still be fixed before reuse.

This was a source-level and local-runtime audit, not a formal proof of all 80 mathematical definitions, a production load test, or an authenticated infrastructure review. Architecture

A plugin-like include pipeline built on request-global state

The public helper and PAD tag entry points converge on the same pipeline. Sequence types, actions and options are discovered primarily through naming conventions and file presence. Runtime state is carried in globals prefixed $pq; selected strategies and type files are then included dynamically.

Public tag / helper
start/
Initialise state
inits/
Select and run builder
build/ + types/
Plays and actions
plays/ + actions/
Store, shape, return
exits/

Benefits

  • Adding a type is inexpensive and convention-driven.
  • Build strategies separate generated, predicate, function, order and fixed-table families.
  • Actions compose after generation and the demo app exercises a broad surface.

Costs

  • Global mutable state obscures contracts and makes nested/reentrant execution fragile.
  • Dynamic includes and function naming are difficult for static analysis and require strict allowlists.
  • Filesystem layout becomes executable configuration, so dead or maintenance files can affect dispatch.

SEQ-01

OEIS constant has catastrophic per-process memory expansion

Critical

types/oeis/oeis.php is a 73,379,695-byte source file defining 375,611 array entries as one PHP constant. Text that is large on disk expands into hashes, zvals and arrays when compiled/loaded. A single controlled include reached approximately 1.81 GB peak memory and took about 0.845 seconds; the same include failed with memory_limit=1G.

Sourcepad/sequence/types/oeis/oeis.php:3–10
pad/sequence/types/oeis/fixed.php
pad/sequence/types/oeis/make.php
Observed375,611 entries · 73.4 MB source
PHP peak: 1,808,220,160 bytes
1 GB limit: fatal memory exhaustion

Impact. A deployment with a common 1 GB worker limit cannot serve OEIS. With a 2 GB limit, even a few concurrent workers can exhaust host memory, trigger swapping or be killed. The all-sequences page invokes OEIS and therefore inherits the cost.

Recommendation. Remove the corpus from PHP source. Store records in an indexed, read-only format such as SQLite or a compact keyed binary/line-offset file; retrieve only one A-number per request; add a bounded process cache for hot records. Keep metadata/catalogue rendering from loading any term corpus. Test under realistic FPM worker concurrency and a deliberately modest memory limit.

SEQ-02

Non-progressing increments defeat the safety limit

High

When to= or stop= supplies a “natural end”, initialisation replaces an omitted try limit with PHP_INT_MAX. The main builder only checks $pqGo <= $pqTo and then adds the unvalidated increment. With increment=0, the iterator never advances. A negative increment starting below to moves farther away from termination.

Sourcepad/sequence/inits/limits.php:11–18
pad/sequence/build/types/type/loop.php:13–25
Safe bounded prooffrom=1,to=3,increment=0,try=5 → [1,1,1,1,1]
from=3,to=5,increment=-1,try=5 → [3,2,1,0,-1]

Impact. An erroneous or attacker-controlled tag can occupy a PHP worker for an extreme duration. Dynamic random increments can encounter related zero/direction problems.

Recommendation. Validate that increments are finite and directionally valid. Either reject <= 0 for the current ascending contract, or implement explicit ascending/descending branches. Retain an absolute, configurable hard candidate cap even when a natural bound exists, and validate random increment ranges before entering the loop.

SEQ-03

Easy error paths return environment and credential-bearing diagnostics

High

Unrecognised query values are dereferenced or scanned without validation. Requests such as an invalid concept, example, or reference item return HTTP 500 with the framework’s verbose JSON error state. The response includes stack details, filesystem paths, server variables, framework globals and configured database credentials. Values are intentionally redacted from this report.

Reproduced triggers?index…&concept=bogus
?examples&example=bogus
?reference2&dir=bogus&item=bogus
Observed responseHTTP 500 · full trace and application/global state · filesystem and server metadata · database password variables

Impact. An unauthenticated visitor can acquire reconnaissance data and live secrets if the app is reachable. The root issue spans app input validation and the production error renderer.

Recommendation. Map query values through explicit allowlists and return ordinary 404/400 responses for invalid values. In non-development modes, send only a correlation ID and generic message to the client; log a redacted trace server-side. Ensure global dumps filter all secret-like keys and add a test that deliberately throws while asserting no configured sentinel secret appears in the response.

SEQ-04

Reference endpoint accepts path traversal

High

The reference endpoint interpolates request-derived $dir and $item directly into DATA . "reference/sequence/$dir/$item.txt". No identifier validation, catalogue lookup, canonicalisation or base-directory containment check occurs.

Sourceapps/sequence/reference2.php:3–12
Safe proofdir=../../../pad/sequence/types/prime/flags
item=readme
Read text from outside the intended reference tree

Impact. The forced .txt suffix narrows targets, but any readable matching file reachable from the data directory can be disclosed and parsed. Future changes to suffix or parsing would widen the exposure.

Recommendation. Resolve dir/item from the generated reference index, reject non-identifier values, canonicalise with realpath(), and verify the resolved path begins with the canonical reference root plus a directory separator. Return 404 on any mismatch.

SEQ-05

The lucky-number algorithm returns a different sequence

High

The lucky-number sieve should begin 1, 3, 7, 9, 13, 15, 21, 25…. Its recursive predicate resets $counter = 2 on every call, so it repeatedly performs only the first elimination stage. Live output is 1, 3, 7, 15, 31, 63, 127…—Mersenne numbers.

Sourcepad/sequence/types/lucky/bool.php:3–28
pad/sequence/types/lucky/generated.php
ObservedExpected: 1,3,7,9,13,15,21,25
Actual: 1,3,7,15,31,63,127,255

Why the current check misses it. The generated table contains output from the same broken algorithm. Runtime/generated agreement therefore proves internal consistency, not mathematical correctness.

Recommendation. Implement the actual lucky-number sieve with explicit survivor-list state, regenerate its table, and add a golden vector from an independent authoritative definition. Include membership/non-membership cases around every early sieve boundary.

SEQ-06

The documented build= strategy override is never applied

Medium

build/given.php returns when $pqBuildName == TRUE. Under PHP loose comparison, every non-empty strategy string equals TRUE, so a supplied name is silently discarded. A probe with build=fixed retained pqBuild=loop even though the parsed parameters contained the requested override.

Sourcepad/sequence/build/given.php:3–21
pad/sequence/options/types/build.php:3–9
Observed statepadPrm build = "fixed"
pqBuildName = "fixed"
pqBuild = "loop"

Recommendation. Use an explicit sentinel check such as === TRUE. Before re-enabling this path, map the requested value through a strict strategy allowlist. Otherwise the later dynamic include path could turn the correctness fix into a traversal/local-file-inclusion risk.

SEQ-07

Action boundary cases become framework-level fatal errors

Medium

average divides by the result count without handling an empty sequence. element=N constructs a one-based map and indexes it without checking the requested position. Both validly shaped tags can therefore terminate the page instead of producing an empty result or controlled domain error.

Sourcepad/sequence/actions/types/average.php:3–6
pad/sequence/actions/types/element.php:3–10
ReproducedEmpty filtered result + average → Division by zero
3 values + element=10 → Undefined array key 10

Recommendation. Define action contracts for empty input and invalid indices. Prefer a typed/structured Sequence error that the renderer can present safely. Apply the same existence/range validation to named stores, merge/append/prepend, pull indices and parameter-derived store lookups.

SEQ-08

median is a positional middle, not a mathematical median

Medium

The action does not sort. It selects the zero-based floor(count / 2) entry from the pre-action snapshot; for an even count it returns the upper positional middle rather than averaging the two central sorted values. The unsorted input [9,1,5,3] returned 5, while its conventional numeric median is 4.

Sourcepad/sequence/actions/types/median.php:3–17
Contract mismatchCurrent: positional upper-middle
Conventional: sort, then central value or mean of two

Recommendation. Either sort a numeric copy and implement a documented even-count rule, or rename the operation to middle. Preserve original keys only if that behavior is intentionally part of the action contract.

SEQ-09

strong has a public taxonomy conflict

Medium

The implementation tests whether a number equals the sum of the factorials of its digits, producing factorions/strong numbers such as 1, 2, 145, 40585. The sequence list describes it as “strong primes,” which is a different concept. The current generated output begins 1, 2, 145.

Sourcepad/sequence/types/strong/bool.php:3–23
Decision requiredKeep algorithm → label/document “strong numbers (factorions)”
Keep label → implement strong-prime definition

Recommendation. Resolve the intended public contract, rename the type if necessary, and lock it with independent golden vectors and a definition in the reference page.

SEQ-10

Demo breadth is not regression-test depth

Medium

No formal unit, property or conformance suite was found for the subsystem. The demo application supplies impressive route breadth, but success means “rendered without an error,” not “returned the right mathematics.” Generated tables are often produced from the implementation they are later compared against, allowing shared defects such as lucky to pass.

Recommendation. Add three layers: (1) independent golden vectors for every type; (2) property tests for identities, monotonicity, bounds, membership and action semantics; and (3) hostile-input tests for progress, limits, stores, indices, empty sets and path values. Keep the full demo/reference crawl as a fourth end-to-end smoke layer.

SEQ-11

The demo app is not responsive or structurally accessible

Medium

The rendered app declares HTML 4.01 Transitional, omits a language and viewport declaration, has no main/nav landmarks, and relies on deprecated center, font, bgcolor and layout tables. At a 390 px viewport the document was 557 px wide, creating 167 px horizontal overflow and clipping the code/result table.

Base-page DOM2 h1 · 2 h2 · 6 tables · 0 main/nav/header/footer landmarks · 3 center · 26 font
Content defectsUnclosed bold element in index.pad
“with” instead of width in rendered table
substract/sence spelling and stale URL copy

Recommendation. Move to semantic HTML5 with lang, viewport metadata, skip link, labelled navigation and aria-current. Replace layout/deprecated elements with CSS; stack or horizontally contain demonstration tables; improve focus states; and run automated accessibility checks plus keyboard and screen-reader smoke tests.

SEQ-12

Global state and dead paths make changes harder to reason about

Low

The engine shares a large mutable $pq* namespace. Initial cleanup unsets nearly every matching global except selected stores, making nested calls, extensions and error recovery fragile. Duplicate initialisation exists, while several apparent paths are unused or stale: sequence/pull.php, exits/return.php, exits/start.php, start/eval/pull.php and start/types/resume.php. One stale exit refers to an undefined variable.

A maintenance generator named types/oeis/build.php also lives where file presence participates in runtime strategy discovery. It is not currently selected because another strategy wins, but the placement is unnecessarily hazardous.

Recommendation. Introduce a request-scoped context object with explicit fields and typed action/type interfaces, then migrate incrementally behind the existing public API. Confirm and delete dead paths. Move code/data generators outside runtime discovery directories and make the registry explicit rather than inferred from arbitrary files.

SEQ-13

Smaller performance and validation debts compound under scale

Low
  • harshad/bool.php divides through floating point until underflow instead of walking digits with intdiv().
  • The fallback array helper serialises through comma-separated text and reparses it, which is lossy for string values containing commas and ambiguous for empty results.
  • Temporary action stores use generated __action__… keys without an obvious cleanup phase.
  • Random increment setup and several store-index paths lack zero, range or existence validation.
  • The all-sequences catalogue recomputes 80 types—including OEIS—on each request rather than serving metadata or a cached preview.

Recommendation. Address these behind the P0/P1 fixes: add an internal array-return API, clean temporary stores deterministically, centralise numeric/store validation, use integer arithmetic and render catalogue previews from cached vetted vectors.

Application quality

The desktop demo is usable; mobile and information architecture need work.

Desktop

The restrained, text-first interface makes individual examples easy to scan and the primary pages render without console noise. The actions page exposed 48 table rows; the examples page exposed 47 links.

Mobile

The fixed table-based layout exceeds a 390 px viewport by 167 px. Code/results are clipped without horizontal navigation cues, and the missing viewport metadata further weakens real-device rendering.

Reference discoverability. The reference index presents 493 links (475 reference targets) in a dense page. Add search, filter by category/type, a clear current location and short definitions. This will improve discoverability more than adding further link density.

Positive findings

Useful foundations worth preserving

  • The subsystem has a broad, inspectable catalogue: 80 types, 29 actions and 32 option definitions.
  • All PHP files in scope passed syntax validation.
  • Every discoverable shipped demo and intended reference route rendered successfully.
  • All 54 generated tables tested agreed with live output for the sampled prefix.
  • Basic ranges, primes, order offsets and keep filters produced expected representative results.
  • Type/build/action separation gives a plausible seam for incremental hardening without breaking the public tag syntax.
  • Untrusted type text tested in the catalogue was HTML-escaped; no reflected XSS was found in that path.
  • No client-side console errors or warnings were observed on the principal app pages.

Remediation roadmap

A practical order of operations

P0Contain operational and disclosure risk

  1. Replace the PHP OEIS constant with per-record indexed storage and keep catalogue rendering metadata-only.
  2. Validate iteration direction/increment and enforce a hard absolute candidate budget.
  3. Disable secret-bearing client diagnostics outside development; add response redaction tests.
  4. Allowlist app query values and enforce realpath containment in reference2.php.

P1Restore contract correctness

  1. Fix lucky from an independent definition and resolve the strong taxonomy.
  2. Fix build= with strict comparison plus an explicit strategy allowlist.
  3. Define and implement empty/index/store error semantics for all actions.
  4. Decide whether median means statistics or positional middle.
  5. Add golden vectors, properties and malicious-input regression cases to CI.

P2Reduce long-term friction

  1. Modernise the demo to semantic, responsive HTML and improve reference search/filtering.
  2. Introduce a request-scoped context and explicit registries behind the current API.
  3. Delete confirmed dead paths and move generators outside runtime discovery trees.
  4. Replace string round-trips, floating digit loops and temporary-store leaks.
  5. Correct copy, spelling and stale route documentation.

Bottom line

Do not scale the current OEIS path; harden iteration and errors before broader exposure.

The normal demonstration surface is impressively broad and mostly stable, but happy-path coverage masks a small number of severe failure modes. The first remediation cycle should be tightly focused: move OEIS out of PHP source, guarantee loop progress, eliminate client-side state dumps, contain reference paths, and correct the lucky sequence. Those changes remove most acute risk without requiring a wholesale rewrite.
