App: alpine - Page: guide
PHP
 HTML
guide.pad 		Result 
{meta title='Guide - PAD + Alpine'/}
<header class="example-head">
  <h1>Alpine on a PAD page</h1>
  <p class="lede">
    Alpine reads attributes, PAD writes them. Both love braces - so give each its own, hand
    Alpine its state as JSON, and let it talk back to the page that wrote it.
  </p>
</header>

<h2>1. The braces</h2>
<p>PAD reads every <code>{</code> of a template as the start of a tag; Alpine writes objects
   with them. Three ways that never collide:</p>
<div class="grid">
  <div class="card">
    <h3>State from PHP</h3>
    <p>The ^ sigil writes a field as JSON, escaped for the attribute - <code>x-data="{^profile}"</code>.
       No brace of Alpine's in the template, and a quote in a value stays text.</p>
  </div>
  <div class="card">
    <h3>Components in a file</h3>
    <p><code>Alpine.data('tabs', ...)</code> in a script of <code>www/</code>, called by name:
       <code>x-data="tabs({^tabs})"</code> - the file never meets the PAD parser.</p>
  </div>
  <div class="card">
    <h3>A space after the brace</h3>
    <p><code>x-data="{ open: false }"</code> written as <code>{ open: false }</code> -
       a brace with a space after it is no PAD tag. It works for a short object; prefer the other two.</p>
  </div>
</div>

<h2>2. Load order</h2>
<p>The application's scripts first, Alpine last and deferred - a page's components register
   themselves on <code>alpine:init</code> before Alpine walks the page:</p>
{highlight 'html'}
<script src="alpine-app.js"></script>                         <!-- pad.get, pad.post -->
<script defer src="https://unpkg.com/alpinejs@3/dist/cdn.min.js"></script>
...
<script src="examples/search.js"></script>                    <!-- Alpine.data('search', ...) -->
{/highlight}

<h2>3. Talking back</h2>
<p>A page answers JSON when asked - <code>?page&amp;padFormat=json</code> - with only what its PHP
   names in <code>$padExpose</code>; the templates do not run for it. A post carries the session's
   token in a header, read from <code><meta name="csrf-token" content="{csrf token/}"></code>:</p>
{highlight 'js'}
const answer = await pad.get('examples/search', { q: this.q });   // the JSON of $padExpose
const saved  = await pad.post('examples/todos', { op: 'add', text }); // X-CSRF-Token sent
{/highlight}

<h2>4. One set of rules</h2>
<p>Keep a form's rules in PHP: <code>padValidate ( $rules )</code> checks the post,
   <code>padValidateClient ( $rules )</code> hands them to the component, {validator} brings the
   checker, and <code>padValidate.field ( rules.email, value, form )</code> answers in the server's
   words.</p>

<h2>5. Events from the server</h2>
<p><code>padSse()</code> streams JSON events; an <code>EventSource</code> opened in
   <code>x-init</code> - in a component that closes it again in <code>destroy()</code> - turns them
   into state.</p>

<div class="callout"><p>Values are text: whatever a visitor typed, the ^ sigil writes it as JSON escaped for the attribute,
   and <code>x-text</code> puts it in as text. Avoid <code>x-html</code> with data that is not yours.</p></div>

App: htmx - Page: guide
PHP
 HTML
guide.pad 		Result 
{meta title='Guide - PAD + htmx'/}
<header class="example-head">
  <h1>How PAD answers htmx</h1>
  <p class="lede">
    htmx asks for HTML and swaps it in. A PAD page is HTML with names on its parts - so the
    same template answers the browser's first visit and every question htmx asks after it.
  </p>
</header>

<h2>1. Name the part</h2>
<p>A {fragment} around the part that changes; the element around it gets the same name
   as its id:</p>
{highlight 'pad'}
<input name="q" hx-get="?products" hx-trigger="input changed delay:300ms" hx-target="#results">

<ul id="results">
  {fragment 'results'}
    {products}<li>{$name}</li>{/products}
  {/fragment}
</ul>
{/highlight}

<h2>2. PAD answers the part alone</h2>
<p>htmx sends <code>HX-Request: true</code> and the id of the element it swaps in
   <code>HX-Target</code>. When the page has a fragment of that name, the answer is that fragment
   and nothing else - no wrapper, no rest of the page; when it has none the page renders whole,
   as it always did. A request can also name the fragment itself, for an element without an id
   or another part than the target:</p>
{highlight 'pad'}
<tr hx-get="?orders&p=2&padFragment=rows" hx-trigger="revealed" hx-swap="afterend">
{/highlight}
<p>The page's PHP runs as for any request - <code>$q</code> is the request's value - and may narrow
   what the fragment shows: <code>$padFragmentOnly = 'row'</code> sets the answer from PHP. A
   fragment inside a loop answers with the first row it renders, so narrow the rows to the one
   asked for.</p>

<h2>3. Posts carry the token</h2>
<p>With <code>$padCsrf</code> on, a post without the session's token is refused before the page
   runs. A {form} carries it as a field; for an <code>hx-post</code> on anything else, put
   the header on the body once - the ^ sigil writes the array as JSON for the attribute:</p>
{highlight 'pad'}
<body hx-headers="{^headers}">          <!-- $headers = [ 'X-CSRF-Token' => padCsrfToken () ] -->
{/highlight}

<h2>4. Forms check the same rules twice</h2>
<p>Fields with <code>rules=</code> are checked on the server before the PHP runs, and with
   <code>client</code> in the browser first. Posted through htmx, a form that broke a rule comes
   back as its own fragment, refilled, with PAD's messages beside the fields:</p>
{highlight 'pad'}
<div id="signup">{fragment 'signup'}
  {form 'signup', client, error, hx-post='?signup', hx-target='#signup'}
    {input 'email', label='E-mail', rules='required|email'/}
  {/form}
{/fragment}</div>
{/highlight}

<h2>5. More than one place</h2>
<p>An answer can update other parts of the page as well: elements in it marked
   <code>hx-swap-oob="true"</code> go where their id is - the cart count in the header, a summary
   beside the list.</p>

<h2>6. Pushed by the server</h2>
<p><code>padSse()</code> keeps a page's connection open and sends events; with htmx's sse
   extension each event's HTML is swapped in as it arrives:</p>
{highlight 'pad'}
<div hx-ext="sse" sse-connect="?ticker" sse-close="done">
  <ol sse-swap="tick" hx-swap="afterbegin"></ol>
</div>
{/highlight}

<div class="callout"><p>The page cache knows htmx: a request for a part is answered fresh and never stored, and a
   fragment chosen by a header is never stored under the page's address.</p></div>

{meta title='Alpine'/}

<p>Alpine adds behaviour to HTML with attributes - and PAD writes that HTML. Both use braces,
and PAD reads every <code>{</code> of a template as the start of a tag, so the state of a
component comes from the page's PHP as JSON instead:</p>

{ignore}
<code><div x-data="{^profile}">                <!-- $profile = [ 'name' => 'Ada', 'likes' => 12 ] -->
  <h2 x-text="name"></h2>
  <button @click="likes++">♥ <span x-text="likes"></span></button>
</div></code>
{/ignore}

<p>The ^ sigil writes a field as JSON escaped for the attribute: a quote or a brace in a value
stays text. Three ways keep the braces apart:</p>

<ul>
  <li><b>State from PHP</b> - <code>x-data="{^field}"</code>, as above.</li>
  <li><b>Components in a file</b> - <code>Alpine.data('tabs', list => (...))</code> in a script of
      <code>www/</code>, called by name with PAD's data: <code>x-data="tabs({^tabs})"</code>.
      Load the page's scripts before Alpine, and Alpine with <code>defer</code>.</li>
  <li><b>A space after the brace</b> - <code>{ open: false }</code> is no PAD tag; fine for a short
      object.</li>
</ul>

<h2>Talking back</h2>

<p>A component asks the page that wrote it: <code>?page&amp;padFormat=json</code> answers what
the page's PHP names in <code>$padExpose</code> ({manual 'data_answers'/}). A post carries the
session's token in an <code>X-CSRF-Token</code> header, read from
<code><meta name="csrf-token" content="{csrf token/}"></code>. A form's rules can live in
PHP for both sides - <code>padValidateClient ( $rules )</code> for the browser,
<code>padValidate ( $rules )</code> for the post ({manual 'client_validation'/}) - and
<code>padSse()</code> streams events an <code>EventSource</code> in <code>x-init</code> turns into
state ({manual 'server_sent_events'/}).</p>

<p>The Alpine application shows each of these, with its template, PHP and script:
<a href="{$padHost}alpine/">alpine</a>.</p>

        want: <p>Total 42</p>

              apps/shop/_tests/checkout.pad:1:1  {assert $total eq 42/}
  2 tests, 1 failed</code>
{/ignore}

<h2>The answer</h2>

<ul>
  <li>the exact output of the page, trimmed;</li>
  <li><code>/a pattern/</code> matched over it - for output that changes, a date or a count;</li>
  <li><code>HTTP 500</code>, with an optional <code>/pattern/</code> on the next line, for a test that is meant to fail.</li>
</ul>

<p>A test without an answer counts against the run; <code>pad test shop --record</code> writes
the missing answers from what the pages render now, and never overwrites one.
<code>pad test --all</code> runs every application that has tests, and <code>./ci.sh</code>
does that as its <code>apptests</code> line.</p>

<h2>Asserts</h2>

<p>{tag 'assert'/} holds a page to a condition during a test run: false, and the test fails
with the condition and the message as its report. Anywhere else it is silent - the
condition is not even evaluated - so it can stay in the application's own pages. The switch
is <code>$padAssert</code>, which <code>pad test</code> turns on; this example turns it on in
its PHP:</p>

{example 'fragments/app_tests_1'/}

<h2>A test page</h2>

<p>It is a page like any other, rendered bare - without the application's wrappers - and no
URL reaches it. It can bring in a real page with <code>{page 'cart'/}</code>, or
include the page's own PHP and check the data it sets:</p>

{ignore}
<code>_tests/cart.php    <?php include APP . 'cart.php'; ?>

                   <p>Total {$total}</p>

{meta title='Charts'/}

<p>{tag 'chart'/} draws a chart as inline SVG on the server. There is no JavaScript, so the
chart prints, works where scripts do not run, and caches like any other output. A
<code>bar</code> chart puts columns on a zero baseline; a <code>line</code> chart draws a line
over a light wash with the last point marked.</p>

{example 'fragments/charts_1'/}

<p>The first word picks the kind of chart, after the job the data has to do:</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>Kind</th><th>Shows</th><th>Options</th></tr>
  <tr><td><code>line</code></td><td>change over time</td><td><code>label</code>, <code>value</code></td></tr>
  <tr><td><code>bar</code> (or <code>column</code>), <code>hbar</code></td><td>categories compared</td><td><code>label</code>, <code>value</code>, <code>stacked</code></td></tr>
  <tr><td><code>pie</code>, <code>donut</code></td><td>parts of a whole</td><td><code>label</code>, <code>value</code></td></tr>
  <tr><td><code>scatter</code>, <code>bubble</code></td><td>how two numbers relate</td><td><code>x</code>, <code>y</code>, <code>size</code>, <code>label</code>, <code>color</code>, <code>trend</code></td></tr>
  <tr><td><code>heatmap</code></td><td>patterns in a grid of two categories</td><td><code>x</code>, <code>y</code>, <code>value</code></td></tr>
  <tr><td><code>sankey</code></td><td>flows from one stage to the next</td><td><code>source</code>, <code>target</code>, <code>value</code></td></tr>
  <tr><td><code>network</code></td><td>connections</td><td><code>source</code>, <code>target</code>, <code>value</code>, <code>layout</code>, <code>arrows</code></td></tr>
  <tr><td><code>treemap</code>, <code>sunburst</code></td><td>a hierarchy, each part's share</td><td><code>label</code>, <code>value</code>, <code>levels</code></td></tr>
  <tr><td><code>sparkline</code></td><td>a shape the size of a word</td><td><code>label</code>, <code>value</code></td></tr>
</table>

<p>An option left out takes the first field that fits: a numeric one for a number, another one
for a name.</p>

<p>Every kind is a file of <code>pad/charts/types/</code>, and the files there are the kinds
there are - the <a href="../reference/">reference</a> lists them, each with the pages that draw
it. The kind can also be the name of the tag: <code>{chart:pie data='budget'/}</code>
is the chart type, the same chart as <code>{chart 'pie', data='budget'/}</code>, and
so is the bare <code>{pie data='budget'/}</code> when no tag, store, field or
sequence has the name.</p>

<h2>Where the numbers come from</h2>

<ul>
  <li><code>data='sales'</code> - a {tag 'data'/} store, a sequence store, an array of the page's PHP, or a <code>_data</code> file of that name.</li>
  <li><code>value=</code> names the field with the number, <code>label=</code> the field for the axis. Without them the first numeric field is the value and the first other field the label.</li>
  <li><code>sequence='fibonacci', rows=12</code> - the first terms of a sequence, for demo data straight away.</li>
</ul>

<h2>Several series</h2>

<p>A list of fields in <code>value=</code> draws a series each - bars side by side, or on top of
each other with <code>stacked</code>, or a line each, named at its end. A legend above the plot
names them in the fixed order of the colours; eight series at most.</p>

{example 'fragments/charts_3'/}

<h2>Horizontal bars</h2>

<p><code>hbar</code> lays the bars down, the names on the left - for long names or many
categories.</p>

{example 'fragments/charts_4'/}

<h2>Pie and donut</h2>

<p>Parts of a whole: only positive values count, clockwise from twelve o'clock, a legend with
each value and its share. Past eight parts the smallest are folded into one grey
<em>Other</em>. A donut shows the total in its middle.</p>

{example 'fragments/charts_5'/}

<h2>Scatter and bubble</h2>

<p>A dot per row on two numeric axes, <code>x=</code> and <code>y=</code>. <code>color=</code>
colours the dots by a field, <code>trend</code> draws the least-squares line. A bubble's
<code>size=</code> sets its area.</p>

{example 'fragments/charts_6'/}

<h2>Heatmap</h2>

<p>Two categories as columns (<code>x=</code>) and rows (<code>y=</code>), each cell coloured by
its value in seven steps of one hue, with the scale underneath.</p>

{example 'fragments/charts_7'/}

<h2>Sankey</h2>

<p>A row is a flow from <code>source=</code> to <code>target=</code>, as wide as its
<code>value=</code>. The columns follow the flows; flows that go round in a circle are an
error.</p>

{example 'fragments/charts_8'/}

<h2>Network</h2>

<p>A row is a link between two nodes. The default <code>layout='force'</code> pulls linked nodes
together - the same data always draws the same picture - and <code>layout='radial'</code> sets
them on a circle; <code>arrows</code> shows the direction.</p>

{example 'fragments/charts_9'/}

<h2>Treemap and sunburst</h2>

<p><code>levels=</code> lists the fields above the parts, the outermost first. A treemap nests
rectangles, a sunburst rings; the colour is that of the outermost level.</p>

{example 'fragments/charts_10'/}

<h2>Sparklines</h2>

<p>{tag 'sparkline'/} is a line chart the size of a word, without axes, to stand in a sentence
or a table cell.</p>

{example 'fragments/charts_2'/}

<h2>Accessible and themeable</h2>

<p>Every chart is an image to a screen reader (<code>role="img"</code>), named by its
<code>title=</code> and described by a list of its values. Every bar, point, slice, cell, flow
and node carries its own tooltip; a sparkline has none. The colours are CSS custom properties - <code>--pad-chart-series</code>,
<code>--pad-chart-text</code>, <code>--pad-chart-grid</code>, <code>--pad-chart-surface</code>,
the categorical <code>--pad-chart-1</code> to <code>--pad-chart-8</code>,
<code>--pad-chart-other</code> and the heatmap's <code>--pad-chart-heat-0</code> to
<code>--pad-chart-heat-6</code> - set on <code>.pad-chart</code>, and their defaults follow the
page's <code>color-scheme</code>, light or dark.</p>

{meta title='Clean URLs'/}

<p>A page is named in the query string - <code>/shop/?products/42</code> - or by the path
behind the application: <code>/shop/products/42</code>. The path is mapped onto the files,
and a file or directory whose name is a bracketed variable name stands for any one segment.

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>url</th><th>file</th><th>variables</th></tr>
  <tr><td><code>/shop/products/42</code></td><td><code>products/[id].pad</code></td><td><code>$id</code> is 42</td></tr>
  <tr><td><code>/shop/products/new</code></td><td><code>products/new.pad</code></td><td>a name of its own wins over a bracket</td></tr>
  <tr><td><code>/shop/blog/2026/hello-pad</code></td><td><code>blog/[year]/[slug].pad</code></td><td><code>$year</code> and <code>$slug</code></td></tr>
  <tr><td><code>/shop/docs/a/b</code></td><td><code>docs/[path+].pad</code></td><td><code>$path</code> is the rest, a/b</td></tr>
</table>

<p>The same names resolve wherever a page is named - here through
<code>{page}</code>, with <code>shop/products/[id].pad</code> and
<code>shop/blog/[year]/[slug].pad</code> beside the fragment:</p>

{example 'fragments/clean_urls_1'/}

<ul>
  <li><code>?products/42</code> resolves the same way, so the application runs on a server
      that routes no paths, and <code>/shop/index.php/products/42</code> works everywhere.
      A bracketed file is never reached by its own name.</li>
  <li>Every <code>?page</code> link keeps working: on a clean URL, a query string that starts
      with a bare page name - the relative <code>href="?about"</code> - names that page.</li>
  <li><code>$padCleanUrls = TRUE</code> in <code>_config/config.php</code> makes
      <code>$padGo</code> write <code>/shop/products/42</code>. Apache needs one line,
      <code>FallbackResource /shop/index.php</code>; <code>php -S</code> needs nothing.</li>
</ul>

{meta title='Barcodes and QR codes'/}

<p>{tag 'barcode'/} and {tag 'qr'/} write a code a scanner reads. It is encoded on the server and
drawn as inline SVG - no image library, no font, no remote service - so a page with a code prints,
caches and goes in an e-mail like any other. There are {echo php:count(padKinds('codes'))/}
symbologies, every one a file of <code>pad/codes/types/</code>. Twelve or thirteen digits are an
EAN-13, with the check digit added when it is left off; any other text is Code 128.</p>

{example 'fragments/codes_1'/}

<h2>Three ways to write one</h2>

<p><code>type=</code> on the tag names the symbology: <code>{barcode '0425261', type='upce'/}</code>.
The barcode type does the same, <code>{barcode:upce '0425261'/}</code>, and so does the
name alone, <code>{upce '0425261'/}</code>, as long as no tag, store, field or sequence
has that name. All three draw the same UPC-E.</p>

{example 'fragments/codes_2'/}

<h2>Products, parcels and labels</h2>

<p>The product codes - <code>ean13</code>, <code>ean8</code>, <code>upca</code> and
<code>upce</code> - check the digit a number ends in, or add it. Code 128 and Code 93 take printable
ASCII, Code 39 capital letters, digits and a few signs, with <code>check</code> for its check
symbol. <code>itf</code> and <code>itf14</code> are the digits of cartons, <code>codabar</code> the
code of libraries and blood banks, <code>msi</code> that of shelf labels.</p>

{example 'fragments/codes_3'/}

<h2>Two-dimensional codes</h2>

<p><code>qr</code> is the code of {tag 'qr'/}, which a phone camera reads; <code>datamatrix</code>
the square code of parts and medicine packs. Both take any text and choose the smallest symbol that
holds it, and both take <code>size=</code> in pixels in place of the height and scale of the bars.</p>

{example 'fragments/codes_4'/}

<ul>
  <li>The colours are black on white unless <code>color=</code> and <code>background=</code> say
  otherwise - fixed, whatever the page's colour scheme, as a scanner needs the contrast.</li>
  <li>The SVG is <code>role="img"</code> with the text, or <code>title=</code>, as its name.</li>
  <li>A wrong check digit, a character the symbology has no bars for or a text too long for it is
  an error under the strict check, and nothing is drawn.</li>
</ul>
