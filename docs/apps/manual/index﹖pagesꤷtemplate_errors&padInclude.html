An error names the place in the template where it stands - the file, the line and the column, the lines around it with a marker under the spot - next to the engine's own PHP file and line. This page, fragments/template_errors_typo.pad, misspells the $total its PHP sets:

<table>
  <tr>
    <td>{$totl | upper}</td>
  </tr>
</table>

and its error report says where:

apps/manual/fragments/template_errors_typo.pad line 3, column 10

  1 │ <table>
  2 │   <tr>
  3 │     <td>{$totl | upper}</td>
    │          ^^^^^
  4 │   </tr>
  5 │ </table>

did you mean $total?

What the report holds

  • The spot - the template file from the application root, its line and column, and the tag as written. The marker stands under what the message names: the field of {$totl | upper}, the function of {echo $x | uppr}.
  • Did you mean - for a field, a pipe function or a tag that does not exist, the nearest name there is: the fields visible where the error stands, the functions and tags of the engine, the application and _common.
  • Included by - an error in an _include snippet or in a page built by {page} also names the tag that brought it in.
  • Wrapped by - the _inits.pad files the page sits in.
  • An editor link - vscode://file/...:line:column opens the spot.

Where it shows

On the error page of a local request, in the JSON body a local tool gets (as template: file, line, column, tag, excerpt, suggest, included, wrapped, link), on the console, and at the end of the log line as file:line:column. A visitor from elsewhere still sees only the request id.

The build joins the _lib snippets, the _inits.pad and _exits.pad of every directory and the page into one text, and keeps a map of which part came from which file. When a spot cannot be traced back for certain - text a page's PHP printed, a tag's output read again as template - the report leaves the position out rather than guess.
