01 / Recommendation

Deepen the useful contracts.

Start with practical extensions to the existing owners. Introduce statistics as the first new subsystem if one shared analysis result can serve tables, charts and formulas. Follow with graphs when a dependency-analysis consumer exists. Keep the other three new-owner ideas conditional.

BUILD FIRST

Everyday application gaps

Unit dimensions, hierarchical tables, domain-aware inputs and rules, unified diffs, error summaries and configuration highlighters.

EXTRACT CAREFULLY

Reusable computations

Statistics, graph algorithms and potentially nested-schema validation. Preserve existing contracts while sharing their internals.

REQUIRE A USE CASE

More names in mature catalogs

Provider aliases, theme variants and motion effects offer less value than clear capabilities, consistent behavior and documented limits.

04 / New owners

Five possible new subsystems.

Proposed names and helper signatures are design sketches, not existing APIs. Start helper-first through the central helper-kind registry; introduce template namespaces only when they have a clear execution contract. The suggested directories do not exist in the inspected tree.

P1 · FirstL effort · helper-first

statistics/ Reusable numeric analysis

Candidate kinds: describe, quantiles, histogram, regression, outliers

The best new-owner candidate. PAD already calculates median/averages in sequences, quantiles in chart internals and statistics in formulas. What is missing from the subsystem registry is a coherent, renderer-independent batch-analysis contract with explicit missing-value policy and structured results.

Proposed contract. Proposed helper: padStats(kind, rows, options). Return named values plus count/missing counts and method metadata. Start with describe and quantiles, then shared histogram bins, ordinary least-squares regression and an explicitly named outlier rule. No automatic statistical interpretation or causal claims.

Ownership boundary. Sampling stays in fakes/distributions; SVG stays in charts; spreadsheet coercion stays in tables/formulas. Extract proven numeric kernels, preserving existing behavior. A second average() implementation alone would not justify this owner.

Adoption gate. One report should feed the same analysis result to table:standard and a chart. Use independent reference values, degenerate inputs, non-finite rejection, pairwise missing rules and large-magnitude numeric tests.

Source basispad/subs/charts/_lib/distribution.phppad/subs/tables/formulas/types/correl.phppad/sequence/actions/types/median.phpdocs/subsystems/distributions/README.md
P2 · NextL effort · helper-first

graphs/ Algorithms over explicit nodes and edges

Candidate kinds: toposort, components, shortestpath, criticalpath

A strong second candidate for dependency analysis, impact reports and planning. Existing network/Gantt charts and diagrams visualize relationships; a separate helper can compute reusable results without generating markup.

Proposed contract. Proposed helper: padGraph(kind, nodes, edges, options). Require stable IDs, declare directedness and weight semantics, and return structured results. Start with topological order and connected components; add shortest paths with an explicit weight policy, then critical paths over DAG durations.

Ownership boundary. Keep drawing in charts/diagrams. Critical path is numeric dependency analysis, not a project scheduler with calendars or resource leveling. Reuse graph normalization across consumers; do not extract force-layout internals blindly.

Adoption gate. Analyze one task DAG, return a useful cycle witness on invalid input, and highlight resulting nodes in an existing chart. Verify tiny graphs exhaustively, disconnected nodes, duplicate IDs, ties, unreachable targets and bounded work.

Source basispad/subs/charts/_lib/network.phppad/subs/charts/_lib/gantt.phppad/subs/charts/timelines/README.mdpad/subs/diagrams/_lib/diagram.php
P2 · NextL effort · helper-first

schemas/ Shared validation of nested data contracts

Candidate kinds: jsonschema, record, rowset

A conditional extraction, not a greenfield validator. AI already has a bounded JSON Schema subset and inputs already have scalar/cross-field rules. Imports, AI responses and structured forms could share a tree-validation result contract.

Proposed contract. Proposed helper: padSchema(kind, value, schema, options) returns valid plus issues with stable paths, codes and messages. Jsonschema initially means the explicitly documented current subset. Record and rowset are lightweight adapters to the same validation core, only if consumers need those conventions.

Ownership boundary. Do not claim full JSON Schema compliance or silently coerce values. Preserve AI response/error/cache behavior and form-rule behavior. Keep no automatic remote references. Create this owner only after a second real consumer uses the extracted validator.

Adoption gate. Validate the same nested payload at import and AI boundaries. Check absent versus null, object versus list, typed enums, unknown keywords, depth limits and deterministic issue paths. Existing AI fixtures must remain unchanged.

Source basispad/subs/ai/_lib/json.phppad/subs/ai/README.mdpad/subs/inputs/rules/types/required_if.phppad/subs/formats/_lib/format.php
P3 · ExploreL effort · helper-first

textanalysis/ Deterministic text and corpus measurements

Candidate kinds: counts, ngrams, similarity

Useful for document QA and duplicate-content reports if several applications need it. Start with token/paragraph counts, bounded n-gram frequencies and a named similarity measure, not a loosely defined “text intelligence” layer.

Proposed contract. Proposed helper: padTextAnalysis(kind, textOrRows, options). Declare normalization, tokenization, locale and size limits. Similarity must name its metric and return a score with enough metadata to interpret it. Reading-time estimates can be an option on counts with an explicit rate.

Ownership boundary. Simple string transforms stay in pad/functions and locale behavior stays in pad/lib/locale.php. Search retains indexing/ranking; diffs retain edit records. Share tokenization deliberately without changing search caches or phrase positions.

Adoption gate. A duplicate-document report consuming local strings. Verify Unicode normalization, grapheme handling, punctuation, empty documents, symmetry where promised and pairwise comparison limits. If only counts is needed, implement a helper instead of a new owner.

Source basispad/subs/search/_lib/search.phppad/functions/_lib/grapheme.phppad/lib/locale.phppad/subs/diffs/README.md
P3 · ExploreL effort · helper-first

constraints/ Bounded combinatorial solving

Candidate kinds: exactcover, matching, assignment

An exploratory candidate for puzzle generation and small allocation problems. The important reusable product is a solver result and work-limit contract, not another visual component.

Proposed contract. Proposed helper: padSolve(kind, problem, options) returns a solution and a distinct status such as solved, infeasible or limit. Start with one algorithm only after two consumers exist. Keep node/step budgets, deterministic tie-breaking and cancellation explicit.

Ownership boundary. Games retain their own rules and interfaces; calendars retain display and recurrence behavior. Matching and minimum-cost assignment need separate, documented input semantics. This is not an invitation to move application workflows or queue execution into subsystems.

Adoption gate. Use a tiny exact-cover puzzle plus an independent allocation example. Exhaustively enumerate small problems as an oracle; distinguish exhausted search from proven infeasibility. Defer if no application needs the generality.

Source basispad/subs/games/_lib/sudoku.phppad/subs/games/_lib/game.phppad/subs/calendars/README.md

06 / Integration requirements

A type file is only the registration step.

  1. Define the contract first. Record inputs, output shape, missing/empty behavior, errors, strict/lenient behavior where applicable, work limits and ownership. Provider/data registries must not be mixed with view registries.
  2. Use existing registration and shared helpers. Add kinds to their current directory. New public/helper families require central registry/dispatch integration; never imply that every helper family supports a prefixed template tag.
  3. Make the feature discoverable. Update the tags catalog, subsystem catalog, examples, reference/editor data and applicable documentation. Preserve the current explicit namespaces and nested ownership.
  4. Preserve both execution paths. New charts need PHP/browser SVG parity; sound recipes need sample parity; form rules need equivalent server/browser outcomes; interactive widgets need keyboard/native fallback, multi-instance and fragment lifecycle checks.
  5. Test meaning, not just markup. Use independent numeric/codec oracles, known recurrence results, print geometry and protocol fixtures. Add malformed/limit cases. Keep externally sourced datasets and algorithms versioned and attributed.
  6. Gate the implementation when it exists. Run focused subsystem fixtures and the relevant integration checks, then the repository gate. This report changes no runtime behavior and does not constitute a framework regression pass.
