Independent framework code audit

The PAD engine, read line by line

A deep audit of the PHP that is PAD — the template engine, expression evaluator, tag library, data and database layers, request lifecycle and the sequence subsystem. Every file was read; every finding is traced to source, and the ones that matter most were reproduced on a running server. Fifteen years of careful, honest, well-commented code, carrying a security model that one design decision quietly turns inside out.

Audited 1 October 2026 · commit f641bde20 · PHP 8.5.10 (Apache) / 8.5.11 (CLI) · Apache 2.4.68 · pad/ only — 1,014 files, 26,752 lines

Verdict
Needs work

The craftsmanship is real: zero syntax errors across the tree, a fail-safe error ladder, contained file I/O, correct maths in nearly every sequence generator, and a header comment on nearly every file that tells the truth about what it does. But PAD promotes request parameters into the template namespace and then re-parses rendered values as template code, and a bare word resolves to a PHP function call with no allow-list. Those facts combine into remote code execution — demonstrated live on this machine. The default configuration also writes database passwords and raw request bodies into a web-reachable directory, request values silently override and persist session state, and the declarative select builder uses the wrong escaper on its way into SQL. Not safe to expose to untrusted input or untrusted networks until the template/data trust boundary, the session and SQL ownership rules, and the error-dump defaults are fixed.

What the audit found

The audit converges on five structural problems: field values re-parsed into template code, request parameters taking precedence over session state, PAD's own delimiter escaping used in place of SQL escaping, a page cache that is blind to identity and answers before the application initialises, and a "local" classifier that trusts the Host header. The code-execution path was demonstrated on a live server.

Around those sit a long tail of ordinary defects — the expression evaluator's wrong arithmetic and boolean logic, the sequence runner's filtering and position bugs, comment and comparison parsing, name validation that never rejects, HTTP caching and negotiation errors, data conversion that corrupts text — and a set of maintainability hazards that follow from the include-driven, globally-stateful architecture.

Severity is an engineering priority, not a CVSS score. Preconditions are stated in each finding: the page cache is High only when $padCache is on (off by default), the track SQL interpolation only under the DB-track info mode, the local-dump disclosure only where the Host header or a loopback proxy satisfies the classifier.

Claims marked verified live were reproduced against the running server on this machine; the rest are certain from reading the code or were checked with isolated PHP snippets. No framework file was modified during the audit.

Scope & method

How the engine was read

Scope was the framework itself: everything under pad/, plus the two entry points www/pad.php and home/home.php. Applications under apps/ and the regression runner were read only where they show how the engine behaves. The tree was split into six subsystem reviews — request lifecycle; template engine core; expression evaluator; data & I/O; tags, info & events; sequences — each reading every file in its slice and following calls into the shared library as needed.

Behaviour was confirmed four ways: reading the code; running isolated copies of pure functions under PHP 8.5; building temporary applications with a separate DATA directory for HTTP fixtures (identity variants, failed transport, protocol headers, conditional requests) and fetching crafted pages from the live server; and replaying the framework's own test corpus — 987 enumerated cases over HTTP, of which 986 pass — plus 1,395 independent sequence reference checks. Temporary files were removed afterward; the working tree is clean at f641bde20.

Checked and found sound

Things that were tested on suspicion and held up — stated so the findings below are read at their true size.

  • Page selection: the page allow-list rejects traversal syntax and underscore-prefixed segments; no page-name bypass was established. (The tag/type-name validator is a different function and is broken — H6.)
  • Fast-link unserialize: sits behind an unconditional return in inits/fast.php; dormant, not a live deserialization path.
  • x-prefixed raw SQL substitution in db(): a deliberate, trust-sensitive escape hatch; its existence alone is not evidence that request input reaches it.
  • Script arguments go through escapeshellarg; only the executable path is unquoted (a hardening gap, not a demonstrated request-to-shell path).
  • Default field sanitization does escape HTML markup — <b>x</b> comes out encoded. It simply does not escape PAD's own delimiters.
  • Sequence generators: 76 of 77 spot-checked produce correct terms, and 1,395 term and predicate checks pass. The sequence findings are about the runner, not the maths.
  • Nested-pass state: sandbox, reporting level, engine level and a temporary data store all restore correctly on normal return.

The central issue: a trust boundary that isn't there

PAD's documentation states the rule plainly: a form field arrives in a template as {$fieldname} "with no plumbing in between" (inits/parms.php). POST, GET and cookie values are copied into PHP globals for any name that isn't pad-prefixed. That is the framework working as designed.

The engine renders a value by splicing it back into the buffer it is still scanning (lib/level.php:129-137, padLevel()), and the scanner then re-reads from the start of that buffer. So a { that arrived inside a field's value is parsed as the opening of a tag. And the type resolver, at the end of its lookup chain, treats a bare word as a PHP function if one exists:

// pad/lib/type.php:39-42  (and the prefixed form at :89-95)
elseif ( defined         ( $item ) ) return 'constant';
elseif ( padDataFileName ( $item ) ) return 'local';
elseif ( padScriptCheck  ( $item ) ) return 'script';
elseif ( function_exists ( $item ) ) return 'php';   // ← any PHP function

// pad/types/php.php:16 · pad/eval/parms/php.php:12
return call_user_func_array ( $padTag [$pad], $padUserFunc );   // no allow-list

Chaining those facts gives remote code execution. Reproduced on the running server through a field value supplied in the query string, against a page whose PHP does nothing but $value = $_GET['input'] ?? '' and whose template is {$value}:

?index&input={echo 7 * 7}            → 49
?index&input={echo php:chr(65)}      → A
?index&input={php:getcwd}            → /Users/herbert/pad/apps/test
?index&input={php:strrev $r}&r=…      → runs strrev on another field's value
?index&input={object:padSqlPassword} → reads the engine's own DB password global

The default sanitize step does not stop this: it encodes <, >, & and quotes — <b>x</b> comes out escaped — but not braces. The strict syntax check does not stop it either: the value is valid PAD. The raw {!x} form instead fails the request with a 500 ("No close } found") because it escapes } but not {. And even if the padLevel re-scan were fixed tomorrow, three other paths splice untrusted text into template source and run it: {page app=x ajax=false} returns a fetched body unescaped (start/pad/pageApp.php:22), padTagAsFunction compiles a piped value as source (lib/execute.php:74-84), and curl data sniffed as a list is run through the evaluator (data/list.php). The fix is architectural — see Remediation.

Template injection → RCE

Rendered values are re-parsed as template code, and a bare tag name can be any PHP functionverified live

lib/level.php:129-137 · lib/type.php:39-42,89-95 · types/php.php:10,16 · eval/parms/php.php:12 · eval/single/object.php:11 · inits/parms.php:13-16

The full chain is described above. Request parameters become template variables; padLevel() splices a rendered value into the live scan buffer without escaping {/}; the type resolver falls through to function_exists(); types/php.php calls it with call_user_func_array and no allow-list. object: additionally returns any global (including $padSqlPassword) and constant: any constant. HTML escaping alone does not prevent it: this crosses the data-to-code boundary even when the application author wrote a fixed, trusted template.

Other sink sites that re-enter the scanner unescaped: the {!x}, {#x} and {&x} variable forms (level/var.php:55-56); a child level's result merged into its parent and re-scanned from offset 0 (level/end.php:71); every tag's return value and echoed output merged into $padContent (level/go.php:24-49), which also obeys @else@/@content@/@start@ markers carried in data; the ternary branch value; opening/closing-pipe results; and open=/close=/glue=/quote= option values.

Fix: make ordinary field insertion literal to the parser, independently of HTML escaping — escape braces (the existing padEscape) on every value that re-enters the scan buffer, or run it as data rather than source. Drop the function_exists / defined / script fallbacks so php:, constant: and script: must be written explicitly, and gate php: behind a configurable allow-list. Keep explicit, opt-in code evaluation (padCode()) for trusted template strings. Review every data-to-source splice together so a fix in one form does not just move the hole to another.
Critical
SQL injection

Select-subsystem WHERE values are brace-escaped, never SQL-escapedverified live

lib/select.php:259-269, 179-180 · lib/encoding.php:72-77

The declarative select builds its automatic WHERE as $where .= $add . padEscape($value) . "'"; — but padEscape only swaps { } | = , @ for entities. It does not touch ' or \, and the result goes to db($sql) without the placeholder mechanism. The value is $GLOBALS[$field] for a key bound on the tag — the documented {users $id=$id} pattern, where $id is a request parameter — or an outer row's value. A single apostrophe ends the string literal and the visitor controls the rest of the condition.

Builder output: padSelectWhereAdd($w, 'name', "O'Reilly") → where `name` = 'O'Reilly'; a value containing @ → 'a&at;b.example', so ordinary e-mail addresses never match.

Two correctness bugs ride along: a legitimate value containing ,, = or @ is rewritten to an entity and never matches; and page=/rows=/where=/order=/group=/having= are spliced into SQL raw, stopped only by a non-numeric PHP warning under the default error action.

Fix: use prepared statements on the application connection, or at minimum mysqli_real_escape_string on the app connection and cast page/rows to int. Stop running values through padEscape on their way into SQL; keep identifier validation separate.

SQL injection / API

db() placeholders are escaped but never quoted; the documented numeric form is injectable

lib/db.php:68-76 · docs/DATABASE.md:13,28,182-184

str_replace('{'.$i.'}', mysqli_real_escape_string($c,$replace), $sql) escapes the value but does not quote it, and the docs tell authors to write WHERE id={0} unquoted for numbers. Info disclosure

padLocal() trusts the Host header, exposing the full error dump to remote visitors

error/boot.php:184-198 · lib/dump.php:59,76-99,407-413 · error/claude.php:68-81

padLocal() returns true when either REMOTE_ADDR or $_SERVER['SERVER_NAME'] matches localhost/127.0.0.1/::1 — and under Apache's default UseCanonicalName Off, SERVER_NAME is filled from the client's Host header; behind a same-box reverse proxy every visitor's address is loopback. A developer hostname, penguin.linux.test, is hard-coded in the allow-list. A visitor who passes the check and triggers any error gets padDumpLocal instead of Error: <id> — the Configuration block with $padSqlPassword and $padSqlPadPassword in clear, plus request variables, cookies and headers. Reproduction: HTTP fixture with REMOTE_ADDR = 203.0.113.9, SERVER_NAME = localhost, a synthetic sentinel in an application value → HTTP 500 with the sentinel present in the 11,574-byte response body. The exposure is deployment-dependent; the classifier is the defect.

Unsafe default

Error dumps are on by default and write secrets and raw request bodies into a web-reachable directory

config/config.php:19-20 · lib/dump.php:286-292,520-543 · error/types/pad.php:58-59 · www/DATA (symlink)

With $padErrorReport = TRUE (the default), every handled error — including a remote visitor's — writes a directory under DATA/dumps/<app>/<page>/ containing globals.html (print_r($GLOBALS), so DB passwords, $_SESSION, $_COOKIE), input.txt (the raw php://input — a failed-login POST stores the password), request/header captures and phpinfo(). Files are 0644, directories 0755, with no rotation. In this checkout www/DATA is a symlink into the docroot, and the stock Debian Apache config serves that tree with Options Indexes. Stored error reports retain the sensitive material even when the browser receives only an error id.

Fix: default the disk dump off outside development; keep DATA out of the docroot; redact credentials and drop $_SESSION/$_COOKIE/php://input; use 0700/0600; cap the number of dumps and define retention.

Session integrity

Request input overrides session variables and is written back into the sessionverified live

inits/parms.php:15-24 · lib/parms.php:13-16 · lib/session.php:72-81

POST, GET and cookie are imported first; the session is imported last and only fills names not already set (if (!isset($GLOBALS[$field]))). At exit, padCloseSessionTry writes every declared $padSessionVars name back: $_SESSION[$var] = $GLOBALS[$var]. So for any app that uses session variables, ?user=… (or a cookie, or a cross-site POST) shadows the stored value for the request and persists it — the one source the server controls has the lowest priority. The file's own comment, suggesting _inits.php runs first, does not match inits/inits.php: request import precedes the application build. The trim() applied to session values breaks them: a NULL raises a deprecation (500 under pad), an object throws, ints/bools become strings. No session_regenerate_id or strict mode anywhere.

Reproduction: fixture with $padSessionVars = ['role'] and no assignment to $role anywhere. GET ?index&role=admin → role=admin, new PHPSESSID; GET ?index with that cookie and no parameter → still role=admin.
Fix: keep request values and server session state in separate stores; load the session before request import and never let request sources fill declared session names; write back only values the app assigned; copy non-string session values without trimming; enable session.use_strict_mode.

inits/parms.php:15-17 · lib/valid.php:46-54

Correctness

The expression evaluator computes wrong answers silently — even with the strict check onverified live

lib/eval/const.php:17-24 · lib/eval/double.php:18-24 · lib/eval/parse.php:79-82,372-389 · eval/type/parms.php:12-22

Four independent parser faults make arithmetic and conditions wrong with no error raised:

  • Precedence: each operator is its own level, walked one at a time, so left-to-right breaks. Verified on the server: {echo 10 - 2 + 3} → 5, {echo 8 / 2 * 2} → 2 (2 ** 3 ** 2 → 64, 10 % 3 * 2 → 4).
  • Adjacent operators: a binary operator followed by !/not/- is applied "alone" and the rest concatenated as text. Verified: {if $one eq 2 and ! $zero} renders the true branch; {echo 5 -3} → 5-3.
  • Unspaced comparisons: <, >, = aren't tokenized, so $x<=3 becomes a string that is always truthy. Verified: {if $x<=3} with $x=5 renders the true branch.
  • Function without parens swallows the next token even when it's an operator: {if now gt 5} is always true (verified).

These hit totals, discounts, pagination and access conditions. The regression suite's one arithmetic case (2 + 3 * 4) happens to survive because that particular order is right — which is also why the 986-of-987 framework replay passes: the baselines encode current behaviour.

Fix: rebuild the evaluator around precedence groups with a prefix-unary pass; tokenize the symbol comparisons; only take a bare function's argument when the next token is a value. Add reference-valued tests, not just shape tests.
High
Correctness / DoS

The sequence runner corrupts recurrences, miscounts positions, and can be made to loop foreververified live

sequence/build/one.php:39-64 · sequence/inits/limits.php:11-18 · sequence/sequence/sequence.php:34-36 · sequence/inits/clear.php:8-11

The generators themselves are almost all correct — 76 of 77 checked against references are right, and 1,395 independent term and predicate checks all pass. The damage is in the code that drives them:

  • Recurrences break under any filter or play — a term is added to history only after every filter passes, so a rejected term leaves a hole and fibonacci/go.php reads missing keys. Verified: {sequence fibonacci, rows=5, square} → 1 1 2 3 5 (square silently dropped, leading 0 lost).
  • Position lookups return the wrong term — the 10,000-candidate try limit still applies and no completeness check runs. Verified: sequence:fibonacci(100) → 7540113804746346429 (that is F(92), not F(100)); sequence:prime(1230) → 9973.
  • Actions on a literal array see only the first 10 values — the rows limit isn't lifted. Verified: sequence:sum([1…12]) → empty (the array path collapses).
  • DoS: stop=/to=/pull= remove both safety limits, and stop is tested only on accepted terms, so a run that never reaches it loops until max_execution_time or memory exhaustion. Request fields are template variables, so a template that forwards one into stop= is a denial-of-service route.
  • No isolation — a sequence called from an expression runs clear.php, which unsets every pq* global, wiping the tag-driven run that invoked it; {sequence 5, make, eval='sequence:square(@)'} recurses into a fatal error.
Fix: append each term to history before filtering; keep a hard candidate ceiling even with stop/to; report (or fail) when a position build can't reach n; isolate the expression entry's state instead of clearing the globals.

Cache / authorization

The page cache is keyed on the URI alone and answers before the application initialisesverified live

cache/inits.php:20-48,75-82 · cache/hit.php:9-12 · cache/exits.php:10-24 · inits/inits.php:32-35

When $padCache is on (off by default), the key is padMD5($_SERVER['REQUEST_URI']) — no host, scheme, cookie, session or application component. The lookup runs at inits/inits.php:32, before request promotion (:34) and the application build (:35), and a hit includes exits/output.php and ends the request. Reproduction: file cache, 60 s, gzip off; page PHP $value = $_COOKIE['viewer'] ?? 'anonymous'. GET ?index with Cookie: viewer=Alice → Alice; the same URL with Cookie: viewer=Bob → Alice. Both HTTP 200, same ETag, Cache-Control: private.
Fix: restrict shared full-page caching to explicitly public, identity-independent responses; run access checks before cache delivery; partition keys by app, host and intentional variants; bypass requests carrying cookies, a session or Authorization unless an explicit identity-aware policy is configured; add expiry to the file/db backends.

HTTP headers

Conditional requests and encoding negotiation are wrong in several waysverified live

cache/inits.php:50-72 · inits/client.php:11-13 · lib/output.php:38-43,117-129,168-175 · cache/types/file.php:18-22

  • Cross-URL 304: the If-None-Match branch tests the client's ETag for existence and freshness in the global ETag store before ever looking up this URL. Reproduced: warm ?index, send its ETag to ?second → HTTP 304, empty body, index's ETag echoed — the client keeps the wrong page.
  • Date validation against the cutoff, not the representation: If-Modified-Since answers 304 when the client date is newer than the freshness cutoff, even if the cached entry is newer than the client's copy (warm at 03:33:45, send IMS 03:33:15 → 304). No Last-Modified is ever sent.
  • Negotiation: $padClientGzip is a substring test for gzip, so Accept-Encoding: gzip;q=0 still receives a gzip body (observed: 1f8b08… with no Vary). If-None-Match is read as substr(…,1,22), so W/"…", lists and * never match.
  • Vary: Content-Encoding names a response header; it should be Accept-Encoding, and the uncached gzip path sends no Vary at all. The same strong ETag is sent for the gzip and identity bodies.
  • Unvalidated ETag as a key: the client-supplied ETag is used as a backend key and, in the file backend, as a file path (file_exists($padCacheFile."etag/$etag")). Cookies are set before the cache lookup, so cached public responses can carry one visitor's Set-Cookie to others.
Fix: resolve the URL/variant first and compare validators only against that representation; parse If-None-Match and Accept-Encoding quality values per RFC 9110; send Vary: Accept-Encoding on every path that can vary; give the gzip variant its own ETag; validate the ETag against a fixed shape; don't set cookies on public responses.

cache/exits.php:19-22 · cache/hit.php:9-12 · lib/output.php:117-129

The backends store body, ETag and age — not response metadata. A hit skips page PHP and calls exits/output.php, which sends the default/configured $padContentType. The admission loop is while ( $queue and count($flying) < $window ) inside while ( $queue or $flying ). Low & informational — ~35

Lower-severity correctness & hardening

  • Identity cookies: padSesID taken from $_REQUEST unvalidated, stored in a 10-year cookie with no HttpOnly/SameSite/Secure; a newline in it makes header() 500 the victim for the cookie's life. IDs also travel in URLs.
  • Visitor-flippable switches: ?padInclude strips all wrappers; ?padReference writes xref files under DATA; ?padExamples bypasses the cache. (?padInfo=trace is correctly not reachable — CLAUDE.md's tip is stale.)
  • HTTP status: a missing page is a 500, not a 404; the raw page name is logged unsanitized (log forging); pages can't set their own status; errors under exit/log/ignore can end as an empty 200.
  • Router disagreement: {page}/{get}/{redirect} checks miss .html pages and directory indexes and search from the wrong root.
  • Path helpers: padPath() returns / for a root page (substr(APP, -1); verified live) — nothing reads $padPath, which bounds it. A relative path means "under pad/" to padFileGet (file.php:28-31) but "under DATA/" to padFilePut (file.php:55-56), so a put followed by a get of the same relative name reads a different file.
  • Tag targets: {increment}/{decrement} don't validate the name (can touch engine globals); {count} throws on a scalar/missing global; an empty {switch} divides by zero under the lenient walk.
  • Direct /pad.php with www as docroot makes $padApp empty and the whole apps/ tree the application.
  • dump-action reset unset()s only a global alias, so only the first error per request is fully dumped; the myTidy sanitize step is a no-op ((int)"FILTER_FLAG_x"); the db cache backend defaults don't match the shipped schema.

More evaluator & sequence detail

  • Comparisons use loose ==; bare true/false/null resolve to PHP constants ($name eq true is true for "no").
  • Number coercion: 1e-3 * 1000 → 0, 'abc' + 1 → 1, / 0 is an uncaught error, a % pipe and a %-leading printf format collide.
  • slashes and ignore are documented as making values safe for SQL / JS / HTML attributes where they do not; {echo … | ignore} in an attribute can break out.
  • The fast function-name path skips name validation; date() throws on date strings; like() misses across newlines; the eval trace is never reset.
  • Sequences: the tag-form try limit cuts a run short with no notice; randomly without to= samples up to PHP_INT_MAX; name= on a loop silently changes what a bare {pull}/{resume} reads; several unchecked-index crashes; EXPLAIN.md has wrong worked examples.

Informational — dead code & systemic shape

Dead or dormant: padValidFile, padValidatePath, padValidType and padPath()'s result are never used; padFastLink() is documented and still inserts DB rows, but its resolver (inits/fast.php) returns unconditionally, so the unserialize behind it is dormant, not live; inits/database.php and start/sandbox.php are never included; most of events/ never fires and events/stats.php reads keys the stats writer never stores; tags/foo.php and tags/_go/data.php are stubs; in sequences, 186 playSingle/playDouble/readme markers and 211 of 212 flags/ files are never read.

Systemic: control flow is include statements over ~70 parallel per-level global arrays, plus ~360 include-as-function files in sequences — so cleanup, variable lifetime and execution order are part of each fragment's effective API. Correctness depends on hand-maintained lists of global names and prefix filters spread across several files (inits/const.php, lib/checks.php, lib/valid.php), and the list is already out of date (it omits padWhileRound, padOptionsAppStartCall). A restart is a nested include, so abandoned runs stay on the stack; the app's _config/config.php is included two or three times per request (so it can't define functions); and the sequence pipeline exists in four hand-listed copies that have drifted apart — the direct source of three of the H9 bugs. Because several regression baselines were captured from buggy output, the suite now actively protects those bugs.

Test-suite observations

This is not a judgement of the regression suite — the August 2026 test-system audit (www/audit.html) covers that — but the audit touched it in four ways:

  • A full gate run did not complete. ./ci.sh http://127.0.0.1/pad/ exited 2; the trigger answered HTTP 500 with "Maximum execution time of 60 seconds exceeded" at pad/lib/curl.php:386 (curl_multi_select), reproducible outside the replay. Its exact environmental cause was not established and stale result files from an older commit were excluded from the pass claims. The August audit recorded five consecutive green runs at 7–9 s each, so the timeout may be environmental — but M27 shows the multi-curl loop has at least one known way to never return.
  • Fresh suite results before the timeout: Pages 83 pages / 210 tests / 0 failed; Errors 96/96/0; Common 25/25/5 failed — all five become exact matches when 127.0.0.1 is replaced by localhost, i.e. environment-sensitive baselines, not framework defects.
  • Independent framework replay: 987 enumerated cases in 15 groups over HTTP, four client workers; 986 pass, one harness case times out. Sequence reference checks: 1,395/1,395 pass (13 term functions at indices 1–30, five predicates over 0–200). These agree with the per-generator spot-checks (76/77 correct) — and they also show the limits of shape-based baselines: H8's wrong arithmetic and H9's wrong positions pass every existing test because the expected answers were recorded from the current output.
  • Baselines that encode bugs: keepRemoveFlag/substract.txt, divide.txt and loop.txt record the outputs of M13 and M14 as correct; regression/info asserts the XML report file grew (M12).

The testing recommendation that follows: do not merely record the current output as the new expected answer. The highest-value tests assert that untrusted text is inert, that identity does not cross requests, that a quoted SQL value remains a value, that failures restore process state — and that 10 - 2 + 3 is 11.

What is genuinely strong

It holds together

All 1,014 files are syntactically clean on PHP 8.5. The error handling is a layered, fail-safe ladder: the boot net is armed before config and lib load, every reporting step is wrapped and guarded against re-entry, and every path ends at padExit(500) — a failure while reporting a failure doesn't loop or half-print. Remote visitors see only Error: <request id>, with display_errors forced off at boot.

Page routing and file I/O are contained

The page allow-list is restrictive: it rejects traversal syntax and underscore-prefixed segments, and no bypass was established. Engine and app disk access funnels through padFileGet/padFilePut with a single shared guard that rejects .., // and control characters, and writes are confined to DATA. padDeleteDataDir resolves with realpath, checks the DATA prefix and refuses to follow symlinks. (The gap is the tag-name lookups that bypass this — H6 — not the file layer itself.)

The data parsers are safe

XML is parsed without LIBXML_NOENT/DTDLOAD, so external entities don't expand (no XXE); YAML won't decode PHP objects; curl never disables TLS verification and bounds its timeouts; script arguments go through escapeshellarg. db() uses the connection-aware mysqli_real_escape_string, sets TRADITIONAL sql_mode and logs every statement centrally. Default field sanitization does escape HTML markup — the control probe confirms it.

The strict check earns its keep

With $padCheckSyntax on, long-silent failures — unclosed pairs, empty conditions, duplicate {when}, unread options, missing store names, undefined fields — become precise, located messages in the template's own terms, with a deliberate lenient fallback. Runaway loops are bounded (while-round limit, nesting depth limit, always-advancing pair search), and shadowed globals are saved and restored by the scope model: a nested-state probe confirms sandbox, reporting level, engine level and a temporary store all restore correctly on normal return.

The maths is right

76 of 77 sequence generators spot-checked are correct against independent references (Catalan through C(35), the lucky sieve, Golomb and Newman-Conway recurrences), and 1,395 term and predicate checks all pass. All 51 lookup tables match their generators; integer overflow is handled in one place so sequences stop cleanly rather than printing imprecise floats; and the 375,354-row OEIS store is opened read-only with prepared statements and a per-sequence cache.

It documents itself honestly

Nearly every file opens with a precise header explaining its contract — and, remarkably, many record the bugs they once had and the reasoning behind the fix, and flag their own dormant code. That candour is what made a review of an include-driven, globally-stateful engine of this size tractable at all.

Remediation, in order

In priority order:

  1. Separate literal data from executable template input (C1). Establish a literal insertion path first: escape braces on every value spliced back into the scan buffer (the padEscape helper already exists) and apply it to the other source-splicing sinks — pageApp, padTagAsFunction, sniffed curl data. Review every user-data output form together so a fix in one form does not simply move the vulnerability to another. In the type resolver, drop the function_exists/defined/script fallbacks so those prefixes must be written explicitly, and gate php: behind a configurable allow-list. Preserve deliberate trusted-code features such as padCode().
  2. Define ownership of request, session and database values (C2, H1, H2, H5, H7). Remove implicit writes into trusted session state; promote only declared request names. Move the select subsystem and db() to prepared statements, or quote and connection-escape every interpolated value including numerics and the track session queries; cast pagination to int.
  3. Make cache eligibility and diagnostic exposure explicit (H3, H4, H10). Public-only cache policy with access checks before delivery and keys partitioned by app/host; base "local" on REMOTE_ADDR behind an off-by-default switch; default the disk dumps off; keep DATA out of the docroot; redact credentials, session values and request bodies from any dump; define retention.
  4. Validate names and hosts (H6, M1, M2, M3, M19). Repair padValid, reject / and . wherever a name becomes a path, escapeshellarg the script exec, allow-list {output} and sequence build=/action=, contain {files}/{dir}, and build cross-app URLs from a configured base rather than the Host header.
  5. Repair the evaluator and sequence runner (H8, H9, M13, M14, M20, M28). Rebuild expression evaluation around precedence groups with a prefix-unary pass and real comparison tokens; in sequences, record history before filtering, keep a hard candidate ceiling, isolate the expression entry, fix pqArray's cardinality and the zero-ending range. Add tests that compare against independent reference values, and regenerate the baselines that currently encode wrong output.
  6. Repair representation and error lifecycle handling (M7, M9, M22, M23, M26, M27). URL-specific validators, cached response metadata, finally-based cleanup, honoured q=0, correct Vary, case-insensitive header parsing, a validated curl-multi window, and a restart guard that actually stops.
  7. Then the remaining Medium set — comment parsing, == as assignment, Tidy defaults, multibyte strings, CSV, the XML report leak, empty-file writes, the select row/htmlAttrJson mix-up, handler crashes, state clobbering — most of which are small, local, independently verifiable patches.

The Critical and High items are what make PAD unsafe to expose to untrusted input or an untrusted network today. Everything below them is quality and correctness work that a codebase this carefully commented is well positioned to absorb. Keep changes small; add negative and boundary tests with an independent expected result; document any compatibility change to recursive output or session promotion.
