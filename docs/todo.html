Start with named component slots, HTML attribute helpers, and ifchanged. They would make everyday PAD templates substantially cleaner and fit its existing design.

What PAD already covers

The analysis inspected the core tag/function dispatch, content stores, wrappers, data handlers, escaping, caching, and application examples, then compared them with official Twig, Blade, Latte, and Smarty documentation. This is source-level feature analysis; the proposed features have not been implemented.

PAD already has useful equivalents of many common template features:

  • Layout wrapping through _inits.pad, _exits.pad, and @page@.
  • Reusable templates through _tags, _include, and stored content.
  • Capture through toContent, empty-loop branches through @else@, and cycling through {switch}.
  • Sorting, slicing, pagination, and deduplication.
  • Direct PHP function access, enabled by default. Consequently, helpers such as join, round, or number_format would mostly add aliases. See function resolution.

The proposals below add capabilities or clear conveniences beyond those foundations.

Proposed syntax: all suggested syntax below is illustrative, not currently implemented. Effort labels are relative estimates, not implementation commitments.

Seven tag additions

Practical conveniences and larger capabilities
  1. 01

    Named slots and declared parameters

    Highest architectural value for reusable tags

    Large

    PAD’s custom tags and @content@ merging already provide a foundation for components. The useful addition would be multiple named content areas, defaults, required parameters, and slots scoped to each invocation.

    {card title='Monthly revenue'}
  <strong>{$revenue}</strong>

  {slot 'footer'}
    <a href="?reports">View report</a>
  {/slot}
{/card}

    A card could have independent header, body, and footer slots; nested cards would not overwrite each other’s content. Extend PAD’s existing _tags mechanism rather than introduce a separate component directory.

    Precedents: Blade slots · Twig embed

  2. 02

    attrs and classes helpers

    Best everyday convenience

    Small–medium

    Generate correctly quoted attributes, conditional classes, and HTML boolean attributes without repeated conditions.

    <button {attrs disabled=$busy, title=$help}>
  Save
</button>

<div class="{classes 'panel', active=$isActive, invalid=$hasErrors}">
  ...
</div>

    PAD provides escaping primitives, but the inspection found no built-in attribute-map or conditional-class serializer. This helper should omit false HTML boolean attributes while preserving values such as aria-expanded="false".

    Precedents: Latte n:attr and n:class

  3. 03

    ifchanged

    Especially useful for PAD’s data-driven templates

    Medium

    Render a heading whenever a value changes during iteration:

    {orders sort='customer'}
  {ifchanged $customer}
    <h2>{$customer}</h2>
  {/ifchanged}

  <p>{$number}: {$total}</p>
{/orders}

    PAD already exposes first/last/current iteration properties, but those do not express “this customer differs from the previous customer.” This would simplify grouped reports, timelines, alphabetical directories, and invoices.

    Track state separately for each tag location and enclosing loop invocation. The first occurrence should render.

    Precedent: Latte ifchanged

  4. 04

    push, stack, and once

    Let components declare their assets

    Medium–large 
    {push 'scripts', once='chart-library'}
  <script src="/assets/chart.js"></script>
{/push}

{stack 'scripts'}

    Repeated components could request their scripts or styles, with each dependency emitted once. PAD’s content stores currently assign a named value; a stack would add ordered accumulation, deduplication, and deferred insertion.

    Deferred insertion matters when the layout’s <head> appears before the components that contribute styles.

    Precedents: Blade stacks · @once

  5. 05

    Named layout blocks with overrides

    Useful beyond directory-based layouts

    Large 
    {extends 'layouts/report'}

{block 'title'}Sales report{/block}

{block 'sidebar'}
  {parent}
  <a href="?export">Export</a>
{/block}

    PAD already has directory-based wrapper inheritance. The additional capability is selecting a layout independently of directory placement and overriding individual regions, optionally retaining their parent content.

    Develop this alongside slots because both need well-defined ownership and override rules.

    Precedent: Smarty blocks and parent content

  6. 06

    Fragment caching

    Explicit keys and expiry for individual sections

    Medium–large 
    {cache 'homepage-top-products', ttl=300}
  {topProducts}
    <article>{$name}</article>
  {/topProducts}
{/cache}

    PAD has whole-response caching. The inspection found no implemented template-fragment cache, despite the reference mentioning a cache option.

    This would cache an expensive section while the surrounding page remains dynamic. A cache hit should skip the enclosed template work. PHP already executed before rendering would still run, so query savings depend on where data retrieval happens. Keys must include inputs that change the rendered result.

    Precedent: Twig’s optional CacheExtension

  7. 07

    Named response fragments

    A natural extension of PAD’s AJAX support

    Medium–large 
    {fragment 'order-list'}
  {orders}
    <li>{$number}</li>
  {/orders}
{/fragment}

    A normal request would render the complete page; a fragment request would return only order-list.

    PAD’s existing ajax fetches another page without wrappers. Named fragments would allow one template to serve both the full page and a selected update region, useful for search results, pagination, and HTMX-style interfaces.

    Precedent: Blade fragments

Loose ends found along the way

Small fixes to make before building anything new

More template ideas

Expressions, data shaping and tags
  1. 08

    Expression upgrades: ??, inline ternary, in, matches

    Medium
    {echo $nickname ?? $name}
<span class="{echo $stock gt 0 ? 'in-stock' : 'sold-out'}">
{if $status in ('active', 'trial')} … {/if}
{if $code matches $skuPattern} … {/if}

    The evaluator supports arithmetic, . concatenation, comparisons, and/or/xor/not, parentheses and array literals (lib/eval/const.php). Four everyday forms are missing: null-coalescing, a ternary inside expressions (today only the tag-level {even@rows ? a : b} exists, in level/ternary.php), an in operator (only the in() pipe exists), and regex matching (only the SQL-style like() pipe exists).

    ?? also answers “default for an empty value”, which today takes optional, else= or null=. Regex literals need a decision: a quantifier such as {2} inside a pattern collides with PAD’s braces, so pass patterns as variables or define an escape.

    Precedent: Twig expressions and operators

  2. 09

    A where filter on any data

    Medium
    {orders where="$status eq 'open' and $total gt 100",
        sort='total DESC', first=5}
  <li>{$number}: {$total}</li>
{/orders}

    The handling options sort, slice, page, dedup and shuffle, but none of them filters rows. Filtering exists only for database tables through Select, so JSON, XML, CSV, curl or page-PHP data cannot be narrowed in the template.

    Evaluate the condition per row with PAD’s own evaluator, with the row’s fields in scope. Run it before first, page and rows, so they count the filtered rows.

    Done. handling/types/where.php: a quoted expression evaluated per row with the row as the current occurrence, in written order with the other handling options and with negative; Select tables keep their SQL where. A level the handling empties now shows its @else@ branch (also for first=0). Regression: six framework options/ cases (where_* and first_zero_*; they fail on the old engine); manual Data handling demos; HANDLING.md, OPTIONS.md, CLAUDE.md.

    Precedent: Twig filter

  3. 10

    Grouping with subtotals

    Medium–large
    {orders group='customer', sum='total'}
  <h2>{$customer}: {$count} orders, {$total}</h2>
  {rows}
    <p>{$number}: {$total}</p>
  {/rows}
{/orders}

    ifchanged prints a heading when a value changes. Grouping goes further: each group is an occurrence with its key, a count, aggregated fields and its rows as nested data. Inside {rows}, $total is the row’s own value again.

    Sum, average, minimum and maximum exist today only as sequence actions and through Select’s SQL grouping.

    Precedent: Jinja groupby

  4. 11

    {pager} navigation

    Medium
    {products page=$pg, rows=12}
  <article>{$name}</article>
{/products}

{pager 'products', window=2}
→ ‹ 1 … 4 5 [6] 7 8 … 20 ›

    The page handling already slices the data, but every app writes its own previous and next links. A pager would use the total and current page that the handling step knows, build links through $padGo so mount prefixes keep working, keep the other query values, and mark the current page with aria-current="page".

    Precedent: Laravel pagination links

  5. 12

    Recursive trees

    Medium
    {tree data='menu', children='items'}
  <li><a href="?{$page}">{$title}</a>
    {branch}<ul>{recurse}</ul>{/branch}
  </li>
{/tree}

    Menus (_common/_data/menu.json), category trees, threaded comments and {files recursive} results are all trees. A tag can call itself up to the 100-level limit, but nothing says “render this body again for the children”.

    {recurse} would re-enter the body with the current row’s children, {branch} would render only when there are children, and depth@tree would give the level for indentation.

    Precedent: Jinja recursive loops

  6. 13

    Whitespace control

    Small–medium
    <ul>
  {~items}
    <li>{$name}</li>
  {/items~}
</ul>

    Only {tidy}, @tidy@ and the trim pipe handle whitespace today. A ~ just inside a brace would remove the whitespace on that side, newline included. It matters most where tidy cannot help: plain-text emails, CSV, JSON, console output and inline-block layouts. A {spaceless} pair could cover whole blocks.

    Precedents: Twig whitespace control · Smarty strip

  7. 14

    Inline {debug}

    Small
    {debug $order}
{debug}        every field visible here

    {dump} stops the request with a full dump, and the dump option writes to a directory. Neither shows a single value in the page while rendering continues. {debug} would print a collapsible <details> tree for local requests and nothing for remote visitors, using the same local check as lib/dump.php.

    Precedent: Twig dump

  8. 15

    Several values per {when}

    Small
    {case $status}
  {when 'new', 'open'} Active
  {when 'closed'}      Done
  {else}               Unknown
{/case}

    {when} evaluates its text as one expression and compares it with ==, so values that share an outcome need branches with duplicated content. Accept a list and compare each value in turn. Fix the {when 'default'} documentation at the same time (see loose ends).

    Precedent: PHP match with several conditions per arm

  9. 16

    Markdown tag and pipe

    Small–medium
    {markdown}
## Release notes
- **Faster** first render
{/markdown}

{echo $post.body | markdown}

    For help texts, release notes, content kept in a database, and the README files the apps app already reads. Use a CommonMark library when it is installed, with a small built-in subset as a fallback. Pass user content through an HTML sanitizer after conversion, and use the ignore option when the text contains braces.

    Precedent: Twig markdown_to_html

  10. 17

    Inline SVG charts

    Medium
    {chart 'bar', data='sales',
       label='month', value='amount'}
{sparkline data='visits', value='count'}
{sparkline sequence='fibonacci', rows=12}

    Server-rendered SVG needs no JavaScript, works in emails and print, and caches like any other output. Bar, line and sparkline cover most dashboards, and the sequence subsystem provides demo data straight away. Colour through CSS variables so dark mode works, and add a <title> for screen readers.

    Precedent: none of the compared engines ship this; it would be distinctively PAD.

  11. 18

    Page metadata with {meta}

    Medium
    {meta title='Monthly report', layout='print',
      cache=600, access='admin', sitemap=false}

    A page with PHP can set $title for the wrapper, because all PHP runs before rendering. A page without PHP, a plain .pad or a dropped-in .html, cannot. A {meta} tag read at build time, where @page@ is replaced (pad/build), could set:

    • the title;
    • an alternative wrapper;
    • a per-page cache TTL (caching is per app today);
    • an access rule (#30);
    • sitemap inclusion (#36).

    Today: the only page metadata is the <!-- PAD: … --> markers that _common/_lib/example.php searches for in the file text.

Developer experience

From “where did that come from?” to a fast edit loop
  1. 19

    Errors that point into the template

    Large
    PAD error · there is no field named '$totl'
apps/shop/orders/list.pad  line 14, column 11

  13 │   <tr>
  14 │     <td>{$totl | money}</td>
     │          ^^^^^ did you mean $total?
  15 │   </tr>

wrapped by apps/shop/_inits.pad › apps/shop/orders/_inits.pad

    Today the file and line in an error report are the PHP engine’s (padError reads debug_backtrace), and some brace errors give a character position. The template author has to find the spot by hand.

    The build step joins _inits, the page and _exits into one source, so this needs a small offset map from that joined source back to each file. With it, errors can show:

    • the template file, line, column and an excerpt;
    • a “did you mean” that compares a missing name with the fields, tags and functions in scope;
    • a vscode://file/…:14:11 link that opens the editor at the spot.

    The same map would also power the LSP (#21), the toolbar (#20) and template coverage (#52).

    Builds on: pad/build, lib/dump.php · Precedents: Symfony and Laravel error pages

  2. 20

    A debug toolbar

    Medium

    A collapsible bar added to local text/html responses, showing what PAD already collects:

    • timings, which today go out only in the PAD-Stats header;
    • the SQL statements in $_SQL;
    • the tag tree that the xml info mode writes to DATA/;
    • level variables and session values;
    • cache hit or miss.

    Clicking a tag in the tree could highlight the output it produced. It would be opt-in, for example with $padToolbar = 'local'.

    Precedent: Symfony web debug toolbar

  3. 21

    LSP: diagnostics, hover, go-to-definition

    Medium

    The language server offers completion and close-tag suggestions only. The next steps:

    • diagnostics from pad lint (#22) on save;
    • hover text from docs/reference;
    • go-to-definition that follows PAD’s own lookup order: {mytag} to the nearest _tags/mytag.* up the directories, {include:x} to _include/x.pad, | money to _functions/money.php.

    Page pairing makes one more feature possible: jump from {$total} in orders.pad to the line in orders.php that assigns it.

  4. 22

    One pad command

    Medium
    pad new shop               # apps/shop + www/shop/index.php
pad new shop/orders/list   # list.php + list.pad
pad serve                  # PHP's built-in server, no Apache needed
pad render demo clock      # any app's page to stdout
pad lint shop              # strict check of every template, no server
pad test shop              # the app's own tests (#23)
pad export demo out/       # a static copy (#41)

    Today apps/cli/pad hard-codes $padApp = 'cli', setup assumes Apache (pad/install/apache.sh), and a new app means creating both apps/x/ and www/x/index.php by hand.

    One command would cut the cost of a newcomer’s first hour:

    • pad serve needs only a small router for php -S; www/pad.php already derives $padRoot from SCRIPT_NAME, so serving at / should just work.
    • pad lint reuses $padCheckSyntax without rendering for a browser.
  5. 23

    Tests for application authors

    Medium
    _tests/cart.pad   the test page
_tests/cart.php   its data
_tests/cart.txt   the expected answer

{assert $total eq 42}

    The framework’s suites already work this way: a page next to an answer that holds an exact body, HTTP 404 or a /regex/ (regression/pages, and the Other suite). An app author has nowhere to put their own tests. A _tests/ directory in the app, picked up by pad test and ci.sh, would give every app snapshot tests. An {assert} tag would fail a test run and stay silent in production.

  6. 24

    Live reload

    Small–medium

    Add a tiny script to local responses. It asks an endpoint for the newest file time under the app (plus _common, and pad/ when working on the engine) and reloads the browser when a file changes. With pad serve, a save shows up in the browser at once. Keep it out of anything cached or exported.

  7. 25

    A PAD playground

    Medium

    A new app with two panes: PAD source and JSON sample data on the left; output, tag tree and errors on the right. It would be shareable through the URL hash, which also suits the manual and bug reports.

    It must be local-only or hardened. {sandbox} isolates PAD state, not PHP, and php: calls are allowed by default. The playground needs $padPhpFunctions = [], $padRequestVars = [], and limits on time and output size.

  8. 26

    Designer preview with sample data

    Medium
    ?orders&padSample
→ _samples/orders.json replaces orders.php

    A designer could work on orders.pad without a database or a login. A pad sample shop orders command could capture the variables of a real render into that file. PAD already keeps data and template in separate paired files, so this fits it better than engines where a controller builds the template context. Database tags inside the template still need the database; the sample file could override them by name.

  9. 27

    A Tree-sitter grammar

    Medium–large

    editors/README.md lists this as the remaining gap: without a Tree-sitter grammar, Zed and Helix have no native PAD highlighting. It would also give Neovim structural selection, folding of tag pairs, and text objects such as “inside this {items} loop”. Generate its keyword lists from the same source as the completion data.

Web application toolkit

The pieces every small app rebuilds by hand
  1. 28

    Forms with CSRF tokens, refill and validation

    Large
    {form 'contact'}
  {input 'email', type='email', label='E-mail', required}
  {textarea 'message', label='Message', required, rows=6}
  <button>Send</button>
{/form}

// contact.php
$errors = padValidate ( [
  'email'   => 'required|email',
  'message' => 'required|max:2000',
] );

    Today each page validates by hand. apps/demo/contact.php checks with filter_var into an $errors array and copies posted values into $formName to refill the form. It has no CSRF token; the only cross-site protection is the SameSite=Lax cookie flag.

    The pieces:

    • CSRF. {form} adds a session-bound token, and $padCsrf = TRUE rejects any POST without one. This part can ship first, on its own, with a {csrf} tag.
    • Fields. {input} refills from the posted value (escaped), and renders the label, the error message, and aria-invalid/aria-describedby when validation fails.
    • Post-redirect-get. The demo now does this by hand; it can become the default after a valid post.

    Precedents: Laravel CSRF · Nette forms with Latte

  2. 29

    Flash messages

    Small
    padFlash ( 'Thanks, your message was sent.' );
padRedirect ( 'contact' );

{flash}
  <p class="notice {$type}">{$message}</p>
{/flash}

    After the post-redirect-get change, the demos pass a query flag such as ?contact&sent=1 to show the thank-you. A flash message survives exactly one redirect through the session. The session would have to start on demand: today it starts only when $padSessionVars lists names.

  3. 30

    Directory guards: _guard.php

    Small–medium
    // apps/shop/admin/_guard.php
if ( ! $session_user )
  padRedirect ( 'login' );

return $session_role == 'admin';   // FALSE → 403

    PAD already runs _inits.php for every page below a directory. A _guard.php in the same place, run before anything else, would make access control follow the file tree: put one in admin/ and every page there is protected, with no route list to keep in sync. {meta access=…} could add per-page rules. Guarded pages already stay out of the page cache, which skips visitors with a session.

  4. 31

    JSON and CSV from the same page

    Medium
    ?orders&padFormat=json
Accept: application/json

// orders.php: only these leave the server
$padExpose = [ 'orders', 'total' ];

    A paired orders.php already produces the data, so the same page could answer with JSON, or CSV for a single list, instead of rendering orders.pad. This would be a fifth output type next to web, console, file and download.

    Exposure must be an explicit list, never “all variables”. The React pages could then fetch from ordinary pages instead of separate _providers.

  5. 32

    Clean URLs with dynamic segments

    Large
    /shop/products/42
  → products/[id].pad, $id = 42
/blog/2026/hello-pad
  → blog/[year]/[slug].pad

    Pages are reached through the query string only (inits/page.php). An optional mode, enabled with one Apache FallbackResource line or the pad serve router, could map the path onto the file tree and bind bracketed names as variables. That keeps “no routing, just create files”, and $padGo would generate matching links.

    Precedent: SvelteKit file-based routing

  6. 33

    Security headers and CSP nonces

    Medium
    <script nonce="{nonce}"> … </script>

    The output step (lib/output.php) sends content type, caching, Vary and ETag headers, but no security headers and no Content-Security-Policy. The proposal:

    • a default set of headers: X-Content-Type-Options, Referrer-Policy and frame-ancestors;
    • a $padCsp setting;
    • a per-request {nonce}, so pages with inline {ignore} scripts can run under a strict policy.
  7. 34

    Template emails

    Medium
    {mail to=$email, template='order',
      subject='Order confirmation'}

    Mail templates would live in _mail/, with their own _inits.pad for the email layout and both HTML and text parts. The transport is configurable (mail() or SMTP). In development, messages are written to DATA/mail/ instead of being sent, and shown in the toolbar (#20). {file} already writes rendered output to disk, so the rendering side is mostly there.

  8. 35

    Safe file uploads

    Medium
    $avatar = padUpload ( 'avatar',
  types: [ 'image/png', 'image/jpeg' ],
  max:   '2M' );

    Nothing handles $_FILES today. A helper that:

    • checks the real type with finfo, not the type the browser claims;
    • enforces a maximum size;
    • stores the file under a random name in DATA/uploads/ and returns a record.

    Together with a file field in #28, it would replace the most error-prone code in small apps.

  9. 36

    Sitemap from the file tree

    Small

    In PAD every page is a file, so the sitemap can be generated:

    • walk the app;
    • skip _ directories, guarded directories (#30), and pages that opt out with {meta sitemap=false};
    • use file times as lastmod.

    A robots.txt answer can point to it. Frameworks with a routing table need a route list for this; PAD needs nothing extra.

  10. 37

    Early flush

    Medium–large
    {flush}

    The response is buffered and sent once, after the whole page is rendered (padWebSend in lib/output.php). A {flush} right after the wrapper’s <head> would let the browser fetch CSS and fonts while a slow query runs.

    Flushing conflicts with tidy, whole-body gzip, ETag and Content-Length, so it should be explicit and switch those off for the request. A lighter alternative: {preload 'style.css'} sends Link: rel=preload headers.

  11. 38

    Locale as a first-class setting

    Medium
    // _lang/nl.json
{ "cart.items": "%d artikel|%d artikelen" }

{t 'cart.items', count=$n}

    Only $padFmtDate exists today. A $padLocale and $padTimezone would give the proposed trans, currency and localDate functions one source of truth. They would be chosen from the app config, from Accept-Language, or by a ?lang= choice kept in the session. A _lang/ directory fits the existing auto-loaded directories, with the usual lookup from the page’s directory up to _common.

Data & sequences

More sources, less glue code
  1. 39

    Remote data with a cache

    Medium
    {curl 'https://api.example.com/rates.json',
      ttl=600}

    {curl} and .curl files in _data/ fetch and parse remote data, but every request fetches again. A ttl= option could use the cache backends PAD already has (apcu, file, redis, memcached, db), which would make dashboards on external APIs cheap. When the API is down, serve the last good copy and log the failure.

  2. 40

    Markdown collections

    Medium
    _content/blog/hello.md
  ---
  title: Hello PAD
  date: 2026-10-05
  ---
  First post …

{collection 'blog', sort='date DESC', first=10}
  <h2><a href="?blog/post&slug={$slug}">
    {$title}
  </a></h2>
{/collection}

    A folder of Markdown files with YAML front matter as a data source. Each file is a row: the front-matter keys become fields, plus a slug and the rendered body. This builds on the YAML reader, which needs the PHP yaml extension, and on #16. It would make PAD a small flat-file CMS.

  3. 41

    Static site export

    Medium

    docs/apps/ already holds a crawled copy of the apps, with file names such as index﹖clock.html and separate &padInclude variants. A built-in pad export would improve on it:

    • crawl the pages the way the Other suite does;
    • rewrite ?page links to page.html;
    • copy assets and skip _ directories.

    Brochure sites and the manual could then be hosted on any static host.

  4. 42

    SQLite for zero-setup apps

    Medium–large

    The database layer is MySQL through mysqli, with two fixed connections (lib/db.php). After the PDO move that ANALYSE.md recommends (section 4), SQLite costs little extra. Then classicModels, the database cases in the suites, and new apps from pad new could run without a database server. Named connections such as db('reports', …) would come from the same change.

  5. 43

    Lookups between data sets

    Small
    {orders}
  {$number}:
  {echo $customer_id
        | lookup('customers', 'id', 'name')}
{/orders}

    Joins exist for database tables through Select relations, and {at "id=5@customers"} finds the first matching row. A lookup pipe would fit that into templates where two lists come from different sources, such as JSON plus CSV, or an API plus page PHP. Index the second set once per request, not once per row.

  6. 44

    Sequences you can see and hear

    Small–medium

    The sequence subsystem holds 80 types and 29 actions. Three additions that would make it engaging:

    • plot each type’s terms as SVG (#17) next to its OEIS link;
    • a “guess the next term” game that shows the start of a random sequence;
    • Web Audio playback that turns terms into notes. Recamán’s sequence is a famous one to listen to.

    Good for workshops, and a light way to show off PAD’s data model.

Engine & performance

Measured speedups and extension points
  1. 45

    Cache the parse, not only the page

    Large

    Each request repeats the same work:

    • it rebuilds the page source from _inits, the page and _exits;
    • it walks the directories to resolve _lib, tags, functions and includes;
    • it rescans the string: find the first }, then the nearest { before it (level/level.php), until none remain.

    Two steps, measured with the develop app’s Benchmark page before and after:

    1. Cache the build result, and which file each name resolves to, in APCu, keyed by file times. This is cheap and safe.
    2. Cache where each tag sits and how its parameters split, per hash of the source string.

    ANALYSE.md mentions template compilation in general; this narrows it to PAD’s two hot spots without changing how the engine works.

  2. 46

    Event hooks for applications

    Medium
    _events/error.php    report to Sentry or Slack
_events/sql.php      log slow queries
_events/output.php   post-process the final HTML

    pad/events/ holds about 58 hook points, but each runs only under $padInfo and serves trace and stats. Opening a small, stable subset to apps through an _events/ directory, with the same lookup rules as _callbacks, would allow integrations without editing the engine. The dormant cache hook suggests a tidy-up first.

  3. 47

    App options that act on the result

    Small

    An app’s _options/name.php runs once, before content is generated, and works on the template source (options/_go/app.php). The built-in toContent, toData, tidy and dump run at the end, on the result, but app options cannot. Letting an option declare its phase would allow options like {report minify} or {price highlight} that work on rendered output.

  4. 48

    Parallel fetching

    Medium
    padPrefetch ( [
  'rates'   => 'https://example.com/rates.json',
  'weather' => 'https://example.com/weather.json',
] );

    Several {curl} sources on one page are fetched one after another. Fetching them together with curl_multi in the page PHP, then reading them as named data, would make the wait as long as the slowest response, not the sum of all of them.

  5. 49

    Benchmark history

    Small–medium

    The develop app’s Benchmark already times every page through the PAD-Stats header. Storing each run with its commit hash, and charting the trend with #17, would catch slowdowns the way the suites catch output changes. ci.sh could fail when a page slows past a set threshold.

Moonshots

Bigger bets that would make PAD stand out
  1. 50

    An MCP server for AI assistants

    Medium

    pad/error/claude.php already returns machine-readable JSON errors to local tools. A small MCP server could let assistants:

    • render a page and read the trace of a request;
    • list apps, pages and tags;
    • look up a tag or function in the reference;
    • run pad lint and a suite.

    Assistants could then check PAD syntax against the engine itself, instead of relying on a long CLAUDE.md.

    Precedent: Model Context Protocol

  2. 51

    Replay real traffic as tests

    Medium–large

    Track mode stores each request and response as JSON under DATA/track/. pad replay would re-run recorded GET requests against the current code and diff the output with the regression comparator, which already normalises the host. Real use becomes a regression suite: a framework change that alters any page’s output shows up before release. Requests with sessions and cookies need care, and a replay must never write.

  3. 52

    Template coverage

    Medium

    During a suite run, record which tags, {if}/{else} branches, {case} arms, includes and _functions actually ran. The xref mode already records which page uses which tag. With the source map from #19, the report could show each template with the parts that never ran highlighted, and point to manual fragments that no test exercises.

  4. 53

    PAD in the browser

    Large · experimental

    PHP compiled to WebAssembly, as WordPress Playground does, could run PAD in the browser. That would make three things possible:

    • the manual’s examples become editable and live on a static docs site;
    • the playground (#25) needs no server;
    • sandboxing becomes the browser’s job.

    Precedent: WordPress Playground

  5. 54

    Output checks in development

    Medium

    After rendering a local request, check the HTML for:

    • duplicate ids;
    • images without alt;
    • form fields without labels;
    • broken internal links.

    The link check is cheap and exact in PAD: a ?page link is broken when its file does not exist. Report the results in the toolbar (#20), or across every app with pad lint --links.

  6. 55

    Live regions

    Large
    {live 'cart'}
  {cart}<li>{$item} × {$qty}</li>{/cart}
  <button pad-click="add" pad-value="42">Add</button>
{/live}

    This builds on named fragments (#07). A small script sends the event to the page, the server re-renders only that region, and the browser swaps it in. Pages become interactive without app-written JavaScript or a client framework, with state kept in the session.

    Precedents: Laravel Livewire · htmx

Where to begin

Before anything else

Close the loose ends

Fix the eight mismatches in the loose-ends table. Most are documentation changes. The {^x} sigil and the .sql reader are small code changes, each with a regression case.

Initial release

Useful, contained additions

Choose attrs/classes, ifchanged, truncate, slug, and bytes: useful additions with relatively contained implementation work. Add ?? and the inline ternary (#08), several values per {when} (#15), {debug} (#14), flash messages (#29) and the sitemap (#36).

First larger feature

Named slots

Add named slots to reusable tags. Design their ownership and override rules alongside the proposed layout blocks.

Highest developer leverage

Errors that point into the template

The source map behind #19 also enables the toolbar (#20), LSP diagnostics (#21) and coverage (#52). Combine it with the pad command (#22) to make a newcomer’s first hour much shorter.

Security comes first among the web helpers: ship the CSRF part of #28 on its own, before the rest of the form helpers. Then add directory guards (#30) and security headers (#33).

Standalone macros rank lower: PAD’s stored template source, parameters, and custom tags already cover much of their practical purpose.

Likewise, array batching could be a pleasant batch=3 data option inspired by Twig batch, but it is chiefly convenience over PHP’s existing array operations.
