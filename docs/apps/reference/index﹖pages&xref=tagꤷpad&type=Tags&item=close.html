{meta title='Application tests'}

<p>An application keeps its own tests in <code>_tests/</code>. A test is a page there -
<code>cart.pad</code>, with <code>cart.php</code> when it needs data - next to its answer,
<code>cart.txt</code>. <code>pad test shop</code> renders every test page and compares:</p>

{ignore}
<code>$ pad test shop
shop
  ok    cart
  FAIL  checkout
        want: <p>Total 42</p>
        got:  HTTP 500 - assert failed: $total eq 42
              apps/shop/_tests/checkout.pad:1:1  {assert $total eq 42}
  2 tests, 1 failed</code>
{/ignore}

<h2>The answer</h2>

<ul>
  <li>the exact output of the page, trimmed;</li>
  <li><code>/a pattern/</code> matched over it - for output that changes, a date or a count;</li>
  <li><code>HTTP 500</code>, with an optional <code>/pattern/</code> on the next line, for a test that is meant to fail.</li>
</ul>

<p>A test without an answer counts against the run; <code>pad test shop --record</code> writes
the missing answers from what the pages render now, and never overwrites one.
<code>pad test --all</code> runs every application that has tests, and <code>./ci.sh</code>
does that as its <code>apptests</code> line.</p>

<h2>Asserts</h2>

<p>{tag 'assert'} holds a page to a condition during a test run: false, and the test fails
with the condition and the message as its report. Anywhere else it is silent - the
condition is not even evaluated - so it can stay in the application's own pages. The switch
is <code>$padAssert</code>, which <code>pad test</code> turns on; this example turns it on in
its PHP:</p>

{example 'fragments/app_tests_1'}

<h2>A test page</h2>

<p>It is a page like any other, rendered bare - without the application's wrappers - and no
URL reaches it. It can bring in a real page with <code>{page 'cart'}</code>, or
include the page's own PHP and check the data it sets:</p>

{ignore}
<code>_tests/cart.php    <?php include APP . 'cart.php'; ?>
_tests/cart.pad    {assert $total eq 42, 'the cart total'}
                   <p>Total {$total}</p>
_tests/cart.txt    <p>Total 42</p></code>
{/ignore}

{meta title='Options of your own'}

<p>A file in the application's <code>_options/</code> directory makes its name an option
of every tag - written bare, <code>{staff words}</code>, or with a value,
<code>{staff wrap='em'}</code>. Where the file stands decides when it runs:</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>file</th><th>runs</th><th><code>$padContent</code> is</th></tr>
  <tr><td><code>_options/name.php</code></td><td>before the tag renders</td><td>the template between the tags</td></tr>
  <tr><td><code>_options/end/name.php</code></td><td>after the tag rendered</td><td>the result - every occurrence, joined</td></tr>
</table>

<p>&nbsp;</p>

<p>The handler changes <code>$padContent</code>, and the option's value is in
<code>$padGetName</code> - TRUE when the option is written bare. An end option sees the
fields filled in, so it can count, mark or tidy what the tag produced. Here
<code>fragments/options/_options/end/words.php</code> appends a word count:</p>

{ignore}
<code><?php                                   // _options/end/words.php

  $padContent .= '(' . str_word_count ( strip_tags ( $padContent ) ) . ' words)';

?></code>
{/ignore}

{example 'fragments/options/options_1'}

<p>With a value - <code>_options/end/wrap.php</code> puts the result in the element it is
given:</p>

{ignore}
<code><?php                                   // _options/end/wrap.php

  $padContent = "<$padGetName>" . trim ( $padContent ) . "</$padGetName>";

?></code>
{/ignore}

{example 'fragments/options/options_2'}

<p>An option may have both files: the first works on the template, the second on what it
became. The end options run before the built-in <code>toContent</code>, <code>toData</code>
and <code>tidy</code> - those store or tidy what the end option made - and before the closing
tag's pipe. Like tags and callbacks they are looked up from the page's directory up to the
application root.</p>

{meta title='Clean URLs'}

<p>A page is named in the query string - <code>/shop/?products/42</code> - or by the path
behind the application: <code>/shop/products/42</code>. The path is mapped onto the files,
and a file or directory whose name is a bracketed variable name stands for any one segment.
The segment becomes that variable before the page's PHP runs:</p>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>url</th><th>file</th><th>variables</th></tr>
  <tr><td><code>/shop/products/42</code></td><td><code>products/[id].pad</code></td><td><code>$id</code> is 42</td></tr>
  <tr><td><code>/shop/products/new</code></td><td><code>products/new.pad</code></td><td>a name of its own wins over a bracket</td></tr>
  <tr><td><code>/shop/blog/2026/hello-pad</code></td><td><code>blog/[year]/[slug].pad</code></td><td><code>$year</code> and <code>$slug</code></td></tr>
  <tr><td><code>/shop/docs/a/b</code></td><td><code>docs/[path+].pad</code></td><td><code>$path</code> is the rest, a/b</td></tr>
</table>

<p>The same names resolve wherever a page is named - here through
<code>{page}</code>, with <code>shop/products/[id].pad</code> and
<code>shop/blog/[year]/[slug].pad</code> beside the fragment:</p>

{example 'fragments/clean_urls_1'}

<ul>
  <li><code>?products/42</code> resolves the same way, so the application runs on a server
      that routes no paths, and <code>/shop/index.php/products/42</code> works everywhere.
      A bracketed file is never reached by its own name.</li>
  <li>Every <code>?page</code> link keeps working: on a clean URL, a query string that starts
      with a bare page name - the relative <code>href="?about"</code> - names that page.</li>
  <li><code>$padCleanUrls = TRUE</code> in <code>_config/config.php</code> makes
      <code>$padGo</code> write <code>/shop/products/42</code>. Apache needs one line,
      <code>FallbackResource /shop/index.php</code>; <code>php -S</code> needs nothing.</li>
</ul>

{meta title='Comments'}

<p>PAD has two comment forms. Both are taken out of the template before it is scanned, so a tag written inside one never runs and nothing of it reaches the output.</p>

<ul>
  <li><code>{# ... #}</code> - the original form</li>
  <li><code>{-- ... --}</code> - the form the editor kits highlight and toggle</li>
</ul>

{example 'fragments/comments_1'}

<h2>Rules</h2>

<ul>
  <li>A comment closes at the first <code>#}</code> or <code>--}</code> after it, and may span lines.</li>
  <li><code>{--</code> must be followed by whitespace: a CSS custom property inside an {tag 'ignore'} block, <code>:root{--gap:4px}</code>, is CSS and stays as it is.</li>
  <li><code>{#name}</code> is not a comment but the option sigil - the value of the tag option <code>name</code>.</li>
</ul>

<h2>See Also</h2>

<ul>
  <li>{manual 'ignore'} - keep PAD from parsing braces</li>

{meta title='Components: slots and declared parameters'}

<p>A tag of your own with a <code>.pad</code> template is a component: the caller's content goes where the template writes {construct 'content'}. Named slots give it more than one place for content, and <code>{parms}</code> says which parameters it takes. The card below is <code>_tags/card.pad</code>:</p>

{source '_tags/card.pad'}

{example 'fragments/components_1'}

<h2>Slots</h2>

<ul>
  <li>A <code>{slot 'footer'}...{/slot}</code> pair standing directly in the content of the tag is a fill: it is taken out of the content and goes where the template has its <code>{slot 'footer'}</code>. The rest of the content goes to {construct 'content'}.</li>
  <li>In the template, the content of a <code>{slot}</code> is its default, rendered when the caller gave no fill. <code>{slot 'header'/}</code> in the caller's content is an empty fill.</li>
  <li>A default holding {construct 'content'} is a frame: <code>{slot 'footer'}<small>&#64;content&#64;</small>{/slot}</code> renders the frame round the fill, and nothing - or its {construct 'else'} part - when there is no fill.</li>
  <li>A fill is the caller's text: it renders with the caller's variables, and a <code>{#name}</code> or a <code>{slot}</code> inside it belongs to the caller's tag - which is how a template passes a slot of its own on to a tag it uses.</li>
</ul>

<h2>Every use has its own</h2>

<p>The fills belong to one use of the tag, so a card inside a card keeps its own footer:</p>

{example 'fragments/components_2'}

<h2>Declared parameters</h2>

<ul>
  <li><code>{parms title, tone='plain'}</code> at the top of the template declares the parameters: a name alone is required, <code>name=default</code> fills in what the caller left out. Both read as <code>{#title}</code>.</li>
  <li>A required parameter left out is an error, and so - under the strict check - is a parameter the tag does not declare: <code>{card titel='x'}</code> is reported by name.</li>
</ul>

{meta title='Template coverage'}

<p>A test suite says what it checks; coverage says what it reaches. With coverage on, every
local request notes which templates it read, which of their tags ran, and which branch each
{tag 'if'} and {tag 'case'} took. The report then shows each template with the parts that
never ran marked.</p>

{example 'fragments/coverage_1'}

<ul>
  <li><code>$padCoverage = TRUE</code> in <code>_config/config.php</code> records into the run
      <code>default</code>; a name instead of TRUE records into a run of that name, and
      <code>?page&amp;padCoverage=name</code> records one request.</li>
  <li><code>develop/?coverage&amp;start=suites</code> records every local request of every
      application until <code>develop/?coverage&amp;stop</code> - start it, run the suites,
      stop it, and <code>develop/?coverage&amp;run=suites</code> lists every template with the
      share of its tags and branches that ran, and the files no request read at all.</li>
  <li>A run is a file of JSON lines, <code>DATA/coverage/<run>.jsonl</code>, one line per
      request. Only local requests are recorded.</li>
  <li>An {if} without an {else} has one branch more: the run in which
      its condition was false. It is marked on the {/if}.</li>
</ul>

App: manual - Page: pages/csrf_protection
PHP

pages/csrf_protection.pad 		Result 
{meta title='CSRF protection'}

<p>Another site can make a visitor's browser post to your application - a hidden form that
submits itself - and the browser sends your session cookie along. A CSRF token tells those
posts apart from the ones your own forms send: a random value kept in the visitor's session
and written into your form, which another site can make the browser send but cannot read.</p>

<h2>One setting</h2>

<p>With <code>$padCsrf = TRUE</code> in <code>_config/config.php</code> every
<code><form method="post"></code> of a page gets a hidden <code>padCsrfToken</code> field
holding the token, and every POST - and PUT, PATCH and DELETE - that does not bring the token
back is answered <code>403</code> before any of the application runs. The forms an
application already has are protected without a change to them. A form that posts to another
site gets no token, and neither does a GET form, whose fields end up in the url.</p>

<h2>The {csrf} tag</h2>

<p>{tag 'csrf'} writes the field itself, for a form the page builds some other way, or for
an application that leaves <code>$padCsrf</code> off and checks a post by hand with
<code>padCsrfValid ()</code>. <code>{csrf token}</code> is the bare token, for a
script that sends it in an <code>X-CSRF-Token</code> header:</p>

{example 'fragments/csrf_protection_1'}

<ul>
  <li>The token is one per session, so two open tabs and the back button keep working. The
  session starts the first time a token is needed.</li>
  <li>A page carrying a token is never stored in the page cache - it would hand one visitor's
  token to the next.</li>
  <li>An application that accepts posts from elsewhere on some pages - a webhook - switches
  <code>$padCsrf</code> off for those pages in its <code>_config/config.php</code>, which
  knows <code>$padPage</code>.</li>
</ul>

App: manual - Page: pages/dates_and_logging
PHP
 HTML
pages/dates_and_logging.pad 		Result 
{meta title='Dates and logging'}

<p>A page's PHP asks for the date all the time: to stamp a record, to say how old a comment
is, to write down what happened. These helpers give "now" in the application's timezone, read
a date whatever form it arrives in, put an age into words and keep a log of the
application's own - plain functions, loaded on every request.</p>

<table border="1" cellpadding="6" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>function</th><th>what it answers</th></tr>
  <tr><td><code>padNow ( $format = NULL )</code></td><td>now, as a <code>DateTimeImmutable</code> in <code>$padTimezone</code> (else PHP's zone) - or, with a format, the formatted text</td></tr>
  <tr><td><code>padToday ( $format = NULL )</code></td><td>today at midnight</td></tr>
  <tr><td><code>padNowFreeze ( $time = NULL )</code></td><td>fixes now for the rest of the request; <code>NULL</code> lets the clock run again</td></tr>
  <tr><td><code>padDateParse ( $value )</code></td><td>a <code>DateTimeImmutable</code> from a timestamp, a date in text or a date object - <code>NULL</code> for what is none of those</td></tr>
  <tr><td><code>padAgo ( $date, $now = NULL )</code></td><td>the age in words: just now, 5 minutes ago, yesterday, in 3 days</td></tr>
  <tr><td><code>padLog ( $message, $level = 'info', $context = [] )</code></td><td>appends one line to the application's log of the day</td></tr>
</table>

<h2>Now and today</h2>

<p>The example freezes the clock first, so it shows the same on every day it is read - what a
test does too. Without the freeze, now is the real moment.</p>

{example 'fragments/dates_and_logging_1'}

<ul>
  <li>A number is a Unix timestamp, as the <code>date</code> pipe reads it; text is read the
  way PHP's <code>DateTime</code> reads it. A timestamp and text without a zone are in the
  application's zone; a zone that was given is kept.</li>
  <li>A date that does not exist - <code>2026-02-30</code>, which PHP itself would make
  2 March - is no date, nor are <code>NULL</code>, <code>''</code> and booleans:
  <code>padDateParse</code> answers <code>NULL</code> for them, never an error.</li>
  <li><code>$padTimezone</code> is read when a function is called, so a page can set it for
  itself.</li>
</ul>

<h2>Freezing the clock</h2>

<p><code>padNowFreeze ( '2026-10-05 14:30:00' )</code> fixes now for the rest of the request:
<code>padNow</code>, <code>padToday</code>, <code>padAgo</code>, the time stamp of
<code>padLog</code>, and text like <code>tomorrow</code> or <code>+1 week</code> given to
<code>padDateParse</code> all count from that moment. A test gets the same answer on every
run, and a page can be looked at as it will be on another day.
<code>padNowFreeze ()</code> lets the clock run again.</p>

<h2>How long ago</h2>

<p><code>padAgo</code> says the age of a moment in words, and the <code>ago</code> pipe does
the same in a template: <code>{$posted | ago}</code>.</p>

{example 'fragments/dates_and_logging_2'}

<ul>
  <li>Under ten seconds is <em>just now</em>, then seconds, minutes and hours. From a day on
  the calendar counts: the day before today is <em>yesterday</em> whatever the hour, then
  days, weeks, months and years.</li>
  <li>A moment still to come is said the other way round: <em>in 3 days</em>,
  <em>tomorrow</em>.</li>
  <li>A second argument - <code>padAgo ( $start, $end )</code>, or
  <code>{$start | ago($end)}</code> - counts from that moment instead of now. An
  empty value answers nothing.</li>
</ul>

<h2>Logging</h2>

<p><code>padLog</code> appends one line to
<code>DATA/logs/<application>/<Y-m-d>.log</code>: the time, the level, the
message and the context as JSON. The levels are those of PSR-3 - debug, info, notice,
warning, error, critical, alert and emergency - and <code>{name}</code> in the
message is filled from the context.</p>

{example 'fragments/dates_and_logging_3'}

<ul>
  <li>One call is always one line: a newline in the message is written <code>\n</code>.</li>
  <li>A message that is no text is written as JSON; a <code>Throwable</code> in the context
  as its class, message, file and line.</li>
  <li>A log line never stops the page: a disk that refuses the write is answered
  <code>FALSE</code>, not an exception. An unknown level is an error, the author's
  mistake.</li>
  <li>The engine's own errors go to PHP's error log; this log is for what the application
  wants to remember - a payment, a login, a failed import.</li>
</ul>

{meta title='Editor support'}

<p>The kits in <code>editors/</code> give PAD templates highlighting, completion and snippets
in Sublime Text, VS Code, Vim, Emacs, Kate, BBEdit and Notepad++. An editor that speaks the
Language Server Protocol - Neovim, Helix, Zed, Emacs with eglot, Sublime Text with LSP - runs
<code>editors/lsp/pad-lsp.js</code>, a Node server without dependencies.</p>

<h2>The language server</h2>

<ul>
  <li><strong>Completion</strong> - the built-in tags, functions, options, properties and type prefixes, and after <code>{/</code> the tags still open.</li>
  <li><strong>Diagnostics</strong> - when a page is opened or saved, PAD itself renders it on the command line under the strict syntax check (<code>editors/render.php</code>), and the error lands on the tag it names. A <code>_inits.pad</code> is checked through the index page of its directory; a snippet in <code>_include</code> or <code>_tags</code> has no page of its own and is not rendered.</li>
  <li><strong>Hover</strong> - the text of <code>docs/reference</code> for the tag, function, option, property or type prefix under the cursor; on an application's own tag or function, the comment at the top of its file; on a field, the line that assigns it.</li>
  <li><strong>Go to definition</strong> - PAD's own lookup order: <code>{badge}</code> to the nearest <code>_tags/badge.*</code> up the directories, then <code>_common</code>, then the engine; <code>{include:footer}</code> to <code>_include/footer.pad</code>; <code>| money</code> to <code>_functions/money.php</code>; <code>callback='x'</code> to <code>_callbacks/x.php</code>.</li>
</ul>

<p>Page pairing makes one more jump possible: from a field in the template to the line of
the paired <code>.php</code> that assigns it. Here, go to definition on <code>{$total}</code>
lands on <code>$total = 42;</code>.</p>

{example 'fragments/editor_support_1'}

<h2>Tree-sitter</h2>

<p><code>editors/tree-sitter-pad</code> is a Tree-sitter grammar: native highlighting in Zed,
Helix and Neovim, with the HTML around the tags highlighted as HTML. A pair of tags is one
node of the tree, so an editor can fold <code>{orders} ... {/orders}</code>,
select it, or select just what is inside it. Whether a tag is a pair is decided as the engine
decides it: <code>{orders}</code> opens a block only when a <code>{/orders}</code>
closes it further on, so <code>{else}</code> and <code>{echo $x}</code> stay
single tags.</p>

<h2>AI assistants</h2>

<p><code>editors/mcp/pad-mcp.js</code> is an MCP server: an assistant such as Claude Code asks
the engine itself instead of relying on what it remembers. It renders a page, or a template
that exists in no file yet, and runs the strict syntax check on it; it traces a request, lists
the applications, their pages and the built-ins, looks a tag or function up in the reference,
and runs the regression suites. Register it with
<code>claude mcp add pad -- node editors/mcp/pad-mcp.js</code>.</p>

{meta title='Ending the Request'}

<p>Some pages do not end by reaching their last line: a form handler redirects, a guard
refuses, an error stops everything. PAD has a tag or a function for each - and none of them
can be demonstrated live on this page, because each one would end the request this page is.
The examples are therefore shown, not run.</p>

<h2>Redirecting</h2>

<p>From a page's PHP, <code>padRedirect()</code> sends the browser to another page and ends
the request cleanly - session closed, buffers flushed, headers sent:</p>

{ignore}
<code>padRedirect ( 'tickets/index' );           // to a page of this application
padRedirect ( 'tickets/index', $vars );    // with variables carried along</code>
{/ignore}

<p><b>Never use PHP's <code>exit</code> or <code>die</code></b>, and not
<code>header()</code> either: they end PHP mid-request, skipping everything PAD still had to
do. The same goes for a restart - <code>padRestart('page')</code> renders another page in
place of this one without a round trip to the browser.</p>

<h2>The tags that end a request</h2>

<table border="1" cellpadding="8" cellspacing="0" style="border-collapse: collapse;">
  <tr><th>tag</th><th>what it does</th></tr>
  <tr><td><code>{exit}</code></td><td>ends the request where it stands - nothing is shipped, not even the output so far</td></tr>
  <tr><td><code>{error 'message'}</code></td><td>reports an error through the configured error action, which normally ends the request with a 500</td></tr>
  <tr><td><code>{exception 'message'}</code></td><td>throws a real PHP exception, for testing the nets that catch one</td></tr>
  <tr><td><code>{dump}</code></td><td>stops the request on a dump of the engine state, the heavy debugging tool</td></tr>
</table>

<h2>What happens on an error</h2>

<p>Any error - a tag that misses, a PHP warning, a thrown exception - ends the request
through the configured <code>$padErrorAction</code>: <code>pad</code> renders an error page,
<code>log</code> and <code>ignore</code> carry on, <code>dump</code> stops on the state
dump. The request answers with HTTP 500, and a command-line run exits with status 1, so a
script can test the outcome without reading the output.</p>

<p>A <code>demand</code> option turns an empty tag into an error: a page that is meaningless
without its data can say so - <code>{users demand}...{/users}</code> -
instead of rendering a hole.</p>
