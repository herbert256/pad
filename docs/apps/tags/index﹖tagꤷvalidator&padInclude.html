{input:validator} writes the browser's half of padValidate into the page as one inline script: the runtime, www/assets/rules/validate.js, with the script of every rule beside it - the same rules, the same messages. The rules are the files of pad/subs/inputs/rules/types/, each with its script in www/assets/rules/: accepted, after, after_or_equal, alpha, alphanum, before, before_or_equal, between, color, date, different, digits, distinct, email, ends_with, gt, gte, iban, in, integer, ip, json, lowercase, lt, lte, max, max_items, max_words, min, min_items, min_words, multiple_of, not_in, numeric, regex, required, required_if, required_unless, required_with, required_without, same, slug, starts_with, time, uppercase, url, uuid. It is written once a page - a second {input:validator}, or one after a {input:form ..., client} that brought it already, writes nothing.

It is for forms the template does not write as a {input:form} - a form a React, Vue or Alpine component draws, or a plain HTML form. Keep the rules in the page's PHP: padValidate ( $rules ) checks the post, and padValidateClient ( $rules ) exports the same list for the browser, each rule with the message padValidate would give.

The script defines padValidate.check ( rules, values ) (the message of every field that broke a rule), padValidate.field ( spec, value, values ) (one field's, empty when it holds) and padValidate.form ( form ). Every form with a data-pad-rules attribute is checked by itself: when it is sent, and a field again when it is left. A regex: rule JavaScript cannot read as PCRE does passes in the browser and is left to the server, which checks every post anyway.

Under a Content-Security-Policy that names 'nonce' the script carries this request's {pad:nonce}.
