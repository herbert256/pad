pages/codes.pad 		Result 
{pad:meta title='Barcodes and QR codes'/}

<p>{app:tag 'barcode:auto'/} and {app:tag 'barcode:qr'/} write a code a scanner reads. It is encoded on the server and
drawn as inline SVG - no image library, no font, no remote service - so a page with a code prints,
caches and goes in an e-mail like any other. There are {pad:echo php:count(padKinds('codes'))/}
symbologies, every one a file of <code>pad/subs/codes/types/</code>. Twelve or thirteen digits are an
EAN-13, with the check digit added when it is left off; any other text is Code 128.</p>

{common:example 'fragments/codes_1'/}

<h2>Two ways to write one</h2>

<p>The name after <code>barcode:</code> selects the symbology: <code>{barcode:upce '0425261'/}</code>.
The barcode type does the same, <code>{barcode:upce '0425261'/}</code>.
Both forms require their type prefix and draw the same UPC-E.</p>

{common:example 'fragments/codes_2'/}

<h2>Products, parcels and labels</h2>

<p>The product codes - <code>ean13</code>, <code>ean8</code>, <code>upca</code> and
<code>upce</code> - check the digit a number ends in, or add it; <code>databar</code>, GS1 DataBar, writes a
GTIN in the small symbol of loose fruit and vegetables. Code 128 and Code 93 take printable
ASCII, Code 39 capital letters, digits and a few signs, with <code>check</code> for its check
symbol. <code>itf</code> and <code>itf14</code> are the digits of cartons, <code>codabar</code> the
code of libraries and blood banks, <code>msi</code> that of shelf labels.
<code>gs1128</code> writes the GS1 element strings of a logistics label -
<code>(01)09501101530003(17)261231(10)AB-123</code> - with every value checked as GS1 defines it;
<code>datamatrix</code> with <code>gs1</code> writes them as GS1 DataMatrix, the code of medicine packs.
<code>bookland</code> is the barcode of a book, its ISBN as an EAN-13 with the ISBN above the bars,
and <code>addon=</code> puts two or five more digits beside an EAN or UPC - a magazine's issue, a
book's price.</p>

{common:example 'fragments/codes_3'/}

<h2>Two-dimensional codes</h2>

<p><code>qr</code> is the code of {app:tag 'barcode:qr'/}, which a phone camera reads; <code>datamatrix</code>
the square code of parts and medicine packs. Both take any text and choose the smallest symbol that
holds it, and both take <code>size=</code> in pixels in place of the height and scale of the bars.
<code>aztec</code>, the code of train tickets and boarding passes with a bullseye in its middle, does
the same, with <code>ecc=</code> for the share of its codewords that corrects errors.
<code>pdf417</code>, the code of boarding passes and driving licences, stacks rows of codewords
instead, each row telling the scanner where it stands; <code>columns=</code> sets how wide it is
and <code>level=</code> its error correction.</p>

{common:example 'fragments/codes_4'/}

<ul>
  <li>The colours are black on white unless <code>color=</code> and <code>background=</code> say
  otherwise - fixed, whatever the page's colour scheme, as a scanner needs the contrast.</li>
  <li>The SVG is <code>role="img"</code> with the text, or <code>title=</code>, as its name.</li>
  <li>A wrong check digit, a character the symbology has no bars for or a text too long for it is
  an error under the strict check, and nothing is drawn.</li>
</ul>

pages/diagrams.pad 		Result 
{pad:meta title='Diagrams'/}

<p>{app:tag 'diagram:auto'/} draws a diagram from a few lines of text between its tags, written the way
Mermaid writes them, and lays it out on the server as inline SVG. There is no JavaScript, so a
diagram prints, works in an e-mail and caches like any other output, and the same lines always
draw the same picture. There are {pad:echo php:count(padKinds('diagrams'))/} kinds - every kind is a
file of <code>pad/subs/diagrams/types/</code>, and a flowchart is the one drawn when the tag names
none.</p>

{common:example 'fragments/diagrams_1'/}

<p>A line of a flowchart is a chain of nodes and edges. The brackets give a node its shape -
<code>[box]</code>, <code>(rounded)</code>, <code>{decision}</code>,
<code>((circle))</code>, <code>[(database)]</code> - and the arrow its line: <code>--></code>,
<code>-.-></code> dashed, <code>==></code> thick, <code>---</code> without a head, a label
between bars. The lines are taken as they stand, so their braces need no
{app:tag 'ignore'/}.</p>

<h2>Two ways to write one</h2>

<p>The name after <code>diagram:</code> selects the kind: <code>{diagram:state}</code>. The diagram
type does the same, <code>{diagram:state}</code>. Both forms require their type prefix.
<code>sequence</code> and <code>tree</code> are tags of their own, so those two kinds are written
<code>{diagram:sequence}</code> and <code>{diagram:tree}</code>. A first
line written the Mermaid way - <code>sequenceDiagram</code>, <code>stateDiagram-v2</code>,
<code>classDiagram</code>, <code>erDiagram</code>, <code>gitGraph</code> - names the kind as well,
so a diagram copied from Mermaid draws as it is.</p>

<h2>Messages and states</h2>

<p>A sequence diagram puts the participants side by side and the messages between them from top
to bottom, with notes and frames for loops and alternatives. A state diagram draws a machine:
<code>[*]</code> is its start on the left of an arrow and its end on the right, a label follows
the colon, and a state can be a choice or a fork.</p>

{common:example 'fragments/diagrams_2'/}

{common:example 'fragments/diagrams_3'/}

<h2>Classes and tables</h2>

<p>A class diagram draws a box of three parts for every class - its name, its fields, its methods
- and the relations between them: <code><|--</code> inherits, <code>*--</code> is made of,
<code>o--</code> holds, <code>..></code> depends on, with the multiplicities in quotes. The
parent and the whole are laid out above. An entity-relationship diagram draws every entity as a
table of its attributes and the relations with the feet of a crow: <code>||</code> exactly one,
<code>o{</code> zero or more, <code>|{</code> one or more.</p>

{common:example 'fragments/diagrams_4'/}

{common:example 'fragments/diagrams_5'/}

<h2>Hierarchies</h2>

<p>A mind map and a tree read their hierarchy from the indentation: a line is a node, and a line
indented under another is its child. The mind map shares the branches of its root over two
sides, each in a colour its twigs keep; the tree stands top down, every box centred over its
children - <code>direction='LR'</code> lays it on its side.</p>

{common:example 'fragments/diagrams_6'/}

{common:example 'fragments/diagrams_7'/}

<h2>Journeys and commits</h2>

<p>A user journey puts the steps of a day in a row, a face under each at the height of its score
from 1 to 5, and a dot for everybody who takes the step. A commit graph draws the commits of a
repository on the lanes of their branches, with the branches leaving and the merges joining.</p>

{common:example 'fragments/diagrams_8'/}

{common:example 'fragments/diagrams_9'/}

<h2>Causes</h2>

<p>A fishbone - the cause-and-effect diagram of Kaoru Ishikawa - reads its hierarchy from the
indentation as well: the first line is the effect, drawn in the head on the right, a line under
it a category, a bone above or below the spine by turns, and a line under a category a cause, a
rib along the bone, with the causes of a cause hanging off it. Mermaid's first line
<code>ishikawa-beta</code> names the kind too. The causes it shows are possible ones: the drawing
proves none of them.</p>

{common:example 'fragments/diagrams_10'/}

<h2>Grammars</h2>

<p>A railroad diagram draws the rules of a grammar written in the EBNF of the W3C - the notation
of the XML specification: <code>name ::= expression</code>, a terminal in quotes, a rule by its
name, <code>[a-z]</code> a character class, <code>|</code> a choice, <code>?</code> optional,
<code>*</code> none or more and <code>+</code> one or more. Every rule is a track; a name the
grammar defines is a link to its own track.</p>

{common:example 'fragments/diagrams_11'/}

<h2>Packets</h2>

<p>A packet diagram lays the fields of a header out by their bits, as the RFCs draw them:
<code>0-15: "Source Port"</code> a field from bit 0 to bit 15, <code>+16: "Destination Port"</code>
the next 16, in rows of 32 bits - <code>bits=</code> takes another width. The fields follow each
other from bit 0, and the first and the last bit of each stand over it.</p>

{common:example 'fragments/diagrams_12'/}

<ul>
  <li>The SVG has <code>role="img"</code>, a <code><title></code> - <code>title=</code>, else
  the name of the kind - and a <code><desc></code> that says every edge, message, relation or
  step in words, so a screen reader hears the whole diagram.</li>
  <li>The colours are custom properties on <code>.pad-chart-diagram</code> -
  <code>--pad-diagram-node</code>, <code>--pad-diagram-border</code>, <code>--pad-diagram-edge</code>
  and their like - with light and dark defaults; the mind map, the journey and the commit graph
  take the colours of the charts.</li>
  <li>A kind reads only the options it draws with: <code>direction</code> on a sequence diagram is an
  option nothing reads, and a line a kind cannot read is an error that names the line.</li>
  <li>A diagram without nodes answers nothing, so its <code>&#64;else&#64;</code> shows.</li>
</ul>

{pad:meta title='Forms'/}

<p>{app:tag 'input:form'/}, {app:tag 'input:field'/} and {app:tag 'input:textarea'/} write the fields of a form. When the
form comes back with mistakes in it, each field shows again what was typed - escaped - and
the message for its mistake beside it. <code>padValidate</code> in the page's PHP finds the
mistakes.</p>

{common:example 'fragments/forms_1'/}

<ul>
  <li>{app:tag 'input:form'/} posts back to the page and carries the session's CSRF token (see
  {app:manual 'csrf_protection'/}) and its name: <code>padPosted ( 'contact' )</code> is true when
  this form came back, so a page with two forms knows which one did.</li>
  <li>{app:tag 'input:field'/} and {app:tag 'input:textarea'/} take the field name first; <code>label=</code> writes a
  label tied to the field, <code>value=</code> the value before anything was posted, and every
  other item is an attribute of the field, as {app:tag 'attrs'/} writes it - <code>required</code>,
  <code>rows=6</code>, <code>placeholder='...'</code>.</li>
  <li>A checkbox or radio is checked when the posted value is its own value; a password or
  file field is never refilled.</li>
</ul>

<h2>Validation</h2>

<p><code>padValidate ( $rules )</code> checks the posted values and answers one message per
field that breaks a rule, keyed by the field - empty when all is well. A second argument
checks other data; a third replaces messages, per field (<code>'email'</code>) or per field
and rule (<code>'email.required'</code>):</p>

{common:example 'fragments/forms_2'/}

<p>A rule takes its argument after a colon: <code>min:n</code>, <code>max:n</code> and
<code>between:a,b</code> are a length, or a value with <code>numeric</code> or
<code>integer</code>; <code>in:a,b,c</code> a list, <code>regex:/.../</code> a pattern,
<code>same:other_field</code> another field, <code>digits:4</code> a number of digits. An empty
field is checked for <code>required</code> and <code>accepted</code> only. Every rule is a file of
<code>pad/subs/rules/types/</code> - its check in the browser beside it in <code>www/assets/rules/</code> -
and these are the {pad:echo php:count(padRuleTypes())/} there are:
{pad:echo php:implode(', ', padRuleTypes())/}. A rule name nothing knows is an error.</p>

<h2>After a failed post</h2>

<p>The fields of the form that came back show the message beside them, in the words of their
own label, tied to the field with <code>aria-invalid</code> and
<code>aria-describedby</code> so a screen reader reads them together. Here the post is
pretended in the PHP, the way a visitor's would arrive:</p>

{common:example 'fragments/forms_3'/}

<p>After a post that passes, store it and send the visitor on with <code>padRedirect ()</code>:
a refresh of the page they land on does not post a second time.</p>

<h2>Rules in the template</h2>

<p>The rules can stand on the fields themselves: <code>rules='required|email'</code> on an
{app:tag 'input:field'/} or a {app:tag 'input:textarea'/}. They are read from the page's template before its PHP
runs, and a post of the form is checked against them there - <code>padPosted ( 'contact' )</code>
is true only for a post that kept them, so the PHP acts on a good post alone. A post that broke
one renders the form again, refilled, with the messages beside the fields and the form's
<code>error=</code> above them (<code>error</code> alone says "Please correct the errors
below."):</p>

{common:example 'fragments/forms_4', skipResult/}

<ul>
  <li>Only what is written out counts: quoted rules, on a field with a quoted name, in a
  {app:tag 'input:form'/} with a name that posts back to its own page. Rules on a field in a snippet, a
  custom tag, a {app:tag 'page'/} or a layout, rules made from a variable, rules in a form with
  <code>action=</code> or <code>method='get'</code> and rules on a file field are errors -
  nothing would check them.</li>
  <li>Every field of the posted form that has rules is checked, also one in an {app:tag 'if'/}
  branch that did not render. A field that is there only sometimes keeps its check in the
  PHP: <code>padValidate</code> adds its messages to those of the template.</li>
  <li><code>padFormFailed ( 'contact' )</code> is true when the form came back and broke its
  rules.</li>
</ul>

{pad:meta title='Games'/}

<p>{app:tag 'game:memory'/} puts a little game on the page that is played in the browser. The server checks
what the game is given and writes its board; the game's script, written once per page, plays it.
There are {pad:echo php:count(padGameTypes())/} of them - every game is a file of
<code>pad/subs/games/types/</code>, and the <a href="../games/">games</a> application plays them all.</p>

{common:example 'fragments/games_1'/}

<h2>Select a kind</h2>

<p>Use <code>{game:tictactoe/}</code> to select the kind.
<code>opens='computer'</code> lets the computer open, <code>two</code> makes it a game of two players
at one screen.</p>

<h2>Words, questions and pictures</h2>

<p>The games that play with words, questions or a picture take them between their tags, a line each,
as they are written - braces and all. A quiz line is the question with its answers after a bar, the
right one first; they are shuffled when shown.</p>

{common:example 'fragments/games_2'/}

<p>The same list can come from the page: <code>data=</code> names a store, an array of the page or a
<code>_data</code> file, as a chart's data does.</p>

{common:example 'fragments/games_3'/}

<h2>The same game every time</h2>

<p><code>seed=</code> makes a game's shuffles, boards and puzzles the same on every load - a page can
say which sudoku it hands out. Without a puzzle the sudoku makes a new one with one solution;
<code>givens=</code> says how many squares it shows. <code>paper</code> draws a sudoku or a crossword
to print instead, with no script, and <code>solve</code> - <code>solution</code> for a crossword -
fills in the answers.</p>

{common:example 'fragments/games_4'/}

<ul>
  <li>When a game ends its board carries <code>data-result="won"</code> or <code>"lost"</code>, and a
  <code>pad-game-end</code> event goes up from it - a page can count the games won.</li>
  <li>The colours are custom properties on <code>.pad-game</code> - <code>--pad-game-accent</code>,
  <code>--pad-game-good</code>, <code>--pad-game-bad</code> and their like - with light and dark
  defaults.</li>
  <li>The script carries the CSP nonce, as the interactive tags' scripts do, and a game a fragment
  or a live region brings later starts as well.</li>
</ul>

{pad:meta title='Rich form fields'/}

<p>Beside <code>{input:field}</code> and <code>{input:textarea}</code> a form can hold
fields that do more: a slider, a row of stars, a switch, a month to choose a day from, a tag input,
a signature, a Markdown editor with its preview. The subsystem has {pad:echo php:count(padInputTypes())/}
types, including the native field, textarea, form container and standalone validator.
Every kind is a file of <code>pad/subs/inputs/types/</code>, with rich fields' scripts and styles in

{common:example 'fragments/inputs_1'/}

<h2>Writing a field</h2>

<p>The input: type names the kind, <code>{input:slider 'volume'/}</code>. The
first parameter is the field's name, <code>label=</code> its label, and every other item the kind
does not take is an attribute of its field, as with <code>{input:field}</code>:
<code>required</code>, <code>placeholder=</code>, <code>autocomplete=</code>.</p>

<h2>A real value, with or without a script</h2>

<p>Every kind writes a native field that a form posts as it is - a range, a number, a date, a
time, a colour, a checkbox, radio buttons, a text field - and its script, written once a page with
the CSP nonce, makes more of it: a month over the date, the times to pick from, swatches beside the
colour. Without the script the form works all the same; only the signature needs it.</p>

<p>Some fields post a text of their own making: a tag input the words joined with a comma, the boxes

a form without the script fills by hand. Choices come from a list - <code>options=</code>,
<code>suggestions=</code> - from a store named by <code>data=</code>, or a line each between the
tags.</p>

{common:example 'fragments/inputs_3'/}

<p>The fields are fields of the <a href="?pages/forms">{input:form}</a> around them: after a

after their frame, in the words of their label. <code>rules=</code> on a field is read from the
template before the page's PHP runs, as on <code>{input:field}</code>, and <code>client</code>
on the form checks the same rules in the browser. Here the post is pretended in the PHP:</p>

{common:example 'fragments/inputs_4'/}

<ul>

App: manual - Page: pages/printables

pages/printables.pad 		Result 
{pad:meta title='Printables'/}

<p>{app:tag 'printable:labels'/} makes pages for paper - sheets of labels, name badges, business cards, tickets
with a stub, a certificate, envelopes, a letter and an invoice for a window envelope, index cards and
place cards. There are {pad:echo php:count(padPrintableKinds())/} kinds - every kind is a file of
<code>pad/subs/printables/types/</code>, and the <a href="../printables/">printables</a> application
shows them all, each with its PDF.</p>

{common:example 'fragments/printables_1'/}

<h2>One item, repeated over the data</h2>

<p>The content between the tags is one item - a label, a badge, a letter - rendered once for every
row of the data, with the handling options of any tag: <code>sort=</code>, <code>where=</code>,
<code>first=</code>. <code>copies=</code> writes every item that many times, <code>skip=</code> leaves
the first labels of a sheet used before empty. A kind takes the parts of an item from the elements
that say what they are: a ticket's stub is its <code><aside></code>, a letter's address its
<code><address></code>.</p>

{common:example 'fragments/printables_2'/}

<h2>The screen, the paper and the PDF</h2>

<p>On the screen the sheets lie on a grey desk at their size in millimetres - <code>scale=</code>
makes the preview smaller. Printed, the page prints the sheets alone, each on a page of its own size
without a margin. And in a <code>{pad:pdf}</code>, or with <code>pdf</code> on the tag, PAD's
own PDF writer lays out the same sheets: <code>pdf</code> links them, the page asked again with
<code>&amp;padPdf</code>.</p>

{common:example 'fragments/printables_3'/}

<ul>
  <li>A sheet of one's own: <code>across=</code>, <code>down=</code>, <code>width=</code> and

<h2>A button, or the elements of the page</h2>

<p>Without <code>target=</code> the tag writes a real button that plays the sound, named after the

sound plays when an element the selector finds has the event <code>on=</code> names - <code>click</code>,

{common:example 'fragments/sounds_2'/}

<h2>One recipe, the browser and the WAV file</h2>

<p>A recipe is voices played together - sine, square, saw, triangle or noise - each with an envelope,
a pitch that sweeps or steps through a few notes, and a filter. The server settles it, every note to
its Hz, and both renderings read the settled recipe with the same arithmetic: the script renders the
samples and plays them through WebAudio, and <code>padSoundWav ( 'bell' )</code> renders them as a WAV
file - the same samples, the noise from a seeded generator, so the same bytes on every request.

{common:example 'fragments/sounds_3'/}
