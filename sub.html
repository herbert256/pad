Extend useful contracts first.

PAD already has a substantial catalogue. The best next work adds reusable data behavior, business-facing controls and precise analytical views, while keeping each subsystem’s meaning consistent.

Start with unit conversion, a highlighter registry and structured diffs. In existing subsystems, prioritize currency fields, identifier rules, fixed-width data, scalar formula functions, a Pareto chart and a navigation tree. These serve ordinary applications and can build on helpers already in this repository.

Scope: source analysis and suggestions only. No proposed subsystem or type is implemented by this report. All sample calls marked “proposed” are design sketches. Counts come from the live filesystem; source observations, design recommendations and future acceptance checks are distinguished below.

Priority: P1 strong first candidates · P2 useful follow-up · P3 demand-led or specialist. Effort: S a small definition/asset, M a renderer/adapter with fixtures, L shared-engine, layout or substantial algorithm work. These are relative scope judgments, not delivery estimates.

What the source says

Observed contractImplication for additions
18 template namespaces + 12 helper/option familiespadSubsystems and padSubsystemKinds in subsystem.php distinguish these. New rules, providers and formats do not automatically become {rule:...} or {format:...} tags.
Directory-driven discoverypadKinds() derives names from files in subs/<family>/types/ and caches them. New kinds still need their family-specific contract. A new family also needs registration, dispatch/helper wiring and documentation.
Explicit template prefixesUse {chart:pareto/}, {widget:treeview} and matching closing prefixes in future examples. The registry’s expression-lookup compatibility flag does not authorize unprefixed template tags.
Types have different meaningsA search type is a language, a map type a view, a holiday type a country, an AI/OAuth type a provider, a formula type a function. Keep options and new capabilities separate from those axes.
Shared implementation is part of the featureCharts have PHP renderers plus browser implementations and a client file map. Inputs/widgets use shared assets and form behavior. A new PHP type file alone may be discoverable while the complete feature is still missing.
Existing core features extend beyond subs/Avatars, identicons, diffs, syntax highlighting, calendar, datatable, timeline, tree rendering, translations, queues and scheduling already exist. The proposals below account for that existing behavior.

The 969 count includes aliases/selectors such as auto, wrapper kinds, formula synonyms and 232 SVG icons. It is a count of type files, not a claim of 969 independent algorithms. The scan found 737 PHP files and 232 SVG files in the immediate type directories.

Seven subsystem proposals

Four introduce a shared capability; three extract existing core behavior and then add new kinds. Directory names below are proposed.

S01 · New capability
P1 M

Unit conversion units/

Locale formatting already changes how numbers look; there is no discovered registry for dimension-checked conversion between physical units.

Starter kinds
length, area, volume, mass, temperature, digital
Contract
One definition per quantity family: canonical unit, symbols/aliases and conversion functions. A helper returns a numeric value; formatting remains separate. Temperature must support offsets, and digital sizes must distinguish decimal from binary prefixes.
Reuse
Use the existing locale/number presentation helpers and proposed input:unitpicker. A later CONVERT formula should call the same conversion engine.
Boundary
Register as helper-only kinds first. Exclude exchange rates, calendar-month arithmetic and inferred compound dimensions from the first version.
padConvert ( 100, 'cm', 'm' ); // proposed: 1

Acceptance: Round-trip and known-value fixtures; reject incompatible dimensions, non-finite values and ambiguous symbols. Test affine conversions separately from multiplicative ones.

Source basis pad/lib/subsystem.php · pad/functions/currency.php · pad/subs/formulas/_lib/functions.php

S02 · Extraction + extension
P1 M

Language definitions for syntax coloring highlighters/

padHighlightKnown currently keeps a fixed language list, and token rules live in the shared highlighter. This already behaves like a registry without a types directory.

Starter kinds
Migrate existing canonical languages; add python, go, rust, diff and a dedicated typescript grammar if justified.
Contract
Each file defines canonical name, aliases and token rules or a tokenizer callback. The shared engine owns escaping, token spans, line numbers and marked lines.
Reuse
Preserve padHighlight(), the highlight pipe and {pad:highlight}. Existing ts already aliases JavaScript: a dedicated TypeScript definition would improve tokenization, not introduce first-time acceptance.
Boundary
Use padSubsystemKinds rather than a mandatory new template namespace. Keep PHP’s tokenizer path intact; move behavior without output changes before adding languages.
{pad:highlight 'python'}print('Hello'){/pad:highlight} <!-- proposed new language -->

Acceptance: Replay existing highlight fixtures byte-for-byte; test quotes, comments, malformed source, HTML escaping and worst-case tokenization time.

Source basis pad/lib/highlight.php · pad/tags/_lib/highlight.php · pad/functions/highlight.php

S03 · Extraction + extension
P1 L

Structured comparisons diffs/

{pad:diff} already compares words and lines with a shared edit-script engine. It lacks distinct structural comparison kinds for nested data and keyed rows.

Starter kinds
words and lines (migrate); json and rows (new)
Contract
A kind normalizes two inputs and returns typed change records; separate renderers produce inline or side-by-side HTML. For rows require a stable key; for JSON distinguish object-key order from array order.
Reuse
Reuse the existing Myers edit-script engine and escaped <ins>/<del> presentation, and formats for explicit data decoding.
Boundary
Preserve existing {pad:diff}, lines and side behavior. Define key collisions, type changes and missing-versus-null semantics before implementation; comparison does not apply changes.
{pad:diff $before, $after, kind='rows', key='id'/} <!-- proposed options -->

Acceptance: Check equal data, reorder-only changes, duplicate keys, nested arrays, mixed scalar types and large inputs. Preserve accessible addition/removal labels and memory bounds.

Source basis pad/tags/diff.php · pad/tags/_lib/diff.php · pad/lib/format.php

S04 · New capability
P2 L

Bounded calendar occurrence expansion recurrences/

The scheduler already matches cron expressions. The ICS reader preserves RRULE text but does not expand it into event occurrences.

Starter kinds
daily, weekly, monthly, yearly; rrule after the common model is stable
Contract
One kind expands a validated rule into occurrences between explicit start/end bounds, with timezone, maximum count, exclusions and a documented invalid-date/DST policy.
Reuse
Feed the current calendars subsystem, printable calendar/planner and ICS format. Reuse date/holiday helpers, and let the existing scheduler continue to execute jobs.
Boundary
This computes event dates; it does not replace cron, queues or job persistence. Publish an explicit RRULE subset and reject unsupported parts rather than silently dropping them.
padOccurrences ( 'weekly', $rule, $from, $to ); // proposed, bounded result

Acceptance: Test month ends, leap days, timezone transitions, COUNT/UNTIL boundaries, exclusions and strict output limits. Check original DTSTART semantics against independent fixtures.

Source basis pad/lib/schedule.php · pad/subs/formats/_lib/ics.php · pad/subs/calendars/_lib/views.php

S05 · New capability
P2 L

Small geographic operations geospatial/

Maps render fixed outlines and formats exchange geographic data. There is no discovered shared operation registry for distance, spatial bounds or point-in-polygon queries.

Starter kinds
distance, bearing, bbox, contains, geohash
Contract
Each operation declares accepted geometry and options, and returns plain data. Establish longitude/latitude order, coordinate reference assumptions and distance units centrally.
Reuse
Consume explicitly normalized GeoJSON/GPX rows and help map applications filter nearby records. Reuse units once available, without changing static map rendering.
Boundary
Start with a documented spherical distance model and bounded simple polygons. Exclude routing, geocoding, spatial databases and arbitrary projection support.
padGeo ( 'distance', $a, $b, [ 'unit' => 'km' ] ); // proposed

Acceptance: Use independent coordinate fixtures; cover dateline crossing, poles, holes, boundary points, invalid coordinates and vertex budgets. State the accuracy of the chosen model.

Source basis pad/subs/maps/_lib/map.php · pad/subs/formats/_lib/geojson.php · pad/subs/formats/_lib/gpx.php

S06 · New capability
P2 L

Seeded statistical sampling distributions/

Fake values, chart density calculations and visual probability toys exist, but there is no shared registry for sampling named probability distributions.

Starter kinds
uniform, normal, bernoulli, binomial, poisson, exponential
Contract
Each file declares parameters, support and a sampler driven by an injected seeded random stream. Density/CDF/quantile methods are optional capabilities added only when implemented.
Reuse
Reuse or extract the fake-data random stream. Expose samples to histograms and teaching toys; keep formulas as wrappers if compatible statistical functions are later added.
Boundary
Do not confuse chart density estimation with a named probability distribution, or random sampling with PAD’s existing mathematical sequences. No cryptographic randomness promise.
padSample ( 'normal', 100, [ 'mean' => 0, 'sd' => 1, 'seed' => 7 ] ); // proposed

Acceptance: Exact seeded fixtures plus range/parameter/error tests; fixed-seed distribution checks with declared tolerances. Bound rejection loops and batch sizes.

Source basis pad/lib/fake.php · pad/subs/charts/_lib/density.php · pad/subs/toys/types/galton.php

S07 · Extraction + extension
P3 M

Deterministic identity artwork avatars/

Initials avatars and symmetric identicons already exist as core tags. More rendering styles would benefit from a common registry only if there is real demand.

Starter kinds
initials and identicon (migrate); rings, mosaic and pixelbot (new)
Contract
Each style receives a normalized identity/seed, size and palette and returns local SVG through a shared accessible wrapper.
Reuse
Keep {pad:avatar}, {pad:identicon} and their existing normalization/output semantics through compatibility wrappers. Reuse icon/SVG and palette helpers where suitable.
Boundary
These are new styles around existing features, not a missing avatar capability. Keep remote Gravatar behavior separate and do not expose raw personal values in SVG IDs.
{avatar:rings $user.id, label=$user.name/} <!-- proposed namespace -->

Acceptance: Replay old tag output, test Unicode labels and escaping, and verify same-identity stability at small sizes. Do not imply a visual fingerprint is collision-free identity verification.

Source basis pad/tags/avatar.php · pad/tags/_lib/avatar.php · pad/tags/_lib/identicon.php

A practical order of work

  1. Take a compact first batch

    Add input:currency, rules/isbn, formats/fixedwidth, formulas/textbefore and textafter. Each has a clear contract and a concrete application use. Build demos from the same deterministic fixture data.

  2. Extract one existing registry and add one new service

    Move syntax-highlighting language definitions into highlighters/, preserving existing output, then add Python and Go. Build units/ separately and use it in input:unitpicker to demonstrate cross-subsystem reuse.

  3. Complete a useful reporting path

    Add Pareto charts with client/server parity, structured row/JSON diffs, a navigation tree and dataset JSON-LD. Demonstrate a fixed-width import, validated values, before/after records and a chart in one small sample application.

  4. Choose expansion by demonstrated demand

    Recurrences unlock calendars and planners; language, country, provider and boundary datasets need an owner for updates. Add games, sounds, patterns and further visual styles after the application-driven batch.

Keep these out of a “just add types” batch

  • Dynamic-array formulas: spill semantics and array evaluation need a shared-engine design.
  • AI operations: streaming, tools, embeddings and multimodal results are capabilities, not provider names under today’s text-return contract.
  • Search backends: the search registry currently models languages. CJK segmentation requires tokenizer work.
  • Generic OIDC brands and compatible AI endpoints: use existing configurable providers unless distinct behavior justifies a dedicated file.
  • More core-framework families: routing, authentication, caching, jobs, translations, forms and collections already exist. A new directory should solve a specific variation problem, not duplicate those services.

What “finished” should mean for a future addition

  1. A declared contract. Define inputs, output, limits, errors and no-data behavior before its type file. Keep provider/country/language identifiers consistent with the surrounding family.
  2. Complete integration. Add the type, shared helper code where needed, versioned assets, an example and documentation. Register new families in pad/lib/subsystem.php; wire the relevant helper/type/tag entry point. Update the tags catalogue for a new namespace and regenerate/check editor references using the repository’s generator.
  3. Compatibility evidence. Extraction proposals first reproduce current output and helper behavior. Source examples must use the current explicit-prefix syntax even where old comments still show bare forms.
  4. Behavior-specific verification. Use native/no-script and keyboard probes for inputs/widgets, PHP/JavaScript SVG parity for charts, round trips for formats, independent numerical or symbol fixtures for algorithms, and mocked HTTP for provider adapters.
  5. The publication modes PAD already supports. Test relevant static, print/PDF, mail, fragment/live and WASM/offline paths. Mark network-dependent integrations honestly; local renderers should not accidentally acquire a remote dependency.
  6. Integration gates when implementation happens. Run focused regressions and editor checks, then the existing ./ci.sh gate against the normal supported environment. This HTML-only analysis does not claim those future features or the full framework suite have been tested.
