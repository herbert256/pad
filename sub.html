Analysis and proposals • 2 November 2026

Where PAD can grow next

Extend the strong foundations already in pad/subs/. Prioritise reusable data operations and practical views; add a new family only when it has a distinct execution contract.

47 existing subsystems1,248 file-defined kinds6 candidate families97 candidate kinds in existing families

1,007 PHP type files + 241 SVG icons. Counts include file-backed selectors such as auto, but exclude virtual selectors supplied by the registry. These figures describe the original baseline. All proposed additions are now implemented; see the implementation and validation record below.

Implementation delivered

All six proposed subsystems and all 97 proposed types in existing subsystems are implemented. The six new subsystems contain four kinds each: 121 new kinds in total. PAD now has 53 subsystems and 1,369 file-defined kinds (1,124 PHP types and 245 SVG icons).

Implementation used three parallel agents and a coordinator. Feature delivery used 103 separate commits, listed below: one for each new subsystem and one for each new type in an existing subsystem. Shared catalog, example, documentation and regression integration is recorded separately. The original agent branch histories have since been merged into master, pushed to origin/master, and their four local worktrees and branches removed. Those history merges preserved the integrated source tree exactly; private recovery bundles and file archives were retained locally. The five families marked for deferred expansion below had no proposed kind to implement.

Validation

The combined ./ci.sh run completed after integration. All 214 independent subsystem fixtures passed, along with 611 page checks, 28 common checks, 1,351 error checks, 3,481 framework checks, 263 regression checks and 566 sequence checks. Editor completion files match the engine; LSP (49), MCP (87), Claude (24), grammar/query (42), browser validation (627), WebAssembly (60) and application (90) checks passed. Chart parity passed for 79 pages, 85 charts, 55 kinds, 34 palettes and eight parity templates. All 121 new example pages and all 38 referenced local assets returned HTTP 200; focused interaction checks also passed. The combined gate exited 1 because six page expectations differed. A targeted replay after concurrent application updates passed apps/index and pad/index; four pre-existing failures remain: manual/pages/prefix, manual/prefix/types, other/reference/dir and other/reference/pages. These unrelated expectations were preserved. The tree-sitter CLI is not installed, so its corpus tests did not run. Validation was combined after integration, not repeated for each of the 97 new types.

Each type has documentation, an executable example and focused verification. New helper contracts and limits are documented in Subsystems and the family README files. The proposal sections below retain the original design rationale and priorities from the baseline review.

Recommended direction: first add missing operations to formulas, graphs, statistics, schemas and units; connect them through practical inputs and widgets. For new subsystems, intervals and colors have extraction seams in existing code, while timeseries fills a distinct data-preparation gap.

Start with three coherent slices

These priorities reflect architectural fit, reuse and implementation surface in this checkout. They are engineering judgements, not measured demand or delivery estimates.

SliceBuild togetherUseful demonstration and acceptance
Data analysisgraphs/strongcomponents, statistics/correlation, schemas/relation, then timeseries.A dependency report and a sampled-measurement report. The same computed results feed tables and charts; independent small-case oracles establish the numerical/graph answers.
SchedulingExtract intervals; add inputs/recurrencepicker, calendars/capacity and times/duration.A resource planner that expands supported recurrences and shows capacity conflicts. Existing availability results stay identical; DST and adjacent intervals have explicit outcomes.
Reporting and toolsDynamic-array formulas, tables/masterdetail, widgets/facets, printables/checklist, and new unit families.A filterable report with expandable rows and a print checklist. Server-only fallback, keyboard use, formula spill errors and print page breaks all work.

P1 = first candidates; P2 = useful next with a concrete consumer; P3 = selective or exploratory. Effort: S = existing mechanism/data definition; M = algorithm or view plus shared integration; L = parser, substantial runtime/UI work or external data. Effort is relative, not a time promise.

Six candidate subsystems

All would be siblings directly under pad/subs/. These proposals are helper families returning data; they do not need a template namespace merely to qualify as a subsystem. Rendering stays with the existing owners.

timeseries/ — Timestamped observations

P1Effort L
resample rolling ewma difference

Turn irregular measurements into chart-ready series without embedding data preparation in each chart or application.

Why a separate family

Statistics currently returns descriptive analysis; charts render values. Time-series operations add ordering, time windows, alignment and gap semantics. PAD sequence operations remain mathematical/iterative sequence operations.

Proposed contract

Rows contain an explicit instant, finite value or missing marker, and optional series key. Declare duplicate policy, fixed-duration versus calendar buckets, window alignment, minimum observations and output timezone. Missing is never silently zero. Return rows plus the chosen method and coverage metadata.

First delivery

Start with fixed-duration resample and count-based rolling windows. Add calendar buckets and EWMA after timezone/gap behaviour is covered. One shared implementation feeds charts and tables.

Acceptance evidence

Use hand-calculated irregular series, duplicate timestamps, gaps, multiple series and DST boundaries. Bound both input rows and generated buckets; reject expanding a sparse century into unbounded seconds.

padTimeSeries('resample', $samples, ['stepSeconds'=>3600, 'aggregate'=>'mean']);

Illustrative API sketch; naming and options need design before implementation.

intervals/ — Reusable interval operations

P1Effort M
union intersection subtract overlaps

Reuse the interval logic now embedded in calendar availability for maintenance windows, resource occupancy and coverage calculations.

Why a separate family

This should begin as an extraction from calendars, not a second independent availability algorithm. Calendars retain their public helper and rendering; recurrences continue to generate occurrences.

Proposed contract

Use homogeneous numeric bounds or explicit instants with half-open [start,end) semantics, grouped by optional resource. Specify empty intervals, touching boundaries, stable source IDs and whether overlap output reports pairs or merged spans.

First delivery

Preserve padCalendarAvailability as a compatibility facade and prove its answers unchanged before exposing new operations. No reservation, scheduling or database side effects.

Acceptance evidence

Check union idempotence, disjoint subtraction, conservation of finite duration, adjacency and independently enumerated small interval sets. Cap pairwise overlap output separately from input size.

padIntervals('subtract', $workingWindows, $busyWindows, ['group'=>'resource']);

Illustrative API sketch; naming and options need design before implementation.

colors/ — Colour computation

P1Effort M
convert mix contrast gamut

Give palettes, avatar text colours and design tools one explicit computational contract instead of separate colour math.

Why a separate family

Palettes remain named colour collections, themes remain semantic UI tokens and filters remain image transforms. Existing palette/avatar luminance and contrast helpers provide a concrete extraction seam.

Proposed contract

Start with explicit sRGB input/output and a named compositing background for alpha. Add perceptual-space conversion only with tested formulas. Expose mix space and gamut/clipping policy; return numeric data, never automatic accessibility certification.

First delivery

First extract the existing sRGB luminance/contrast routines with byte-compatible callers. Add general conversion/mixing behind new helper kinds without changing existing palette interpolation by default.

Acceptance evidence

Compare black/white, greys, alpha composites, reference colour vectors and round trips within stated tolerances. Preserve existing avatar/theme/palette results; test invalid channels and out-of-gamut output.

padColor('contrast', '#183347', '#ffffff');

Illustrative API sketch; naming and options need design before implementation.

geometry/ — Planar geometry

P2Effort L
hull area centroid clip

Provide reusable point and polygon operations for diagrams, custom visual tools and educational examples.

Why a separate family

Geospatial owns longitude/latitude and earth models. This family works in an explicitly planar coordinate system. Keep SVG generation and game simulation outside its API.

Proposed contract

Accept finite 2D coordinates with a caller-defined unit. Start with convex hulls, simple-ring area/centroid and rectangle clipping. Specify closure, orientation, holes, collinearity, degenerate results and numerical tolerance.

First delivery

Ship hull and simple polygons first. Do not promise robust arbitrary polygon Boolean operations; promote only after two concrete consumers need a shared helper.

Acceptance evidence

Use analytically known shapes, translation/rotation invariants, degenerate points and independent fixtures. Reject unsupported self-intersections and cap vertex/output counts.

padGeometry('hull', $points);

Illustrative API sketch; naming and options need design before implementation.

numerics/ — Bounded numerical methods

P3Effort L
interpolate integrate root linear-system

Support small scientific calculators without forcing numerical methods into spreadsheet formulas or descriptive statistics.

Why a separate family

Statistics remains sample analysis, constraints remains discrete combinatorial solving, and formulas remains spreadsheet semantics. A dedicated family is justified only if several standalone callers materialise.

Proposed contract

Start with piecewise-linear interpolation of sorted samples, sampled trapezoidal integration, bracketed roots and bounded dense linear systems. Return status, iterations, tolerance/residual metadata. Functions are trusted PHP callables, never evaluated user text.

First delivery

Treat as exploratory. Implement one small demonstrated calculator before registering the whole family. Do not return a success result after exceeding a numerical work budget.

Acceptance evidence

Use analytic polynomials, singular/ill-conditioned matrices, invalid brackets and independent numerical references. Set evaluation, dimension and memory limits and document floating-point accuracy.

padNumeric('integrate', $samples, ['method'=>'trapezoid']);

Illustrative API sketch; naming and options need design before implementation.

signals/ — Sampled-signal analysis

P3Effort L
spectrum convolve correlate window

Let educational and audio-analysis pages inspect bounded sampled data and feed ordinary charts with the result.

Why a separate family

Sounds synthesises short recipes; toys provide interactive demonstrations, including Fourier. Signals would provide reusable numeric sample results. The existing notation:signals draws maritime flags and has a different purpose. This family should not become an audio recorder or a second sound renderer.

Proposed contract

Finite sample arrays, explicit sample rate, window function, scaling and edge/padding rules. Define one-sided spectrum bin frequencies and amplitudes. Begin with short offline arrays; no browser microphone access.

First delivery

Defer until a real analysis page needs it. First compare a small transform against a direct reference, then optimise behind the same contract; compose results with existing line/heatmap charts.

Acceptance evidence

Check impulses, constant signals, known sinusoids and convolution identities. Cap sample lengths and operations, and make aliasing/sample-rate assumptions visible in examples.

padSignal('spectrum', $samples, ['sampleRate'=>8000, 'window'=>'hann']);

Illustrative API sketch; naming and options need design before implementation.

Fit additions into the existing architecture

Keep ownership flat and explicit

New directories go directly below pad/subs. A kind is a file in its owner’s types directory. Use padSubsystemKinds for a helper registry; add padSubsystems and a type dispatcher only when there is a real rendering tag. Keep explicit namespace prefixes and virtual selectors separate from actual file-backed kinds.

Extend shared dispatch deliberately

A file is discoverable automatically, but its execution contract may still need work. Graph weights, sub-day recurrences and new formula matrix operations affect shared validators or dispatchers. For each addition, inspect every consumer rather than assuming a new file alone is sufficient.

Prefer extraction with compatible callers

Intervals and colors should first reuse proven existing behaviour. Keep the old calendar, palette and avatar entry points as facades while comparing their outputs. Avoid introducing a second implementation and migrating callers opportunistically.

Separate data, presentation and effects

Compute analysis in helpers; show it through tables, charts or widgets. Views should not perform hidden provider calls, reservation writes or scheduling. Input controls emit explicit values that existing server validation can check.

Carry the whole integration surface

Update the owner’s guide, runnable examples, tags/reference catalogue, editor metadata and applicable static/WASM exports alongside implementation. Reuse existing asset loading, CSP nonces, translations and fragment lifecycle hooks. A new showcase should live with its current owner application.

Require evidence proportional to the kind

Use independent numeric/graph oracles; PHP/browser parity where both runtimes exist; hostile/empty/limit inputs for parsers; keyboard and no-JavaScript checks for controls; deterministic seeds for generated data; and visual/PDF checks for printables. External formats and datasets need primary references and provenance before implementation.

Avoid creating these as new subsystems: another form-validation layer (inputs/rules/schemas already own it); another table or chart package; another workflow executor disguised as diagrams/constraints; another search language as an AI model; or a new framework-wide “utilities” registry with unrelated contracts.

Likewise, adding marker mode to maps, another period option to calendars, palette interpolation settings, formula aliases or theme density is usually an option/shared-helper change, not a new kind.

Scope, evidence and limits

This report inventories every direct subsystem directory and every non-hidden file in its types registry. It reviews the central registry, public helper dispatchers, family guides, representative handlers and shared implementation seams. Source links resolve relative to this repository-root HTML file.

This is an architectural and feature-opportunity review, not an exhaustive correctness/security audit of every implementation. Existing subsystem test suites were inspected as validation routes; this analysis does not claim they were executed or that the proposed algorithms are implemented. External provider protocols, holiday law, standards compliance and source-data licensing have not been independently researched here; relevant proposals explicitly require that work before implementation.

Documentation drift found: pad/subs/README.md still says “25 directories” and mentions nested families, whereas the live registry and docs/SUBSYSTEMS.md describe the flat 47-family layout. Several family overview lists also lag type additions (for example diffs omits unified in its opening table). Count and gap decisions in this report use the current filesystem and code, not those older list summaries. Correct the guides as a separate documentation change.

What “type” means here: the filename-defined kind within a subsystem, including SVG icon files, provider definitions, language definitions and callable data operations. It does not mean that every such kind is a public template tag. The six candidate families contribute a further 24 proposed kinds, separate from the candidate-kind total for existing families.
